# HANDOVER · 科学试模群串台根因分析交接

## 一、 背景与调查对象

在“科学试模助手”飞书群（绑定 Live Room `cmrp0vqmz000014f2f12alk32`，涉及成员：`antigravity`、`codex`、`kimi-code`、`pi-agent`）的日常多角色交互与协作中，近期出现了两类典型的“串台、抢话、回复错位与跨 Agent 任务混淆”问题：

1. **Speaker 漂移与意图截胡**：用户使用飞书 `@本地AI助手` 发言，期望默认 Speaker 回复，但特定语句被分发给 `pi-agent`。
2. **跨 Agent 共享上下文污染与代词消歧混乱**：用户与 `kimi-code`（lkc）和 `codex`（lcx）交替讨论不同需求后向 Codex 下达规划指令，Codex 误将 lkc 的 Bug 清单当成自己的规划目标。

本文档汇总 Antigravity 与 Codex 对现场数据库、调度元数据与源码链路的联合排查结论与演进治理方案。

---

## 二、 问题一根因：`@本地AI助手` 触发 Speaker 漂移与意图截胡

### 1. 现象复现
房间当前配置的默认 Speaker 为 `antigravity`，但用户（如 Shaw）在群内通过飞书客户端 `@本地AI助手` 发送如下长指令时：
> “...预计要更改哪些文件，因为等会我的同事还要改其他东西，需要让他知道哪些文件你在改，避免冲突，**还有上次更改没有写文档的先写文档**”

系统并未分发给 `antigravity`，而是分发给了 `pi-agent`。

### 2. 技术根因链条
1. **飞书 `@` 机制与 Agent 别名不匹配**：
   - 飞书 Webhook 传入结构化提及名称为 `mentionNames: ["本地AI助手"]`。
   - 在 [`src/lib/agent-identity.ts`](file:///data1/code/agent-platform-v2/src/lib/agent-identity.ts#L187-L237) 中，各 Agent 成员在房间中注册的别名列表如下：
     - `antigravity`: `['lag', 'local-antigravity', 'antigravity', 'Platform Local (hello) / Antigravity CLI']`
     - `pi-agent`: `['pi', 'local-pi-agent', 'pi-agent', 'Platform Local (hello) / Pi Agent CLI']`
     - `kimi-code`: `['lkc', 'local-kimi-code', 'kimi-code', 'Platform Local (hello) / Kimi Code CLI']`
     - `codex`: `['lcx', 'local-codex', 'codex', 'Platform Local (hello) / Codex CLI']`
   - **群内没有任何成员注册了 `"本地AI助手"` 这个别名**，因此当用户仅使用客户端 `@` 而未在正文中附带 `$agent` 时，[`resolveFeishuMentionMemberIds`](file:///data1/code/agent-platform-v2/src/lib/feishu-live-room.ts#L140-L187) 无法匹配到任何具体成员（`explicitMentionMemberIds = []`，`targetLocked = false`）。
2. **文档专员（Documentation Specialist）意图正则劫持**：
   - 当消息未显式锁定目标成员时，系统进入 [`resolveDocumentationTarget`](file:///data1/code/agent-platform-v2/src/lib/live-room-messages.ts#L593-L612) 意图路由。
   - 该逻辑使用正则表达式扫描全文：`/(?:出|写|生成|提交)(?:个?\s*)?(?:文档|记录|HANDOVER)/i`。
   - 当前房间中，`pi-agent` 的特长字段注册为 `specialty: "documentation"`。
   - 用户长消息末尾的“...**先写文档**”命中了该正则，系统将元数据标记为 `targetResolutionSource: "specialty_documentation"`，强行将目标指定给 `pi-agent`。
3. **默认 Speaker 回退机制**：
   - 只有在既无显式 `$agent`、**又未命中任何 Specialist 意图**时，系统才会回退到 `currentSpeakerMemberId`（`antigravity`）。
   - **结论**：并非不同用户绑定了不同 Agent，而是正文中随口提及的词汇触发了平台 Specialist 意图分发。

## 三、 问题二根因：Codex 跨 Agent 规划串台与上下文交织

### 1. 现场消息时间线还原（2026-08-28 上午真实记录）
1. **08:50:10** 用户发给 `$lkc`（`kimi-code`）：
   > “有两个点需要优化：1. 针对多段信息页面，查看记录时只能看到第一段（射出、温度、熔胶、保压无法切换）... 2. 合模页面顶退段从 2 开始计数...”
2. **08:54:57** 用户发给 `$codex`（讨论轮次继承增压比）：
   > “若来源机台当前已审批主数据与冻结 Run 不同，显示冻结值 1 → 当前已审批值 10... 这个我理解是说即使机台信息没更新，但我试模时可以现场纠正...”
3. **08:55:21** `kimi-code` 针对多段只读与顶退问题输出理解与改动范围说明。
4. **08:55:24** `codex` 针对增压比现场纠正与审计规则输出理解。
5. **08:58:02** 用户发给 `$codex`：
   > “@_user_1 $codex， ok，那你先写个计划，特别是涉及要更改哪些文件，明确列出我反馈的问题，以及针对问题你的措施和实施方案”
6. **09:02:51** `codex` 开始执行并输出计划，内容却变成了 `210_PLAN_20260828_历史多段只读导航与顶退编号修复.md`（规划了多段只读切换与顶退从 1 开始计数）。

### 2. 技术根因分析
1. **共享单一 Task Room 与上下文平铺**：
   - 飞书绑定的 Live Room 底层共用同一个任务会话。群内所有发给不同 agent 的消息（无论是发给 codex 还是 lkc）都会平铺存入同一个 Task Chat Room。
2. **Prompt 组装机制 [`buildHarnessPrompt`](file:///data1/code/agent-platform-v2/src/lib/acpx/prompt.ts#L40-L79)**：
   - 向 Codex 发送指令时，系统提取用户最新指令作为 `Latest task-room instruction`：
     `“$codex， ok，那你先写个计划，特别是涉及要更改哪些文件，明确列出我反馈的问题...”`
   - 同时通过 [`buildTaskRoomPromptContext`](file:///data1/code/agent-platform-v2/src/lib/task-room.ts#L274-L332) 抓取群内最近 12 条/4000 字符的历史消息作为 `Recent task-room transcript` 拼接到 Prompt 中。
3. **指代消除与多角色上下文交织（Context Interleaving）**：
   - 用户在 08:58 发给 Codex 的指令使用了泛指代词“**我反馈的问题**”。
   - 在 Codex 接收到的群聊历史中，前面紧挨着发给 lkc 的具体 Bug 描述（“1. 多段信息... 2. 顶退段...”）以及发给 Codex 的增压比讨论。
   - 由于发给 lkc 的问题包含了非常清晰的“问题 1、问题 2”编号，Codex 在消歧解析 `Recent task-room transcript` 时出现混淆，误将 lkc 的 Bug 采纳为自身计划目标。

## 四、 既有治理机制与相关方案关联

1. **飞书结构化单 Mention 目标锁定**（见 [`98_REMOTE_PI_AGENT_AND_FEISHU_TARGET_LOCK_HANDOVER.md`](file:///data1/code/agent-platform-v2/docs/98_REMOTE_PI_AGENT_AND_FEISHU_TARGET_LOCK_HANDOVER.md)）：
   - 当消息包含单一结构化 mention 时，`feishu-live-room.ts` 打上 `targetLocked: true`，抑制向其他候选 Agent 降级，避免抢话。
2. **Workflow 会话按 Role/Slice 严格隔离**（见 [`413_PLAN_20260813_工作流执行权限与会话连续性.md`](file:///data1/code/agent-platform-v2/docs/413_PLAN_20260813_工作流执行权限与会话连续性.md) 与 [`451_PLAN_20260824_每个Slice强制新Session.md`](file:///data1/code/agent-platform-v2/docs/451_PLAN_20260824_每个Slice强制新Session.md)）：
   - Workflow 内部保持按 role 隔离，避免一人分饰 planner+reviewer 串台；每个新 Slice 派发强制换代 fresh session，消除低水位复用导致的旧上下文污染。

## 五、 系统性改进建议与防御措施

1. **飞书 Mention 别名与通用 Bot 映射**：
   - 在 [`src/lib/agent-identity.ts`](file:///data1/code/agent-platform-v2/src/lib/agent-identity.ts) 或群房间配置中，将“本地AI助手”等通用 Bot 名称显式映射为默认 Speaker 或广播路由，避免别名未命中导致的意图走偏。
2. **收紧 Specialist 意图分发正则（Intent Guard）**：
   - 改造 [`src/lib/live-room-messages.ts`](file:///data1/code/agent-platform-v2/src/lib/live-room-messages.ts) 中的 `resolveDocumentationTarget`：
     - 增加主干判定，仅在“生成交接/写文档”是句子核心谓语且消息较短时触发；
     - 排除作为从句、条件状语（如“...没写文档的先写文档”、“写完记得记录”）出现的场景；
     - 若当前已有明确对话上下文，优先尊重会话连续性，不盲目截胡。
3. **Task Room 上下文目标感知与分角色投影（Target-aware Context Projection）**：
   - 改造 [`src/lib/task-room.ts`](file:///data1/code/agent-platform-v2/src/lib/task-room.ts) 的 `buildTaskRoomPromptContext`：
     - 在 `Recent task-room transcript` 中为每条历史消息清晰标注 `Target: codex`、`Target: kimi-code`；
     - 或按目标 Agent 过滤其他 Agent 的深度上下文细节，降低 LLM 在代词消歧时的交叉污染。
4. **群聊协作交互规范（操作指引）**：
   - 在多用户、多 Agent 并发讨论不同任务时，如果上一轮指令隔了几条其他 Agent 的对话，在要求 Agent“写计划”或“开始实施”时，建议在 prompt 里简要携带具体模块名称（例如：`$codex 请针对刚才讨论的 TX23058 轮次继承增压比审计问题写计划`）。
