## 实际实现与原子边界

1. 新提议沿 `validateExecutionTargets` 的共用入口解析实施者和验收者模型，覆盖新建、卡片配置、命令改派和批准。
   `graphRoleOptions` 将房间成员的 model / reasoningEffort 传入实际 participant；命令改派复用这些设置。
2. 新增 `acceptance-models.ts`：复用任务 Harness 使用的共享配置来源，优先显式 participant.model，
   否则读取 Codex 默认/profile 或 Kimi 默认配置。复用 CLI 模型目录核对可选性；Kimi 别名再解析到实际 model。
   比较实际 model，不比较 Agent 名、Harness 名、供应商名或会话 ID；验收者须不同于每个实施者。
   未知、同模型、目录不可用或未登记模型均拒绝，不自动另选模型。
3. 解析结果写入 `acceptance.models`，同时把明确模型选择固定到 participant.model，进入审批快照哈希。
   卡片展示实施与验收模型。批准时只验证；配置漂移要求重新配置并确认，不能改写已确认快照。
   实施与验收派发前再次核对固定模型；Kimi 别名变为同模型时停止派发。
4. 新增 `acceptance-evidence.ts`：在既有 TASK_GRAPH_REVIEW 结果中增加 verification，绑定 execution inputs、
   固定仓库提交组合及每条批准命令。逐项记录准确 argv、实际 exitCode、日志位置/摘要和环境指纹。
   缺项、错误 SHA、错误命令、非零退出码或缺日志/指纹不能成为批准。
5. `collectGraphReview` 继续使用原有一次有界补收与持久化 claim；新增可选的回执校验。
   无法执行检查可返回明确阻塞，不伪造通过。协调器保存有效回执，事务发布入口再次检查固定输入和回执。
   验收期间污染工作区仍被原有只读/clean 校验拒绝，`assertCandidateInputsIntegrated()` 保留。
6. 完整复用 `agent_owned_v1`：实施者仍自测，验收者实际执行批准检查，平台不增加第三轮业务测试。
   平台检查模型、权限、版本及回执一致性；环境哈希不表示平台亲自证明业务测试正确。

超出原预计两处生产文件的修改均属于同一显式验收入口：角色设置 → 模型解析与审批快照 →
派发 → 结果收取 → 账本发布，外加卡片准确显示。只在协调器增加一个布尔判断会留下入口或发布绕过。
为可靠解析实际 TOML，新增锁定依赖 `smol-toml`；Kimi 既有目录读取抽出复用函数，原命令展示保持。
没有数据库迁移、新状态机、新调度引擎或 S03 失败分类清理。

| 路线 | 行为 |
| --- | --- |
