# 任务目录授权与原会话接续

2026-10-25。按 Feishu DM 08a216 最新指令实施：先修复平台 HEAD 变化触发重试，再实现目录审批卡。源码与隔离测试已落地；M6 实际回归和分服务生效状态见[修复记录](../../../output/reviews/yizumi-permission-card-regression-20261025/report.md)。原实现证据见[实现与验证报告](../../../output/reviews/resource-approval-20261025/report.md)。

## 用户操作

Agent 在已有权限内直接准备依赖和运行测试。需要额外目录时，一次列出用途、目录及只读/读写需求，平台发一张卡：

```text
补充资源授权 · 待决定
任务与执行者：当前任务 / Codex / 原角色
用途：读取参考仓并保存测试产物
只读 /data/references
读写 /data/task-output
范围：当前任务，后续会话沿用

[批准并继续] [调整范围] [拒绝]
```

目录只是示例。宿主目录授权由配置的飞书管理员决定；用户无需转发请求或修改配置。任务原话题收到卡片，无绑定时发管理员；非管理员发起时另发管理员副本，两处引用同一个决定并保存消息 ID。

“调整范围”允许移除目录、降低为只读，或由管理员选同项目复用。修改后产生新版预览，再批准；旧按钮不能批准新范围。项目复用要求持久项目目录与用户归属，并继续限定主机、角色、执行后端、harness 和 Agent 身份。

批准后无需再说“继续”。卡片分别显示等待原进程退出、正在准备、已经接续及失败原因。普通会话的接续答复显示在该卡片中；任务图继续使用已有执行/验收答复链路。

## 已实现范围

| 能力 | 行为 |
| --- | --- |
| 本机 Codex | 支持普通会话、任务图实施者、架构复核和验收者的目录申请；原 Session 与原 cwd 接续 |
| 多目录 | 一次申请多个目录，实际 Bubblewrap 只读/读写绑定 |
| 原生审批 | 边界内操作继续走原进程审批；结构化越界文件请求转成资源卡，拒绝当次越界操作 |
| 原生本轮权限 | 保留原生 method/scope 和目录结构，卡片区分本次操作与本轮 |
| 启动前申请 | 服务端 `requestResourceAccess` 可在没有 TaskRun/Session 时创建申请；首次 Session 由平台原子创建 |
| 持续授权 | 当前任务默认复用；管理员可选同项目、同归属、同执行身份复用 |
| 准备失败 | 保留批准和实际失败原因；普通会话、尚未派发的任务图申请可点“重试准备与接续”，校验原归属后复用原 Session |
| 撤销 | 立即停止新增使用；执行端读取数据库撤销状态并停止进程，证明退出后才显示已撤销 |
| 重启 | 扫描持久申请，批准而未派发的继续处理；已预留但进程消失的普通执行显示可重试，不自动重复原生操作 |

当前只允许已验证启动屏障的本机 Codex 获得这类授权。其他 harness/远程后端不能收到“已挂载”的虚假承诺。网络扩权、系统安装、服务变更、glob/special 原生权限不属于目录卡范围，明确拒绝未知权限形状。

资源卡不新增任务图的交付职责。实施轮次可申请额外仓的读写目录，管理员批准后挂载；已有只读子目录（如依赖环境）仍保留只读。其他 execution 的 worktree 和当前工作区的父目录不能授予写权限，验收与只读问答不能升级为实施者。补充仓的改动需单独提交、验证，原任务固定输入与验收仍按原合同执行。平台不自动创建新的 Git worktree。

2026-10-25 实际 M6 回归修复：执行服务、飞书回复服务与飞书主服务是三个独立进程，必须分别核对生效。旧进程将资源申请记为 waiting_for_user 时，可由原 TaskRun 绑定的明确审批继续，无需改写旧执行结果；必须核验 source、claim、原 Session 和真实退出。

任务图批准回调只保存决定和更新卡片，由调度服务统一完成准备，使用该服务的宿主容量配置。准备失败不取消批准；重试核验同一审批 wake 的 conditions-unavailable 与 admission-deferred 账本、claim、revision 和完整当前 progress，不能把任意 environment_failed 当成授权继续。已经派发的任务图运行仍通过原任务恢复入口处理，不能用资源卡重放。等待重试时，卡片保留实际失败原因。

完成任务的只读收尾问答可使用已有范围；新增资源申请不能借机恢复已完成任务。任务图只读问答的新增授权自动接续暂未开放，必须通过原任务调度入口；本轮不改写这类会话的发布权。

## 运行约束

1. 模型仅提交用途和目录。任务、角色、主机、申请人及原运行身份由平台补全；回调批准者取平台已认证身份。
2. 提案保存目录 realpath、device/inode；批准、登记使用及启动时复核。宿主根目录不能授权，路径替换后必须新提案。
3. 资源运行使用严格只读根，不自动挂载只读目录内符号链接指向的其他目录。同一路径或写入只读根内部的冲突直接报告；可写目录下既有的只读子目录明确保留只读，并由真实沙箱回归验证。
4. 使用登记与撤销共用审批行锁；TaskRun 保存授权 ID 并集，参与者保存实际目录。撤销无法漏掉先前参与者。
5. 补充写目录与其他运行的基线/补充写目录双向校验，祖先目录和符号链接别名同样受控。冲突时须有实际 Writer 退出证明；历史终态本身不够。
6. Task 创建 Session 与派发分别锁定持久身份，重复回调和跨进程并发只允许一次预留。已停止的源运行、暂停任务、换掉的 Session 不会被资源审批自动恢复。
7. 恢复前验证原生 Session；先校验再保存身份。不能恢复时保留现场，不另开新 Session 冒充接续。
8. 任务图资源批准只进入指定 execution 或 review 的原调度准入。复核使用新的阶段 claim，但保留原验收目录回执、固定候选及原生 Session。用户暂停和依赖约束继续有效。

单 Writer 核验覆盖所有运行中的本地任务，以及登记过 graphWriter 或 resources 的运行（包括终态）。这些运行缺少实际退出证明时不能靠“已完成”放行。资源登记机制上线前已结束、从未登记 Writer 的普通会话只是历史记录，不自动成为永久目录锁；其中历史 full_access 也不构成永久的整机排他锁。

## 实现入口

使用既有 `FeishuAdminApproval` 的 `task_resources` 类型，无数据库 schema 迁移。批准决定与应用进度分开；申请版本、决定、应用历史和消息回执保存在 payload。

Agent 最终输出：

```text
<resource-request>{"purpose":"读取参考仓","resources":[{"path":"/data/references","access":"read"}]}</resource-request>
```

这是一段运行协议，不是飞书聊天命令。申请必须独占最终答复，不带说明文字或 Markdown 代码围栏；普通正文、行内引用、引用块和围栏示例中的标记不作为申请。独立 JSON 申请缺少结束标记或字段不合法时仍报协议错误。Codex 原生结构化越界请求也复用该入口。没有新增用户身份或授权令牌的模型输入字段。

- `src/lib/task-resources/access.ts` / `model.ts`：范围、身份、去重、决定和持续授权。
- `cards.ts` / `delivery.ts`：卡片、版本化编辑及原话题/管理员路由。
- `runner-protocol.ts` / `runtime.ts`：可信来源、真实运行权限与会话预留。
- `process-guard.ts` / `writer-boundary.ts`：撤销执行及多任务写入边界。
- `reconcile.ts` / `recovery.ts` / `retry.ts`：批准应用、重启处理和显式重试。
- `graph-admission.ts`：指定阶段准入和原验收目录回执。

## 平台 HEAD 重试修复

平台代码 HEAD 与 `.next/BUILD_ID` 不再参与自动恢复条件。自动准入按候选、上游输入和任务运行资源身份判断；旧版包含全局 HEAD 的回执按这些语义字段兼容去重。任务相关资源恢复和显式定向恢复仍可继续原阶段，累计尝试数不清零。其他票的代码提交不授予重试权。

## 验证界限

回归使用隔离 PostgreSQL schema、真实子进程与 Bubblewrap；Codex 模型输出和飞书投递使用测试替身。测试覆盖实际目录读写、原生身份、撤销、跨进程派发、实施与验收接续、暂停及 HEAD 不重试。未将测试卡片发送到真实飞书话题，也未声称完成线上真人审批验收。
