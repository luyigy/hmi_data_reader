# WR02：检查失败后在同票内自动修复并接续最新成果

状态：拆分待确认，尚未发布或派发。

## What to build

让一张票在实施、结果补收和集成前检查之间自动推进；保存本轮候选提交及失败阶段，修复后自动再查，不要求用户反复发继续。

## Acceptance criteria

- [ ] 复用现有执行记录和领取机制，在检查前持久化阶段、候选提交、原基线、TaskRun 关联与单调 revision；不新建第二套派发器。
- [ ] 阶段 outcome 与审计事件原子落地；可恢复结果自动排成到期 ready，由协调器生成新 claimToken 领取，不依赖飞书消息。
- [ ] 注入首轮代码检查失败，下一轮读取原命令和错误自动回修，通过后继续原验收；人工 resume 次数为零。
- [ ] 缺少结果尾注仅有限补收一次；仍无有效结论进入显式耗尽状态，不合成 delivered 或 passed，不靠普通继续清零预算。
- [ ] 暂停补充文件及属于当前执行的新提交完整保留；恢复读取当前候选，不回退旧 blocked 保存点。
- [ ] 过期 token、过期 revision 和重复 outcome 无法覆盖候选、阶段或重复扣预算。
- [ ] 迁移实施、结果解析和集成前故障的旧写入口；结构化状态是唯一恢复依据，旧事件仅作审计或受控迁移。

## 执行方式

本票按 poteto-mode 的 Bug fix 流程实施：先复现真实故障并保留红色测试，再沿已确认架构修复，运行实际行为回归后交独立验收。技能及项目适配在每个新 Session 显式加载。平台负责批准路线、依赖、受控提交和集成；Agent 不自行扩大权限或派发其他票。

会话结束、代码有变化或结果格式可解析均不等于验收通过。保留原审批、历史证据、原仓文件和既有项目环境。超时后先核对现有操作，避免重复执行。
