# 手动聊天与任务图分离，并打通 M06 交付

状态：draft，2026-10-25。路线与逐票状态见 [558 PLAN](../../558_PLAN_20261025_双通路与M06纵向切片.md)。

## 用户可观察的成功条件

手动主对话在没有任务图调度与展示进程时仍正常工作；已启用任务图的 M06 话题中，
用户像与普通 Agent 一样提问、补充信息和明确要求继续。问问题不自动恢复业务，
内部重试不刷卡，权限批准后原会话实际获得对应能力。最后拿到 M06 修复的正式验收与汇合证据。

## 两条运行通路

| 行为 | 手动聊天通路 | 已启用任务图通路 |
| --- | --- | --- |
| 进入条件 | 普通房间/主对话，没有明确启用任务图的绑定 | 用户批准的路线及稳定任务绑定 |
| 消息 | 投递给所选原 Agent，保留 Native Session | 投递给话题中明确目标的原角色及 Native Session |
| 卡片所有者 | 聊天运行时及其投递恢复设施 | 任务图所属对话轮次及其投递设施 |
| 调度 | 不读取任务图状态决定普通聊天能否回答 | 对明确实施/验收动作检查依赖、占用、批准及候选 |
| 普通文字 | 交流内容 | 交流内容；不因出现 M06、继续的引用或错误说明而改变业务状态 |
| 能力申请 | 通用授权设施，回到原聊天身份 | 同一通用授权设施，加任务图工作区与角色边界 |

可共用渲染、发送、持久回执和权限校验模块；共享设施必须能脱离任务图运行。
绑定由真实入口与已保存归属决定，不按任务名称前缀、对话文本、是否曾有图或某服务是否在线猜测。
停用图调度不撤销既有 Agent 的通信能力；能否继续写业务代码仍服从真实授权和写占用。
两个消费者同时存在时不能重复认领、补投或覆盖彼此卡片。

一轮以原 Agent 的一次连续回答为边界；运行中通过 steering 接收的补充消息继续更新当前卡，回答结束后新发起的一轮才新建卡。
同一轮的内部派发重试保留同一回复身份，不为运行中的每条补充消息另建卡或新增逐消息卡片账本。
此定义按用户 2026-10-25 的澄清更新：模拟普通主对话体验；实施者与验收者只保留各自会话身份。
自动阶段没有用户源消息时，用稳定阶段身份；阶段内重试不能伪造新用户轮次。
用户明确批准能力后产生的接续，显示审批和应用结果，不能混淆为用户又发了一条消息。

## 三层职责

- to-tickets：目标、业务范围、仓库与基线、依赖、验收与命令、默认环境画像、不变量。
  本包依赖由本地票保存；不让票描述沙箱内部实现、数据库恢复步骤或 Session 状态机。
- 平台：稳定身份、单写作者与隔离工作区、宿主资源保护、消息转发、能力审批、冻结候选和验收汇合。
  安全上拒绝一个动作时，返回可解释事实；不能把 Agent 的明确能力阻塞改为业务继续执行。
- Agent：读代码、核实环境、应用 pstack、安装授权范围内依赖、处理工程错误、申请缺失能力、提交验收证据。
  业务是否通过由批准验收合同决定；一轮回答结束不等于票完成。

状态控制采用有身份、事件 ID、类型和明确内容的工具/结构化事件。
身份由运行时注入，Agent 不提供审批人或任意 TaskRun 身份。自然语言和展示摘要不参与状态推断。
S05 先覆盖资源申请；S06 覆盖所选新票的进度、提问、阻塞和提交验收。
其他旧协议通过显式兼容入口读取，不静默重释历史票或历史消息。

## 必须保持的不变量

1. Task、角色、Native Session、话题、轮次和 worktree 归属稳定；实施者和验收者不混用身份。
2. 一任务同时最多一个活跃实施写作者，一写作者使用其隔离 checkout；观察必须证明退出，不能只看状态。
3. 锁外完成慢观察，锁内重验身份和版本再认领；不以扩大事务超时或取消退出核验代替修复。
4. 已批准资源必须在最终启动方案中验证；仍只读时明确报告应用失败，不能显示已生效。
5. 固定输入与原验收证据不被覆盖；共享原仓未提交修改保留；Git 历史只追加。
6. 提交验收后冻结候选，独立验收与按仓串行汇合仍成立；不以“Agent 回答完成”释放依赖。
7. 重试复用回执；结果未知先对账；卡片 PATCH 失败不靠新增卡掩盖；旧终态不被晚到增量覆盖。
8. 手动修复不启用旧 watcher、不发布 Issues、不启动本包任务图；不影响无关生产 TaskRun。
