## 当前约定

1. 先通过讨论和原型确定 Spec，再拆成纵向 Slice tickets。项目 tracker 使用 Gitee。
2. Issues 提供任务目标及依赖；平台生成路线提议。人在父任务飞书卡片确认后，平台按获批快照执行。未确认的提议不派发。
3. 父任务和子任务话题都可讨论、补材料。明确要求继续验收时，平台接续原任务；存在多个目标时只追问目标，不让用户搬图或重建任务。
4. 并行任务使用独立 worktree。同一仓内任务的实施、检查和验收复用交付工作区，不再按角色创建额外验收 worktree。
5. 实施、检查和验收默认只读复用源项目的既有 Python 环境。模型认证与会话状态继续隔离。
6. Git 提交和集成由平台执行；模型不能写共享 Git 元数据。验收源码与图片只读，临时服务、数据库和报告使用可写测试运行目录。
7. 新工作不创建 PLAN/HANDOVER 接力文件，不依赖 `next_action` 或旧 watcher 启动下一会话。不引入 Sandcastle。

## 一次任务如何执行

- 父任务 Agent 从 Spec 和真实 Issues 准备路线、分工、模式及依赖；用户在飞书确认整条路线。
- 平台只释放前置条件满足的 Slice，创建仓内任务、工作区和绑定子话题。
- 实施者在工作区修改代码并验证。项目已有环境只读，模型认证目录独立。
- 平台受控提交，在同一交付工作区执行批准的检查；检查成功后才更新集成分支。
- 平台按获批模式进行架构审查、独立验收或仅实施交付。验收角色在可写运行目录开展测试，读取固定交付源码、冻结 Spec 副本和父子话题材料。
- 验收通过并满足批准完成条件后释放后继。仅实施模式标记 `delivered_unverified`，不能解释成独立验收通过。
- 关键状态回到父任务；子任务保留可问答入口、交付回复及证据。

### 补图与恢复

用户在父或子话题补充图片并明确说“用这张继续验收”，平台校验原发言者、绑定话题、目标节点和当前状态，再登记持久请求。相同原消息去重；运行中或已完成的任务不会重复启动。目标不唯一时回复 Slice 代号即可选择，取消或超时不沿用旧选择。

材料取得不等于验收通过。图片模糊、答案来源缺失或需求范围变化仍可能需要用户补充信息。

### 自动回修的边界

独立验收返回结构化 `in_scope_defect`，且对应批准的验收项时，平台最多两轮交回原实施者修复，再重新集成和验收。没有有效代码变更会停止；新提交不能复用旧提交的架构通过结论。

`blocked_require_human`、无有效分类、缺材料或范围变化不会自动实施。该回修机制不覆盖所有派发或集成环境故障。R02A 此次集成检查失败由受控恢复脚本处理，没有把它伪装成自动回修成功。

## 项目环境的最终选择

详细配置见 [项目运行环境复用](../../architecture/project-runtime-environments.md)。

- 默认从源仓库选择已有 `.venv`。配置位于源仓 `.agent-platform/project-environment.json`，可指向其他既有 venv/Conda 环境。
- worktree 不创建自己的虚拟环境，也不能通过自己的配置覆盖源项目选择。
- 沙箱自动设置 PATH、VIRTUAL_ENV 和禁用 Python 用户包的选项；保留虚拟环境 Python 的调用路径，避免符号链接解析后误用系统 Python。
- 源项目环境在三个阶段都只读；依赖变更单独报告处理，避免并行任务互相升级依赖。
- 删除从 Harness 私有 HOME 扫描 Python 包、要求验收 Agent 手写 PYTHONPATH 的过渡逻辑。
- 没有 `.venv` 且无显式配置的项目沿用原工具链；无效显式配置直接报错，不静默换环境。
- 任务清理保留项目环境。只读挂载限制沙箱写入，不阻止宿主从外部更新环境，因此不承诺依赖字节级冻结。
