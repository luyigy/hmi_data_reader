# Spec：可对话、受限执行、以 Issues 管理的任务工作流

版本：2026-10-17 v1。基于当前房间的讨论、HTML 演示及 Antigravity 审查整理。

状态：本轮授权发布 Spec 与 tickets；尚未批准角色分配或启动实施。Issue 标签表示可被规划和领取，不代替飞书执行审批。

## Problem Statement

用户只能通过飞书操作，希望讨论后明确需求，再由 Agent 拆成纵向 Slice，确认一次分工与执行模式后按依赖自动推进。目前存在三类可见缺口：

- 子任务话题接收了用户提问，却没有可回复 Agent；自动执行与日常对话没有形成同一条任务链路。
- 受限环境缺少工具、凭据刷新、Git 元数据和报告目录的细分授权；放开宿主机权限又扩大影响范围。平台检查与 Agent 执行的环境也可能不一致。
- Slice 与依赖主要由 Agent 编写独立 JSON；用户无法通过熟悉的 Issue 系统审查、跟踪和复用，外部任务状态与真实验收结果可能混淆。

## Solution

通过 Grill 和功能原型形成定稿 Spec；Agent 从 Spec 生成或导入 Issues，登记纵向 Slice 与阻塞关系。用户在飞书选择 Spec 或路线，查看精简关系图、接受或调整建议角色和实施模式，一次确认整条路线。平台冻结获批版本，只派发前置条件满足的子任务。

每个子任务具有真实可回复成员、持久上下文和持续进度。用户能询问、补材料或恢复失败阶段。实施、测试和复核复用同一任务工作区；并行实施使用独立 worktree。Bubblewrap 按任务、阶段和 Harness 限制访问。完成批准条件并确认集成后，平台写账本、同步 Issue、放行后继；不要求逐片重复人工干预。

## User Stories

1. 作为父任务负责人，我希望用飞书讨论和原型确认需求，以便确认的是实际操作体验。
2. 作为负责人，我希望 Spec 与验收条件集中保存，以免重新依赖 PLAN/HANDOVER 接力。
3. 作为负责人，我希望 Agent 自动拆分或导入 Slice Issues，以免逐个手填。
4. 作为负责人，我希望看到串行、并行、汇合和跨仓依赖，以便判断执行顺序。
5. 作为飞书用户，我希望从下拉框选择 Spec 或路线，以免每次输入命令和本地路径。
6. 作为负责人，我希望先采用房间角色的建议分配，再按 Slice 调整实施、架构复核和验收 Harness。
7. 作为负责人，我希望选择精简、仅实施或完整模式，以免每片都被迫配置所有角色。
8. 作为负责人，我希望预先选定自动、Agent 或人工验收，以便只在我选定的节点停下来。
9. 作为子任务用户，我希望看到真实负责人和可回复成员，以便询问当前工作。
10. 作为用户，我希望执行中提问得到答复或排队提示，以免误以为系统失联。
11. 作为用户，我希望问题进入原任务上下文，以免问题被误当作第二次实施请求。
12. 作为用户，我希望缺材料时明确品牌、页面、原图和答案来源，以便一次提供正确材料。
13. 作为用户，我希望补材料后恢复原阶段，以免重做已完成工作。
14. 作为实施者，我希望受限环境能运行已登记工具链和模型认证，以便无需宿主机全权限回退。
15. 作为平台管理员，我希望工具链、其他仓和非任务分支不可写，以便限制任务影响范围。
16. 作为验收者，我希望读取固定提交、原始截图和读回数据，以便独立判断实际结果。
17. 作为验收者，我希望代码只读、报告目录可写，以便验证不会改掉被验收对象。
18. 作为用户，我希望认证、网络、工具和业务验收失败分别说明，以便知道如何恢复。
19. 作为负责人，我希望一条并行支线失败时，独立支线仍可继续。
20. 作为负责人，我希望服务重启与重复回调不会重复启动、合并或关闭 Issue。
21. 作为负责人，我希望外部修改任务目标或依赖后重新确认，以免执行未批准的路线。
22. 作为负责人，我希望手动关闭 Issue 不会伪造验收完成或绕过放行条件。
23. 作为用户，我希望已完成 Slice 的关键进度回到父任务，并仍可在子话题查证据和问结果。
24. 作为管理员，我希望完成后自动保存证据并清理 worktree，异常时保留现场。
25. 作为业务负责人，我希望已完成的 S03/S04 可被导入且不重跑，S05 保留真实材料缺口后继续跨仓任务。

## Implementation Decisions

### 信息归属与审批

- Spec 定义目标、范围、原型和验收条件；Issues 是 Slice 内容与依赖的唯一编写来源。
- 平台账本记录 Task、Session、工作区、提交、检查、审批、失败和同步回执。Session 结束不等于 Slice 完成。
- 路线卡及运行依赖图从 Issues 生成；获批快照是执行依据，不是独立手写的第二套路线。
- 确认时校验引用版本并冻结目标、依赖、仓库基线、角色、执行模式和验收条件。未经批准不启动。
- 目标、依赖、验收条件或实施配置漂移后，暂停受影响的后续派发，展示变更并重新提审；不打断正在进行的写操作后盲目重派。普通评论不造成误暂停。
- 人工确认遵循既有任务归属与权限；旧卡片、未保存角色、重复回调不能批准另一份快照。

### Issues 适配与完成语义

- 以 provider、owner、repo、issue ID 组成规范引用；保留 Gitee 字母数字 ID，拒绝跨仓裸编号歧义。
- GitHub 使用原生子 Issue 与 blocked-by 关系。Gitee 使用明确版本的结构化字段，经程序解析、校验和往返写入；不根据自然语言猜测依赖。实际 API 权限与能力以探测为准。
- 生成 tickets 时保存来源标记；重试或导入已有父 Issue 不重复建单。API 部分失败保留进度，恢复前先对账。
- 执行中的放行依据是账本中本片批准的完成条件，而不是远端 open/closed。仅实施模式明确记录“已交付、未验收”。
- 写入证据与集成结果后，持久记录 Issue 同步意图，再幂等评论和关闭；暂时断网可延迟同步，不能重复实施，也不能伪称远端已同步。
- 外部手动关闭、重开、删除或取消权限分别展示差异，不自动转成已验收或删除原执行证据。

### 可对话任务与执行

- 创建子任务时登记获批的负责人和参与角色，关联房间、会话与执行记录；不能仅创建输出转发目的地。
- 自动执行和用户消息走统一的任务身份与上下文，继续复用已有执行入口，不引入另一套私有 Agent 调度。
- 同一任务的写操作串行；执行中问题排队或由明确负责人以只读方式回答。不得把一般提问直接当成重跑实施。
- 缺材料、执行失败、等待人工验收、仍在运行分别显示状态。补充信息进入原任务并恢复合适阶段，重启后仍可接续。
- 结束后的问题读取已保存证据；若需要再次修改代码，显式建立后续任务或批准恢复，不隐式复用已清理目录。

### 工作区、Git 与沙箱

- 不引入 Sandcastle 或第二套 worktree 管理。保留平台的工作区、仓库锁、集成分支和追加式 Git 历史。
- 并行实施的仓内任务各用独立 worktree。单个仓内任务从实施到检查、架构复核和验收复用原目录。
- 工具链只读挂载；实施代码可写；测试、复核冻结代码并开放必要报告和临时目录。依赖安装、构建缓存与临时 HOME 使用任务独立位置。
- 凭据按 Harness 最小授权；订阅令牌刷新需要可写路径时明确列出，避免整段用户 HOME 可写或在证据中泄露凭据。
- Git 历史可读。禁止默认开放主仓整个 Git 元数据可写；提交与集成优先由平台提供限定仓库、任务分支及操作的受控步骤。非法分支、任意参数、钩子或路径逃逸必须被拒绝。
- 认证、代理、模型调用和本地服务单独探测。当前共享网络不是域名白名单，不宣称零风险；不自动降级为 full_access。
- 首个交付闭环固定为 Codex 实施、Kimi Code 验收。其他 Harness 逐个登记实测能力，未验证组合不可作为自动派发成功的前提。
- Agent 与平台集成检查使用一致、声明过的环境和权限，防止宿主机检查成为权限旁路。
- 完成后验证提交及无活动会话，保存必要报告、截图、读回数据，再清理临时 worktree。失败、待补资料、未提交改动或保存失败保留现场。

### 纵向 Slice 顺序

- W1：用户在真实子话题提问、获得回答、补材料并接续原任务。无前置。
- W2：一个小任务在细化权限的本机沙箱中完成实施、受控提交、检查及只读验收。无前置。
- W3：从 Spec 生成或导入 Issues，并在飞书选取、调整角色和模式、确认获批路线。无前置。
- W4：通过 W1、W2、W3 后，按 Issues 的获批关系完成并行、汇合、集成、恢复、同步和自动接力。
- W5：通过 W4 后，导入 mold 与 Reader 真实剩余任务，保留既有结果并完成可追踪的跨仓续跑。
- 技术准备属于各片内部步骤。只有通过当前 Slice 的可见行为验收才完成；不以实现文件数量或成功 spawn 为凭据。

## Testing Decisions

- 主验收入口是飞书任务话题：用户选择路线、确认、提问、查看进度、补材料、恢复和看到后继推进。测试同时核对真实运行账本、Git 提交、Issue 关系与消息回执，避免只有截图或内部函数断言。
- 复用已有消息派发/历史、任务图审批/持久化、实际 Git worktree、检查时限与进程回收的验证方式。扩充行为用例，不另建独立模拟调度器。
- W1 以本轮真实缺陷为回归：有执行输出但无 Agent 成员时必须失败；修复后同一话题提问有可回复对象和派发记录。
- W2 用真实 Bubblewrap 和真实子进程执行正反探针：允许的编辑、提交、报告和认证成功；禁止修改工具链、其他仓、非任务分支或主仓配置。不能仅检查生成的命令字符串。
- W3 同时覆盖 GitHub 原生依赖与 Gitee 结构化依赖的往返；循环、缺失、重复、跨仓歧义、部分 API 失败、角色变化、旧卡片均有可见结果。
- W4 使用两支并行后汇合的小交付：一支失败、认证失效、检查超时、合并冲突、Issue 同步失败、重启与重复事件不会越过 gate 或产生重复任务。
- W5 核对真实材料、真实原图与答案来源；既有 S03/S04 不重跑，S05 未满足第二张不同照片时不伪造通过。Reader 任务只能在获批的 tracker 和干净基线上执行。
- 发布证据包含精确提交、命令/结果、截图或读回数据、适用环境及未覆盖项；缺少真实业务输入与平台故障分开报告。

## Out of Scope

- 引入 Sandcastle、Docker 执行后端或第二套 Git 生命周期。
- 恢复 PLAN/HANDOVER watcher 或通过文档标记启动下一 Session。
- 以关闭 Issue 代替测试、集成或验收。
- 在这一轮同时证明全部 Harness、网络白名单、GPU 直通与所有部署环境。
- 把平台改造的完成等同于 mold 的第二张照片验收、真实 OCR 准确率或业务功能自动完成。
- 未经路线审批就启动实施，或修改现有业务路线的完成条件。

## Further Notes

- 当前实现已有工作区复用、部分只读挂载、检查超时回收及完成后清理，属于复用基线；不能据此宣称上述用户体验已全部实现。
- 本 Spec 是新目标：将现有工作流中“父 Agent 手写 JSON 定义依赖”的入口收敛为“从 Issues 生成获批快照”。实施时迁移调用者并退役重复入口，不继续长期维护两套依赖编写方式。
- Spec 在 Gitee 父 Issue 发布全文，本地包是版本化镜像；Slice 的实时关系和状态以 tracker 与获批运行账本的明确分工为准。不得手改本地索引制造第二份进度。
- HTML 是讨论与操作演示，不是已实现功能。已发送附件可直接在飞书下载，不发送用户无法打开的本地原文链接。
- 本轮只完成 Spec → tickets；五片的实施者、复核者、验收者和执行批准另由飞书确认。不能把 ready-for-agent 标签当作启动授权。
