状态：实施中。2026-10-17，接力评审后经用户批准，改按 D1 → D2 → D3 顺序，由 Codex 每个 Session 完成一个可验证单元。旧 C1–C3 为初稿编号，以下以 D1–D3 为准。本文补充本目录 Spec，不触发派发、不改变既有审批或业务节点状态。

## 目标

跨仓前置完成后，平台同时准备调度条件与固定交付输入。后继任务不猜测宿主目录、分支 HEAD 或服务版本。Issues 仍是依赖来源，执行输入清单由平台从获批路线和账本生成，不新增人工维护的依赖文件。

S06 在 mold 仓实施，消费 Reader R02A/R02B 的固定交付。它不应切到 Reader 仓，也不应直接读取 Reader 当前主检出或不明版本的常驻服务。

## 评审采纳与修正

- 采纳前置依赖闭包、固定提交源码、合同与报告输入、各仓项目环境只读复用、四阶段一致挂载、明确实施阻塞结论。
- 提交祖先关系只证明包含所需提交，不证明没有夹带未验收支线。必须结合集成账本核对候选来源；信息不足则阻塞，不能宣称祖先检查保证无夹带。
- 要求存在一个包含所需提交集合的已完成候选，不要求所有提交两两构成全序。无法从已完成候选中选出唯一提交时，不自行创建未经过验收的新合并版本。
- 前置源码缓存可以跨任务、跨运行共享，不能因为一张图结束就删除仍被其他任务使用的缓存。清理依据引用和活跃使用情况，不只依据单个 Slice 或 Run 结束。
- 已开始的消费尝试冻结输入版本。前置回修不能让正在执行的下游静默换版本；新尝试重新解析并记录与旧输入的差异。
- S06 的旧 worktree 实际已删除，不能按评审中的“保留旧工作区”操作。需从已有交付提交恢复后续尝试，保留历史结果。
- 当前自然语言恢复主要重跑独立验收，且仅实施模式会直接结束；仅把 S06 改成 attention 再走旧入口，不会补做未完成的实施。必须先具备按阻塞阶段恢复的能力。
- 隔离联调不能只靠 Prompt 约定。平台必须验证进程、版本、临时数据、健康检查与退出回收，才能声明运行环境就绪。

## 统一执行输入

平台提供一个输入准备入口，由实施、平台检查、独立验收和话题问答共同使用。清单与原批准图、节点、执行尝试关联，并追加到执行账本；环境变量或 Prompt 仅是同一清单的投影。

清单至少包含：

- 主执行仓库、可写工作区、本次基线、获批模式与输入摘要。
- 每个前置仓库的来源节点/执行记录、交付提交、质量状态、只读源码位置。
- 合同文件位置、原工作区归档和验收报告归档。
- 每仓项目环境目录和解释器绝对路径，以及主进程默认环境归属。
- 若阶段需要联调，记录批准的启动入口、固定版本、运行目录和运行实例回执。

输入准备失败需区分提交/来源缺失、固定源码无法准备、环境无效、服务无法启动及业务材料缺失。平台故障不能显示成“请用户再发图”。

### 提交选择

1. 放行与来源校验查看本次获批依赖闭包；输入物化仅提供声明要消费的成果，默认消费直接跨仓前置所属仓库的所需固定版本，可声明仅顺序等待或显式前置标识。同仓继承基线，不额外物化源码副本。声明不能是模型提供的任意目录。
2. 按批准完成条件检查前置状态。需要达到批准的完成门禁；若路线明确允许仅实施交付，清单必须保留其未验收质量标签，不得提升成 passed。
3. 同仓提交去重后，利用 Git 祖先关系寻找集合中包含全部所需提交的候选。
4. 同仓共用集成分支时，前一片未过批准完成门禁，后一片等待，不继承未通过的代码。该门禁须覆盖已有候选来源，不能仅检查显式祖先；跨仓并行不受影响。对候选核对集成来源，拒绝来自范围外且尚未满足完成条件的任务变更；无法证明来源时停止输入准备，不直接取 integrationRef 当前 HEAD。
5. 将选择、来源证据及摘要写入本次消费尝试。重复准备得到同一结果，不重复派发。

### 源码、环境与清理

前置源码使用按仓库和提交寻址的宿主受管只读缓存。优先物化固定 Git 树，不因角色变化新增可写 worktree。物化时校验路径、链接、内容与完整性，明确处理 submodule/LFS，缺少内容时报准备失败，不把指针文件当真实交付。固定交付须有保留期内可追溯的 Git 引用，不依赖临时 worktree 存活。现有 cleanupIntegratedJobWorktree 会删除 job 分支；已集成提交需核对由保留的集成分支保护，未集成保存点保留原 job 分支。若保留策略不能保证引用，再增加必要锚点，不能假定分支永不删除。

缓存的创建、并发使用和释放由平台管理；无活跃引用且满足保留规则时才能清理，恢复时可按原提交重建。报告依照既有归档策略保存。Git 交付、报告归档、源码缓存、临时服务和项目环境有不同生命周期，不能在一次笼统目录删除中处理。

所有相关仓库的已有项目环境和依赖目录均只读挂载。默认 PATH/VIRTUAL_ENV 只来自主执行仓库；主仓无环境时，不自动借用某个前置仓环境。验收在临时目录运行时，主仓身份由执行清单明确提供，不靠目录扫描猜测。访问前置仓使用清单中的绝对解释器和固定源码位置，不拼接多仓 PYTHONPATH。项目环境不会随任务清理删除，也不会自动创建、安装或升级。

### 联调服务

按阶段使用批准的真实启动入口，从固定源码和对应项目环境启动测试实例。业务数据与输出使用隔离运行目录，端口使用临时回环地址。服务未实际支持隔离数据配置时，先补齐能力，不假设存在 `--data-dir` 等参数。

平台记录固定提交、输入摘要、实际启动命令、PID/进程归属、端口、健康结果及日志；验证服务来自本次启动，而非恰好响应同端口的旧进程。阶段成功、失败、超时或取消后均回收进程与临时状态。网络沿用本机沙箱能力，不声称提供容器级网络隔离。

合同和验证入口须明确哪些内容可用稳定夹具检查、哪些必须使用用户新实图；不能用模拟 OCR 或旧照片代替 S06 所需的真实新页验收。

## 实施结果与恢复

实施者返回结构化结果，至少区分 delivered 与 blocked，并给出阻塞类别、实际交付和证据。普通 completed 只表示 Harness 进程结束。缺少有效交付结论时不自动提升节点，不用自然语言关键词猜测状态。

- delivered：由平台按批准模式检查、集成、架构复核或验收；仅实施结果明确未验收，但仍必须确有交付。
- blocked：保留代码和已有证据，在账本记录阻塞类别及发生阶段。缺业务材料显示具体材料，平台输入或环境错误显示平台待处理事项。
- 保存点：blocked 只在任务私有分支保存进度，追加 implementation_blocked 事件，绝不调用 completeExecution 或合入共享集成分支。保存 checkpointCommit、workspaceBase、taskRunId；不改写原 dispatchMetadata。
- 恢复：人补材料并明确继续后，平台按显式 recoveryKind 与记录的阻塞阶段恢复实施或验收。integrated 不是实施已完成的证明，历史重分类事件必须明确 implementation。消息去重、权限、输入版本和活跃尝试检查统一执行，不新建重复业务任务。

修复记录应保留先前 TaskRun、提交和证据，追加后续尝试；旧状态不覆盖为“从未发生”。恢复使用新 claim/TaskRun；干净工作区按保存点复用，已删除目录从受保护提交重建，脏目录或分叉时保留并报错。恢复准备不自动合并最新 integrationRef，集成仍在实际交付后执行。只保留现有协调器、事件账本和恢复入口，不新增 worker、队列或状态表。
