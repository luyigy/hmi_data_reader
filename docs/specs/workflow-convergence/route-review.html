01 / 收敛方向

每种信息只保留一个编写来源

Grill + 功能原型 → 定稿 Spec需求、交付范围、验收标准放在 Spec 包中
↓ 拆成纵向 Slice
Issues：任务 + 前置依赖GitHub 原生依赖；Gitee 使用严格校验的结构化字段
↓ 自动生成路线卡
飞书：确认分工、执行模式和整条路线默认建议角色，可调整；确认后冻结获批版本
↓ 按批准版本执行
平台：运行、集成、验收、重试与证据通过本片批准的完成条件 → 回写 Issue → 放行后继
Issues 是任务与依赖的编写来源；运行账本保存执行事实。平台保留获批快照，不另写第二套依赖。Issue 被手动关闭不能直接放行后继；关闭也不等于已部署。
采纳 Antigravity 的哪些意见？
  • 保留已有 worktree 生命周期与集成机制，不再叠加 Sandcastle。
  • 工具链只读，任务目录按阶段授权；认证刷新、缓存和本地服务单独处理。
  • 提审前读取 Issues，启动时冻结版本；目标、依赖或验收标准漂移后暂停受影响的后续派发，重新提审。
  • 跨仓引用包含 provider、owner、repo 和 issue ID，Gitee 的字母数字编号不能当整数处理。

需要修正的表述：只读挂载不是“宿主机零风险”；现有 worktree 机制仍要实测。不能用宿主机全权限回退掩盖沙箱失败。

03 / 沙箱改什么

把可用性和权限一起验证

可以读什么

  • 登记的 Node / Python / Conda / CLI 工具链只读挂载。
  • 实施、测试、复核使用同一任务 worktree。
  • 兄弟仓、Git 历史和已保存证据按任务需要只读挂载。

可以写什么

  • 实施阶段：任务代码目录。
  • 测试、复核：明确的报告、构建产物及临时目录；代码冻结。
  • 每任务独立缓存和临时 HOME。认证刷新只开放该 Harness 必要路径。
Git 的坑：worktree 的 .git 是指向仓库元数据的文件。不能把主仓整个 .git 默认设为可写。方案优先由平台提供限定任务分支的受控提交、集成步骤；Agent 保留读历史和编辑代码的能力。这一边界要先验证，再写进 Spec。
认证、代理与本地服务

沿用现有本机订阅登录，不要求容器内重新登录。逐个验证读取凭据、令牌刷新、代理、模型请求和断线恢复。错误明确区分认证、网络、权限、工具缺失。

本地代理、OCR/GPU 服务按任务需要授权。当前共享网络并不提供目标域名隔离，也无法阻止被授权服务产生写入；文档不宣称完整网络白名单或零风险。

先验证 Codex、Kimi Code，再测房间中实际使用的其他 Harness。未验证的组合显式标记不可用；启动失败不自动降级到 full_access。

启动前自检 工具可执行？ 模型认证成功？ Git 历史可读？ 允许目录可写？ 禁止目录确实写不进去？ 当前阶段能生成报告？ ↓ 全部满足才启动 失败 → 在飞书说明原因，不创建“已经开始”的假象

并行实施各用独立 worktree；每片内部的实施、测试和复核复用该片工作区。

W1 · 在任务话题中问得通、接得上

前置：无

自动注册负责人和批准角色，关联会话、历史与消息路由。能询问进展、列出缺失材料、补材料后继续；忙碌时有排队反馈。

验收：S05 风格的话题中发问得到回复；重启后不重复实施；完成后仍能查证据。

W2 · 在受限沙箱内完成一次交付

前置：无

权限由任务、阶段、Harness 三项生成。贯通工具、模型认证、编辑、受控提交、测试与只读复核。集成检查也使用声明的环境和权限，避免宿主机检查成为旁路。

验收：Codex 实施、Kimi 验收的真实小任务可走完；写宿主机工具、其他仓和非任务分支的探针全部被拒绝。

W3 · 从 Spec 和 Issues 发起路线审批

前置：无

从定稿 Spec 生成或导入 tickets；GitHub/Gitee 统一引用、校验依赖。飞书下拉选择 Spec / 路线，生成精简卡片，可调整建议角色和执行模式。批准时冻结内容与依赖。

验收：两种 tracker 均能读出串行、并行及跨仓关系；缺少引用、循环依赖、版本漂移均被拦截。

W4 · 验收后自动集成、回写并接力

前置：W1 + W2 + W3

复用现有调度器和集成分支。按精简、仅实施、完整模式推进；仅在配置了人工验收时停人。失败保留现场、原地恢复。回写 Issues 使用持久回执，网络失败不重复派发。

验收：两支并行后汇合；一支失败不挡独立支线；手动关闭 Issue 不越过验收；重启、回写重试和恢复均不重复启动。

W5 · 导入 mold + Reader 剩余任务

前置：W4

登记 Reader 的 Issue 归属和干净基线，映射已完成 S03/S04 的提交与证据；保留 S05 待补材料状态。继续 R02A、R02B、S06，沿用批准的真实依赖。

验收：父话题有总进度，子话题能问答；跨仓接口和集成版本可追踪；完成后保存证据并自动清理 worktree。

工作量：这是跨消息路由、权限和 tracker 的中等改造。W2 的认证刷新、受控 Git 与各 Harness 兼容性是主要不确定项。先用小任务验证 W1/W2 并核实两种 tracker 的接口，再给有依据的工期；本稿不把尚未验证的方案说成“改几行即可”。
05 / 怎么知道下一步做对了

先跑一个小闭环，再恢复业务路线

先验证平台行为

  • 你在子话题提问，指定的 Agent 确实回答。
  • 一个小改动在受限环境完成提交与验收。
  • 验收通过后，下一个 Issue 对应任务自动启动。
  • 认证失败、缺资料、测试失败有不同提示和恢复路径。

再继续 S05

已通过的 31 项 API 和 1 项浏览器测试保留。S05 尚缺第二张不同的真实照片，不能用同图的第二条记录替代。

先让负责人在话题中明确所需品牌、页面、原图与答案来源，再由你补图。平台修复不会自动宣告业务验收通过。
