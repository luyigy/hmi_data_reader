# PLAN · 工作流诊断与飞书操作导航

## 目标

让飞书用户能理解 workflow watcher 的当前状态、历史改写等阻塞原因及安全恢复边界；让
`/ap help` 按稳定分组分页展示；让 workflow 审批/执行卡片明确显示 PLAN、Slice 与阶段。

## 边界

- 诊断命令只读，不自动移动 cursor、不清 pending、不发送或启动 Agent。
- 仅有明确管理员操作时才允许既有 cursor/run 等写操作；不新增“猜测性恢复”功能。
- 复用现有 `/ap` parser、job 状态、workflow 文档 frontmatter、审批卡和消息发送能力，不新增
  数据库表、第二套帮助注册表或独立调度器。
- 帮助页使用 `/ap help [页码]` 与 `--page=<页码>`；不引入裸 `/ap1`、`/ap3` 形式。

## S01：工作流诊断命令

新增 `/ap job diagnose workflow-watcher`。它展示 job 状态、cursor、当前 HEAD、祖先关系、
pending、最近失败、待处理 workflow 文档和安全提示。历史改写时必须说明 `--latest` 会跳过
待处理提交，并要求人工确认恢复基准；不得自动建议或写入具体替代 commit。补充解析和输出测试。

## S02：分组分页帮助

将 `/ap help` 改为紧凑的分组目录，支持 `/ap help 2` 和 `/ap help --page=2`。至少覆盖房间与
Agent、运行控制、workflow/Jobs、权限/管理四页；每页显示页码、上一页和下一页命令。帮助内容
从现有命令能力集中维护，不重复维护 parser 的权限或动作真相。补充页码边界和主要命令可发现性测试。

## S03：workflow 阶段可见卡片

复用工作流文档的 `plan`、`slice`、`plan_progress` 与路径，在 PLAN 审批卡以及启动下一 Session
的 workflow 提示/卡片中显示：所属 PLAN、当前或将执行的 Slice、文档状态和下一动作。无法从
合同文档确定的信息要明确显示“未声明”，不得从正文猜测。覆盖 PLAN、HANDOVER 和终态文档显示；
不改变审批、cursor、Session 或消息路由语义。

## S04：验证与交接

运行命令解析、workflow watcher/validator、相关卡片测试、TypeScript、相关 ESLint、
`git diff --check` 和 GitNexus `detect_changes`。如生产构建仍受既有客户端 `child_process`
依赖链阻塞，只记录证据，不在本计划内修复。完成后创建终态 HANDOVER，
`plan_progress: complete`、`next_action: await_acceptance`，列出需真人在飞书中验证的诊断输出、
帮助分页和卡片阶段展示。
