# PLAN 写作与 Slice 划分规范

## 1. 为什么需要这份规范

PLAN 不是给执行者看的任务清单，而是让不了解代码细节的人也能判断以下问题的路线图：

1. 总体要得到什么结果；
2. 为什么要按这个顺序推进；
3. 每一步具体怎么实现、解决什么问题；
4. 每一步是否小到一个 session 可以完成；
5. 做到哪一步时，用户已经能看到或验证什么。

以后新建或大幅修订 PLAN，必须遵守本文；文档状态与自动接力字段继续遵守
`docs/workflow/workflow-contract.yaml`。

## 2. PLAN 必须按“故事线”展开

每份 PLAN 必须依次回答六层问题，不能直接从函数名或 S01 开始：

1. **总体目标**：最终用户要完成什么事情，用一句非技术语言说明。
2. **当前障碍**：现在为什么做不到，列出已经确认的缺口，不把猜测写成事实。
3. **总体路线图**：从当前状态到最终目标要经过哪些阶段，标明本 PLAN 负责哪一段、后续由谁接力。
4. **本 PLAN 结果**：本 PLAN 全部完成后，用户、调用方或运维人员实际能看到什么。
5. **Slice 路线**：每个 Slice 如何承接上一步，并为下一步提供什么。
6. **验收与退出**：怎样证明完成，失败时停在哪里，明确哪些事情没有做。

推荐使用一张最小路线表：

| 阶段 | 解决的问题 | 交付结果 | 是否属于本 PLAN |
| --- | --- | --- | --- |
| A | 为什么先做 A | A 完成后可验证的结果 | 是/否 |

## 3. 每个 Slice 的强制内容

每个 Slice 必须完整写出以下七项，缺一项就不能进入 `ready`：

| 项目 | 必须回答的问题 |
| --- | --- |
| 目的 | 为什么需要这一步；它消除哪个障碍或风险 |
| 完成后结果 | 用户或下一层调用方能看到、拿到或验证什么 |
| 实现方法 | 修改哪条现有链路，复用什么，数据如何从输入走到输出 |
| 修改边界 | 预计涉及哪些生产文件、测试文件；明确不碰什么 |
| 验收 | 哪些自动测试、合同断言或人工检查能证明完成 |
| 前置与停止条件 | 依赖什么；什么情况必须停止而不能扩大范围 |
| 交付物 | 一个提交、一份 HANDOVER，以及必要的测试/报告 |

如果某个 Slice 只有内部结果、用户暂时看不到，必须额外用一句话解释：它为何不能与下一步安全地
放在同一个 session，以及它独立验收后降低了什么风险。

## 4. 一个 session 的工作量规则

默认一个 Slice 必须能由一个 Agent 在一个 session 内完成理解、修改、验证、HANDOVER 和提交。
划分时采用以下硬规则：

- 一个 Slice 只有一个主要结果和一个主要失败原因；
- 默认只跨一个工程边界，例如“纯函数/算法”“HTTP 接口”“Web UI”“数据库迁移”四者选一；
- 默认只改一组紧邻的生产代码及其直接测试，通常不超过 2 个生产文件和 2 个测试文件；
- 必须能在不依赖下一个 Slice 的情况下运行本 Slice 验收；
- 每个 Slice 结束时只提交本 Slice，创建 HANDOVER，然后停止；
- 算法 + HTTP + UI + 数据库不得塞进一个 Slice；跨仓工作默认分仓立 PLAN。

文件数量是预警线，不是机械目标。超过预警线时，PLAN 必须解释为什么仍可在一个 session 收口；
无法解释就继续拆分。不能为了满足文件数，把同一原子修改拆成无法运行或无法验证的半成品。

## 5. Slice 怎么切：按可验证结果，不按代码目录

正确的切法是“每一步产生一个可验证能力”：

```text
总体目标
  -> 能力 A：先建立可靠的核心结果
  -> 能力 B：再把核心结果接入真实调用入口
  -> 能力 C：再给用户操作和确认
  -> 能力 D：最后保存或进入生产流程
```

不允许只写“改 util”“改 service”“补测试”作为 Slice 目的；这些是实现动作，不是交付目的。
也不允许为了显得完整，把所有层一次做完。测试属于其对应能力，不单独堆到最后一个 Slice。

## 6. 状态、审批与提交规则

- 起草时使用 `draft / await_plan_approval`，只展示路线，不携带可执行 `WORKFLOW_PROMPT`；
- 用户批准后，才改为 `ready / start_first_slice`，并只派发第一个 Slice；
- 每完成一个 Slice：运行项目门禁，创建 HANDOVER，提交该 Slice，然后停止；
- PLAN 全部完成后改为 `completed / none`；
- PLAN 的创建或修订本身也必须单独提交，不能只留在工作树，否则不可作为飞书同步和后续执行依据；
- 提交前必须确认暂存区只含本次 PLAN/规范改动，不得夹带既有业务代码。

## 7. PLAN 进入 ready 前的检查表

- [ ] 开头用非技术语言写清最终结果；
- [ ] 有从总体目标到本 PLAN、再到各 Slice 的路线图；
- [ ] 每个 Slice 都写了目的、结果、实现、边界、验收、停止条件和交付物；
- [ ] 每个 Slice 默认可在一个 session 内完成；例外已有明确理由；
- [ ] 相邻 Slice 的依赖关系能用“上一步产出 -> 下一步输入”读通；
- [ ] 示例覆盖真实业务范围，没有用单一样例冒充通用能力；
- [ ] scope out、风险和 breaking change 已显式说明；
- [ ] draft 阶段没有执行 Prompt；
- [ ] PLAN 修订已经提交。
