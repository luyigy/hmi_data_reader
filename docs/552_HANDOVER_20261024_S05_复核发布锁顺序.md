## 确定性复现与根因

新 `task-graph-review-lock-order` 在生产源码修复前执行。每个用例：

1. 在随机 schema 建立 verifying 节点、integrated 固定候选、running review binding 和已有 durable claim；
   真实 nonce 子进程退出后释放 Writer，使用原退出证明逻辑。
2. 在独立单连接 PrismaClient 上运行真实 `reserveGraphReviewClaim`。
   测试只在其成功取得 graph-control 后设置会合点，暂缓继续；没有替换生产 SQL 或账本结果。
3. 在原 Prisma 客户端上运行真实 `submitNodeVerification` 或 `publishReviewPreparationFailure`；
   第三条观察连接读取 `pg_stat_activity` / `pg_blocking_pids`，确认发布正在等待预留。
4. 释放会合点，让预留继续请求 node 行锁，采样实际双方等待关系并收集两个调用的结果。

修复前四组均出现相互阻塞：publication 等待 advisory，reservation 等待 transactionid/node FOR UPDATE。
四组发布均 rejected，预期 fulfilled；测试汇总实际失败数 4、预期 0，沙箱退出 1。
客户端三组明确显示 `40P01 deadlock detected`，另一组 Prisma 显示 N/A；**数据库服务日志四组均明确记录 deadlock detected**。
红色证据不是启动错误或无关超时。

核对的解释为：锁顺序倒置、连接池等待、claim/身份竞争。双向 PostgreSQL blocker 及服务端 deadlock 日志
直接支持锁顺序倒置；连接池等待不会产生这种 SQL blocker 环，归属竞争也不能解释数据库死锁。
此处与 551 的单连接 P2028 是不同缺陷，不将新死锁追认为旧 P2028 根因。

最小修复：

- `submitNodeVerification` 在事务开始先调用已有 `graphRunCanStartTx`，再取得 node 锁。
- `publishReviewPreparationFailure` 在事务内读取 node 所属 runId，取得相同 graph-control，再锁 node。
- `applyReviewFailureTx` 的两个生产调用入口均已持有 graph-control；注释明确调用前提。

复用既有锁函数，不新增锁管理器。这里取得锁不改变暂停策略：后续 outcome 原有 active 校验仍有效，
普通验证结果沿用原发布语义。候选、授权、claim/revision 和退出证明仍在原位置核验。
修复后同一四组用例全部 fulfilled，账本状态与事件断言通过；单连接发布回归也通过。
测试会合点的等待补充了事务提前结束时的失败出口，随后复跑最终测试文件。
