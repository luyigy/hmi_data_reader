## 实现及不变量

- 本机可信操作入口 `scripts/task-graph-register-input-candidate.ts --receipt <JSON>` 接收明确的补充候选。
  receipt 绑定 execution、claim、revision、旧 inputHash、Mold 候选、Reader 新旧提交、授权出处和文件证据摘要。
  登记前校验旧清单、提交继承、可重建源码、文件摘要、真实写作者退出；事务内重新核对身份和状态。
  requestId 重放幂等，内容不同时拒绝，待应用候选不能覆盖。
- 原 claim 的 task_inputs_prepared 原样重放。下一 claim 使用新提交并记录 replacement 来源；
  新候选标为 candidate_unverified，不继承旧版 passed、已通过执行编号或旧报告目录。
  原 R6 已通过节点、批准快照、旧源码副本和其他消费者的输入均不改写。
- 实施、架构复核和测试验收读取同一清单。补充候选变化进入验收身份，即便 Mold 提交未变也不复用旧验收缓存。
  已应用候选在之后的主仓修改和阶段重试中保持；首次应用前主仓候选漂移会拒绝。
- 已批准的 Reader 写目录映射到新 SHA 对应的私有 checkout；原工作区保留。
  仅在有候选登记时，提示明确允许主仓消费并提交验收。额外修改仍须由平台重新固化，不能自行提交或汇合。
- 自动通过、人工确认、仅实施交付三个完成入口都检查补充候选是否已进入原批准目标分支。
  未汇合时拒绝完成和释放后继；业务失败结论仍可发布。该检查只检查 Git 归属，不代替 Agent 的业务判断。
  若独立验收先通过而 Reader 尚未汇合，保留其 TaskRun/报告，完成汇合后重试发布；不伪造已完成账本。

## 回归中发现的回修等待

完整 Agent-owned 回归在 repair 场景出现 P2028，随后持续等待 phase writer 退出；隔离重跑也复现。
上轮 c7fc0f0 的 repair 单场景曾通过，因此不把它描述为上轮必现失败。
源码发现 pendingReviewRepairTx 在数据库事务内调用使用全局 Prisma 的写作者观察。
这会争用单连接，并与原验证流程释放 phase worker 的事务互相等待；新路径的时序暴露了该窗口。

修复把 pendingReviewRepairTx 限制为账本读取。在 scheduleGraphRepair 的事务外观察实施、复核、phase writer，
在原事务锁内比较完整 writer snapshot 和待回修绑定；活写作者、未知身份、版本变化仍拒绝派发。
没有增加重试次数或放松 writer 退出判断。

新增真实 Git/真实 writer 的单连接回归；原 pending-review 测试也改用临时真实 Git 仓与真实提交，
避免旧 `/tmp/KEY/repo` 和虚构 SHA 在新增的候选指纹检查前失败，掩盖测试原本要检查的退出与幂等行为。
