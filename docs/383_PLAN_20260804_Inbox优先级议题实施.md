# PLAN · Inbox 优先级议题实施（5 波次）

基于 ROADMAP（378）的优先级排期与 pi-agent 的波次分析，将 inbox 中 9 个议题按
**代码依赖与主题内聚**分入 5 个 Slice。Slice 间可部分并行（S02 与 S03 独立），
但 Slice 内部严格按子步骤顺序执行。

## 议题覆盖总览

| Slice | 议题 | 主题 |
|---|---|---|
| S01 | 380(P0) | 错误分类——消除"PLAN 未提交"误导 |
| S02 | 348 → 376 → 380(P1) | 失败可观测性与恢复簇 |
| S03 | 382 → 375 | Agent 职责分工与意图路由 |
| S04 | 377 | 执行信息折叠显示 |
| S05 | 357 → 351 → 350 | 架构演进（鉴权→并发→分布式） |

## S01：380 P0——Workflow 编排失败错误分类

**范围**：修改 `src/lib/live-room-workflows.ts` 中 `/plan`、`/run` 的单一 `catch`，
区分四类失败并给出对应文案与处置引导。

**子步骤**：
1. 在 `live-room-workflows.ts` 中为成员执行失败 / PLAN_PATH 非法 / Git 提交失败 /
   validator 失败定义独立错误类型或错误码。
2. 替换末尾 `catch` 的统一"PLAN 未提交"为按类型分发的提示文案，
   包含失败阶段、成员、退出状态、是否产生文件或提交。
3. 将 tcmalloc 等无害 stderr 归入"诊断详情"而非主错误标题。
4. 提供"重新执行原始请求"的恢复兜底（当前暂不做断点恢复）。

**验收**：
- 任意阶段失败时，提示明确区分失败类型；不再出现笼统"PLAN 未提交"。
- 非关键 stderr 不出现在主错误标题。
- 现有 `/plan`、`/run` 的正常路径不受影响。

## S02：失败可观测性与恢复簇（348 + 376 + 380 P1）

**范围**：三个议题代码路径均在 `live-room-workflows.ts` / watcher 附近，
按依赖顺序实施：先修 Watchdog 判定（348），再补 Watcher/Handoff 状态反馈（376），
最后在准确失败分类基础上实现轻量 Workflow Run checkpoint（380 P1）。

**子步骤**：
1. **348**：修复 `FeishuWatchdog` 将 >12 分钟活跃 Local 进程误判为失败并回退 `idle` 的 bug。
   在 `src/lib/feishu-watchdog.ts`（或对应 watchdog 模块）中增加活跃进程的心跳/输出检测，
   区分"静默超时"与"活跃但耗时长"。
2. **376**：在 PLAN 提交链（Handoff 生成→PLAN 定稿→提交→validator）各阶段增加状态反馈，
   使 Watcher 阻断原因可诊断；卡片自动告警。
   涉及 `src/lib/live-room-workflows.ts`、`src/lib/feishu-approval-card.ts` 等。
3. **380 P1**：在 S01 准确错误分类基础上，为 `/plan`、`/run` 保存轻量 Workflow Run
   checkpoint（独立于现有 `WorkflowDispatch`），支持"从失败阶段继续"。
   包含原子 `paused → running` 状态更新和幂等键。

**验收**：
- Watchdog 不再误杀 >12 分钟活跃长任务。
- PLAN 提交链各阶段失败原因可诊断，卡片自动推送。
- 修复执行环境后，可一键从失败阶段继续；前序阶段不重跑。
- 相同错误指纹不循环重试；瞬态错误最多自动重试一次。

## S03：Agent 职责分工与意图路由（382 + 375）

**范围**：新增正交 `specialty` 字段与消息意图路由（382），再在其上做卡片 UX（375）。
两者必须配对实施：382 提供职责维度，375 提供卡片入口。

**子步骤**：
1. **382**：在 `LiveRoomMember` schema 中新增 `specialty` 字段
   （枚举 `documentation / diagnostics / implementation / general`），
   独立于 `role`。实现消息意图识别（检测"记录/写进 inbox/出文档/写 FIX"等意图）
   并路由给对应 `specialty` 专员。不改动 `ROLE_PRIORITY`/`ROLE_ORDER`。
   涉及 `src/lib/live-room-scheduling.ts`、schema 定义、消息路由逻辑。
2. **375**：在 AP 命令卡片中增加角色工作流入口（`/run feature`、`/run debug` 按钮），
   并基于 382 的 `specialty` 将"文档与记录"作为一等职责入口展示。
   涉及 AP 命令卡片渲染逻辑。

**验收**：
- 可为房间成员指定 `specialty`，独立于 `role`。
- 文档/记录类意图自动路由给 `documentation` 专员，即使未被 @。
- AP 命令卡片展示"文档与记录"一等入口。
- 现有 `/run feature|debug`、`/plan` 的角色排序不受影响。

## S04：执行信息折叠显示（377）

**范围**：前端改动为主，在飞书（`collapsible_panel` 原位卡片更新）和 Web 端
（手风琴组件）引入中间步骤折叠，保持对话主线清爽并保留全量追溯能力。
为 S02 的"查看诊断"提供折叠容器。

**子步骤**：
1. 飞书端：在 Agent 执行过程中将中间步骤封装为 `collapsible_panel`，
   原位更新折叠卡片；展开后可见完整执行日志。
2. Web 端：实现手风琴组件，与飞书端行为一致。
3. 与 S02 的"查看诊断"按钮联动，点击后展开对应折叠容器。

**验收**：
- 飞书与 Web 端均支持中间步骤折叠/展开。
- 折叠状态不影响对话主线的可读性。
- "查看诊断"可联动打开对应折叠面板。

## S05：架构演进（357 → 351 → 350）

**范围**：安全基石 → 并发隔离 → 分布式。三者有明确前置链，按顺序实施。

**子步骤**：
1. **357**：网页登录认证与 RBAC。实现人类用户的鉴权与权限隔离。
   与 382 正交（管人，不管 Agent 分工）。
2. **351**：并行工作流调度与 Git Worktree 任务隔离。
   多 Agent 并发执行，依赖 357 的权限模型。
3. **350**：远程 Agent 守护进程与 WebSocket 接入网络。
   跨机器分布式 Agent 协作，依赖前两者。

**验收**：
- 网页端支持登录认证与 RBAC 权限隔离。
- 多个 Agent 可在独立 Git Worktree 中并行执行工作流。
- 远程机器上的 Agent 可通过 WebSocket 接入平台协作。

  349 已废弃（`superseded`），不做。
