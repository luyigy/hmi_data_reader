# 221_PLAN_20260722_Feishu工作区授权

## 目标

为非管理员 Feishu 私聊用户建立真正可执行的工作区授权闭环：管理员批准新用户时必须同时指定一个授权根目录；用户后续只能把当前工作目录切换到该根目录内部；Platform Local 进程在操作系统层无法访问授权范围之外的服务器路径。

本计划独立于 216 功能内聚重构，不以拆分大文件为前置条件。

## 核心决策

### 1. 区分两个路径概念

- `workspaceRoot`：用户级安全边界，只能由 Feishu 管理员设置或修改。
- `workingDirectory`：房间或任务的当前工作目录，用户可以修改，但必须位于自己的 `workspaceRoot` 内。

`cwd` 不是安全边界。仅校验 `/ap workspace` 不能阻止 Agent 使用绝对路径、`../`、符号链接或 shell 子进程越界，因此路径策略和进程隔离必须同时交付后才能宣称“不能访问外部路径”。

### 2. 首版每个用户只支持一个根目录

不增加多根目录 ACL、路径角色或继承规则。一个根目录已经覆盖当前需求，也能保持审批、命令和隔离参数简单。确有同一用户访问多个不相邻目录的需求后，再增加独立授权表。

### 3. 管理员批准时必须给出根目录

新用户审批卡增加“授权根目录”输入项，批准动作必须携带该值。服务端不信任卡片输入，仍执行统一的路径规范化与授权校验。拒绝不要求路径。

若当前飞书卡片版本或 SDK 无法可靠提交输入值，则使用最小降级流程：卡片展示建议命令，管理员先执行：

```text
/ap user approve <open_id> --workspace-root=/absolute/path
```

不能退化为“先无路径批准、以后再补”，避免出现短暂的无限路径权限窗口。

## 用户行为

### 新用户审批

1. 新用户首次 DM，系统创建 `pending` 准入记录和审批记录。
2. 管理员卡片展示姓名、`open_id`、`chatId` 和授权根目录输入框。
3. 管理员点击批准。
4. 服务端校验并保存 `workspaceRoot`，再创建默认 Safe Local 房间；初始 `workingDirectory` 等于 `workspaceRoot`。
5. 任一步失败则审批恢复为 `pending`，不创建可运行的绑定。

审批必须复用一个共享事务服务，卡片回调和 `/ap user approve` 不得各自实现一套状态转换。

### 后续路径命令

普通用户：

```text
/ap workspace
/ap workspace <root内的绝对路径或相对路径>
```

- 无参数：显示授权根目录和当前工作目录。
- 相对路径：相对于 `workspaceRoot` 解析。
- 绝对路径：只有落在 `workspaceRoot` 内才允许。
- 普通用户不能修改 `workspaceRoot`。

管理员：

```text
/ap user workspace <open_id> <absolute_root>
/ap user approve <open_id> --workspace-root=<absolute_root>
```

- `user workspace` 修改已存在用户的根目录。
- 若现有房间的 `workingDirectory` 不在新根目录内，将其重置为新根目录，并同步来源 Task。
- 缩小或撤销授权时，必须终止该用户仍在运行的 Platform Local 进程；仅影响下一次启动不足以构成权限收回。
- `/ap users` 增加 `workspaceRoot` 展示，便于审计。

## 路径规则

新增一个无状态共享函数作为所有入口的唯一校验边界，至少执行：

1. 只接受绝对的 `workspaceRoot`。
2. 根目录必须存在且为目录。
3. 使用 `realpath` 得到规范路径。
4. 目标工作目录同样使用 `realpath`；不存在的目标先拒绝，首版不代建任意子目录。
5. 用 `path.relative(root, target)` 判断包含关系，不能使用字符串 `startsWith`。
6. 拒绝 `..` 越界、兄弟目录、根目录前缀碰撞和符号链接逃逸。
7. 非管理员 Feishu DM 没有 `workspaceRoot` 时拒绝创建或执行任务，并提示联系管理员补齐。

这些规则覆盖平台路径选择，但不能替代进程隔离。

## 数据模型

给 `FeishuUserAccess` 增加：

```prisma
workspaceRoot String?
```

数据库保存 `realpath` 后的绝对路径。字段先保持可空以兼容管理员和已有数据，但非管理员 `approved` 用户运行前必须非空。

审批中的待确认路径保存在现有 `FeishuAdminApproval.payloadJson`，不新增审批表或第二套状态机。批准事务内再把规范路径写入 `FeishuUserAccess.workspaceRoot`。

## 实施阶段

### Phase 1：策略、审批与命令

预计修改范围：

- `prisma/schema.prisma` 与一条 PostgreSQL 迁移。
- `src/lib/feishu-access-approval.ts`：审批卡输入、统一批准服务、管理员路径命令。
- `src/lib/feishu-long-connection.ts`：从卡片 action 事件读取表单值并交给统一服务。
- `src/lib/feishu.ts`：收紧 `/ap workspace`，展示 root/current。
- `src/lib/feishu-live-room.ts`：创建绑定时写入已验证的初始目录。
- 一个共享路径校验模块，避免卡片、命令、房间创建各自判断。
- 聚焦测试和迁移测试。

Phase 1 完成后，平台不会再接受越界工作目录，但还不能声称 Agent 进程无法读取外部路径。

### Phase 2：Platform Local 操作系统级隔离

在本地 harness 的统一启动边界接入已安装的 `/usr/bin/bwrap`，不要分别给 Codex、Claude、Gemini、Pi 写四套规则：

- 授权根目录映射为唯一可写工作区。
- 必需的系统运行目录只读挂载。
- 其他项目和用户目录不挂载。
- 提供独立 `/tmp`。
- 子进程继承同一 mount namespace。
- 非管理员 Safe Local 默认禁网；网络授权继续走现有权限模型。
- `full_access` 只在现有管理员显式审批后绕过隔离。

如果某个 harness 无法在该隔离配置下启动，先禁止非管理员选择该 harness，不能静默回退到未隔离执行。

### Phase 3：存量用户迁移与上线

1. 部署 nullable 字段和代码，但保持非管理员空 root 拒绝执行。
2. 管理员通过 `/ap users` 找出已批准但缺少 root 的用户。
3. 使用 `/ap user workspace` 逐个补齐路径。
4. 完成 Bubblewrap 越界测试后再开放非管理员 Platform Local。
5. 观察审批失败、路径拒绝和 bwrap 启动失败日志；不自动扩大权限兜底。

## 验收标准

### 审批与状态

- 批准卡片未提供路径时不能批准。
- 非管理员不能提交或修改任何用户的 `workspaceRoot`。
- 重复点击批准只生效一次。
- 卡片批准和命令批准走同一校验与事务逻辑。
- 路径校验或房间创建失败后，用户仍保持不可运行状态。

### 路径校验

- 根目录自身和正常子目录通过。
- `../`、绝对兄弟目录、相同字符串前缀目录和指向外部的符号链接全部拒绝。
- `/ap workspace` 同步 Live Room 与来源 Task。
- 修改根目录后，旧的越界 `workingDirectory` 不再生效。

### 进程隔离

- Agent 可以读写授权根目录。
- Agent 无法读取另一个用户的工作区和其他服务器项目目录。
- `cat` 绝对路径、shell 子进程、`../` 和符号链接均不能越界。
- `/tmp` 不与宿主或其他运行共享。
- 不支持隔离的 harness 对非管理员明确拒绝，不降级运行。
- 管理员批准的 `full_access` 行为保持现状。

## 非目标

- 不做多根目录 ACL。
- 不做 Web 管理后台。
- 不把远程 SSH backend 纳入首轮隔离；远程主机需要独立的服务账号、容器或远端 sandbox 策略。
- 不借此拆分 `feishu.ts` 或实施 216 重构。
- 不把 `writableRoots` metadata 当成已执行的安全边界。

## 推荐执行顺序

先实施 Phase 1 并验证审批/命令闭环，再实施 Phase 2；两者均通过后才对外宣布“Feishu 用户被限制在指定服务器路径内”。Phase 3 作为上线步骤紧随其后，不另建复杂迁移系统。
