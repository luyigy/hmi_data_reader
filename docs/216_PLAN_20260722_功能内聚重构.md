# 216_PLAN_20260722_功能内聚重构

## 目标

把当前职责混杂的超长核心文件按稳定业务边界收聚，降低 Live Room、Feishu、ACPX 和 UI 修改互相误伤的概率。文件长度是结构预警，不是拆分目标。

当前优先对象：

| 文件 | 当前行数 | 建议边界 |
| --- | ---: | --- |
| `src/app/tasks/[id]/chat/page.tsx` | 2456 | 页面容器、消息列表、运行控制、审批交互、数据 hooks |
| `src/components/live-room/LiveRoomWorkspace.tsx` | 2188 | 房间壳、成员管理、消息面板、权限/模型设置、socket hooks |
| `src/lib/feishu.ts` | 2174 | 命令路由、session 命令、权限命令、handover/new-session 文本构建 |
| `src/lib/acpx/runner.ts` | 1910 | prompt/context、participant lifecycle、本地执行、远程执行、interaction handling |
| `src/lib/live-room-delivery.ts` | 1733 | delivery orchestration、业务消息播报、participant/session persistence |
| `src/lib/live-room.ts` | 1675 | repository、message metadata、transcript/context、socket emission |

## 原则

1. 一次只拆一个职责，行为不变；每步可独立提交和回滚。
2. 先复用已有模块，再移动代码；不新增一实现接口、factory 或通用 framework。
3. 保持公开入口稳定，调用方不随内部拆分扩散修改。
4. 不设“必须低于 1000 行”的机械指标；文件持续过长时必须审查是否职责混杂，只有形成明确输入/输出和测试边界时才拆。
5. 每次编辑符号前运行 GitNexus upstream impact；HIGH/CRITICAL 必须先报告。
6. PostgreSQL 迁移期间冻结结构性重构，避免 schema 与模块边界同时变化。

## 执行顺序

### Phase 0：基线收尾

- 先审查并收尾 `live-room-process-registry.ts`、`live-room-delivery.ts` 及相关测试的当前未提交改动，确认 `hasLiveRoomMemberExecution` 的行为基线。
- 确认 PostgreSQL 迁移已稳定，或至少 schema 与切换方案已冻结；未满足时不开始结构重构。
- 记录 Codex、Claude、Antigravity 现有 queued/started/tool/heartbeat/final 和 relay 顺序的聚焦测试基线。

### Phase 1：Live Room 并发与过程消息

#### Batch 1：成员执行链与生命周期

- 不新建 `live-room-member-queue.ts`；复用 `live-room-process-registry.ts` 和现有 scheduling 边界，统一管理同 member 单执行链、queued/started 状态和进程生命周期。
- `live-room-delivery.ts` 只编排调用与业务消息播报，不再形成第三套并发状态。
- 保持现有公开入口与 relay 契约不变。

#### Batch 2：过程消息状态机

- 仅当 started、tool、heartbeat、final 的顺序、节流和 flush 能形成独立纯状态机且有聚焦测试时，才提取 `live-room-progress.ts`；正文 stdout 不作为过程消息。
- 保留 `executeLiveRoomReplyViaAcpx` 为薄 orchestration 入口。
- 不新建 `live-room-retry-policy.ts`；Harness/Session 级 continuation 失效与 fresh session fallback 继续由 `acpx/continuation-retry.ts` 的 `executeAcpxTaskRunWithContinuationFallback` 负责，Live Room 只负责调用和业务播报。

要求：Codex、Claude、Antigravity 的 queued/started/tool/heartbeat/final 顺序与 relay 契约必须有聚焦测试。

### Phase 2：Live Room 数据与上下文

从 `live-room.ts` 提取：

- message repository/persistence。
- metadata parse/resolve。
- transcript/context watermark。
- socket emit/serialization。

`postLiveRoomMessage` 保留为唯一写入入口，防止调用方绕过 Task Room 镜像和 Feishu relay。

### Phase 3：ACPX Runner

从 `acpx/runner.ts` 提取：

- harness prompt/context builder。
- local participant executor。
- interaction request lifecycle。
- run finalization/event persistence。

远程 SSH 执行继续留在现有 remote-harness 模块，不借机重写。

### Phase 4：Feishu 命令域

先判定 `control-plane/FeishuCommandRouter.ts` 的架构定位，再编辑 `feishu.ts`：

- 若它是未来标准路由，将 `feishu.ts` 的现有命令族逐步迁入，不并行新建 Router。
- 若它只是未接入生产的示例/原型，先清理或隔离，再按 room/member、permission、session/handover、workspace 的真实边界拆分。
- 共享解析和回复函数保持少量、显式依赖。

### Phase 5：UI

- `LiveRoomWorkspace.tsx`：先抽无状态展示组件，再抽已有清晰副作用的 hooks。
- task chat page：消息、runs、interaction 三块分别收口；页面保留路由参数和组合。
- 不引入新的状态管理依赖，继续使用 React/现有 socket client。

## 每个拆分批次的模板

1. 用 GitNexus `context` 和 upstream `impact` 锁定入口与调用方。
2. 记录行为基线和现有相关测试。
3. 纯移动/提取一个职责，保持导出签名稳定。
4. 运行聚焦测试、`npx tsc --noEmit`、`git diff --check`。
5. 运行 `detect_changes({scope: "compare", base_ref: "master"})`，确认流程范围未扩大。
6. 一个批次一个提交；每个 Phase 维护一份演进式 HANDOVER，不为微小 Batch 重复建文档。

## 完成标准

- 六个目标文件的职责和依赖方向清晰；长文件已按真实边界拆分，仍明显过长的文件有保留理由和后续拆分触发条件。
- 核心入口仍可从单一文件发现，没有循环依赖。
- Live Room message 写入、Task Room transcript、Feishu relay、ACPX finalization 各有一个明确 owner 模块。
- 没有新增运行时依赖。
- Codex、Claude、Antigravity 各完成一次真实/隔离 smoke。

## 停止条件

- 若提取要求同时改变数据库 schema、外部 API 或消息语义，停止并单独立计划。
- 若新模块只被一个函数调用且没有形成更清楚的职责边界，保留原位。
- 不追求一次完成；Phase 1 完成并稳定后再决定 Phase 2。
