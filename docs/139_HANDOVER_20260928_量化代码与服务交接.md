## 3. 新代码逐文件说明

以下均为本轮实验脚本，不是产品服务业务模块。导出、评估和量化之间主要通过落盘模型及 JSON/PT 文件衔接；API 服务直接由 vLLM 启动，不调用这些量化脚本。

### 3.1 前置：LoRA 合并与 BF16 验收

| 脚本绝对路径 | 参数、作用与输出 |
| --- | --- |
| `/data1/code/hmi_data_reader/output/exports/round2-bf16-20260928/export_check.py` | `export`：先跑 adapter 三图基线，再用 `merge_and_unload(safe_merge=True)` 合并视觉与语言 LoRA，保存完整模型、processor、tokenizer，并补留 MTP；输出 `model/`、`manifest.json`、`export-outputs.json` 和 logits。`reload`：新进程重载落盘 BF16 跑相同三图，输出 `reload-outputs.json`、`reload-comparison.json` 和 logits。 |

## 5. 复用顺序与固定条件

完整依赖顺序：`export_check.py export` → `export_check.py reload` → 两个 BF16 检查脚本 → `evaluate.py adapter` → `evaluate.py bf16` → `quantize.py --prepare` → `quantize.py` → `check_quantized.py` → `vllm_check.py bf16` → `vllm_check.py awq` → 两次 `compare.py` → HTTP 图片验收。

**不要在原目录直接整套重跑。** 这是本轮固定配置实验，换轮次先复制脚本到新输出目录，并核对：

1. `ROOT`、`RUN`、`BASE`、`DEST`、adapter 来源、训练报告、样本和参考答案。`check_weights.py` 还从 manifest 读取路径；只复制文件不足以切换来源。
2. `evaluate.py` 中 best_epoch=6 的断言；`quantize.py` 中 16 图与 15 个 MTP 张量等架构假设；`compare.py` 固定三图；权重检查固定 g32 打包形状。
3. `check_quantized.py`、`vllm_check.py` 仍写死旧 BF16 路径；迁移目录不自动更新它们。
4. GPU 步骤顺序执行。导出、evaluate 和实际量化要求 GPU0 空闲显存超过 65 GiB；离线 vLLM 使用 85% 显存预算。需要重跑时先安排停止 8004 释放 GPU0，完成后再启动。
5. 导出/量化拒绝覆盖已有 `model/`；评估、对比、检查和 HTTP 示例会改写各自同名 JSON/PT。先保存旧证据；仅查看结果时直接读已有 JSON，无需执行脚本。

量化环境为 LLM Compressor 0.14.0 / compressed-tensors 0.19.0；推理环境为 vLLM 0.24.0+cu124 / compressed-tensors 0.17.0。两套环境已实际跑通，不要为了版本一致而随意升级现有环境。PATH 必须包含 vllm2/bin，服务配置和离线 vLLM 脚本已处理 ninja 查找问题。
