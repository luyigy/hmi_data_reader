# PLAN · 飞书群任务广播与整体验收

## 总体目标

用户在群主聊天区明确发布一条公共通知，所有符合范围的任务及其 Agent 在各自下一轮处理时看到通知，同时保持任务私有历史隔离。

## 当前障碍

现有任务话题隔离尚未实现，前置计划为 `docs/466_PLAN_20260922_飞书群任务话题隔离与开关.md`。当前 `live-room-messages.ts` 的 `deliveryIntent: broadcast` 是房间内投递语义，不能当作跨任务公共通知。现有 `live-room-members.ts` 使用 `task-room.ts` 构造成员可见历史，广播必须在真实执行上下文链路接入，不能仅写一条“发送成功”的群消息。

## 总体路线图与本 PLAN 结果

尺度：Phase PLAN，覆盖前置隔离完成后的公共通知能力。每份 PLAN 最多 3 个 Slice。

| 阶段 | 解决的问题 | 交付结果 | 所属计划 |
| --- | --- | --- | --- |
| 任务隔离与开关 | 群内不同任务共用上下文 | 稳定隔离收发与管理操作 | 前置 PLAN 466 |
| 广播持久化 | 公共通知没有可靠身份与范围 | 可恢复、可去重的广播记录 | 本 PLAN S01 |
| 下一轮可见 | 各任务/成员可能漏读或误触发 | 下一轮执行按范围补入 | 本 PLAN S02 |
| 用户广播入口 | 用户无法发出明确公共通知 | 广播操作与真实双任务验收 | 本 PLAN S03 |

完成后，用户可明确广播；系统回执区分“已记录，目标任务下一轮可见”和“已被执行上下文接收”，不承诺 Agent 已理解或正在运行的模型已收到。

## 固定语义与范围

- 只接受群主聊天区的显式广播操作，复用现有发言访问授权；未经授权的用户不得广播。群闲聊不自动广播，话题内消息不自动升级为广播。
- 广播范围为发布时同群、已创建且未归档的隔离任务。按稳定序号与创建/归档状态固定范围，不能在读取时随意扩大；跨群任务绝不读取。
- 模式关闭时拒绝新增广播，已记录但未消费的广播仍可被原目标任务读取；已有任务隔离规则不变。
- 新建任务默认不读取创建前广播；长期公共要求另存群配置，不以补发历史广播替代。新加入任务的 Agent 需要能读取该任务适用的公共上下文。
- 广播不主动唤醒所有 Agent、不打断运行中的模型；它不能代替紧急停止。运行途中出现的新广播在下次执行补入。
- 广播保留原文、来源、顺序及 ID，不复制任务私有讨论。用户通知按用户内容进入上下文，不伪装成系统或开发者指令。
- 不承诺外部模型“恰好执行一次”。本地入库和上下文注入须幂等，失败重试不能漏通知；用稳定广播 ID 支持识别重试。一个房间的某成员读过不能使其他成员漏读。
- 不做实时打断、广播触发批量执行、全文搜索、复杂订阅系统、worktree 隔离或新网页面板。

## S01：建立广播记录与确定的接收范围

- **目的**：公共通知在重启、重放和任务状态变化时仍保留稳定归属。
- **完成后结果**：服务层可发布一条广播，重复事件得到同一记录，A/B 属于范围而其他群及后来任务不属于范围。
- **实现方法**：复用现有 Prisma 与任务绑定，保存群内递增序号或等效稳定顺序、来源消息 ID、原文、发布时间和接收范围。以来源身份/消息 ID 唯一约束去重；在事务中固定目标集合或等价的可重建边界，不依赖可变“当前活跃房间”推算历史目标。存储方案由现有模型决定，只增加需要的记录与约束。
- **修改边界**：`prisma/schema.prisma`、新增 migration、单独的最小广播服务（建议 `src/lib/feishu-task-broadcast.ts`）及直接测试；不开放命令、不接执行器。schema 与服务属于一个持久化能力，允许超过两个生产文件。
- **验收**：真实隔离测试数据库验证重复/并发发布只入库一次、顺序稳定、重启恢复、跨群拒绝、发布时归档排除、后来创建排除、关闭后拒绝新发布；广播原文不混入任务私有文本。
- **前置与停止条件**：前置 PLAN 已通过隔离验收并有提交证据；执行前按 AGENTS 做共享数据影响分析。缺确定的创建/归档语义时停止并补前置，不以易变查询伪造范围。先独立验证持久化可避免执行器问题掩盖漏记广播，故不与 S02 合并。
- **交付物**：存储与测试提交、记录范围与去重约定的 HANDOVER；交接 S02 后停止。

## S02：把广播可靠补入各成员下一轮上下文

- **目的**：通知真的出现在目标 Agent 输入里，且不因另一个成员先读取或执行失败而丢失。
- **完成后结果**：同群 A/B 在各自下一轮能读取广播，A 的私人消息仍不进入 B；广播本身不产生自动执行。
- **实现方法**：追踪 `live-room-delivery-execution.ts` 到成员执行与 `live-room-members.ts` / `task-room.ts` 的真实上下文构造路径，选择现有共享入口接入。优先将广播按稳定 ID 幂等写入各目标房间可见历史，沿用现有每成员会话消费机制；若该机制不能覆盖新会话/重试，则使用最少的成员或会话消费位置。不得仅维护一个房间级“读过”游标。可持久重建上下文后才推进对应消费位置，避免构造 Prompt 后启动失败造成漏读；测试多成员与会话重置。积压超过上下文限制时有序分批，未注入部分不确认、不静默丢弃。
- **修改边界**：广播服务与实际公共上下文入口，必要的执行调用处及直接测试；不改各 Harness 协议、不新增调度器、不做命令 UI。具体接入点以完整调用链为准，不按文件名猜测。
- **验收**：检查实际执行输入包含广播 ID/原文；覆盖 A/B 各两个成员、仅一个成员先执行、执行失败重试、重启、会话重置、新加入成员、运行期间发布、重复事件和积压；验证无广播触发执行、无跨群泄漏、无任务私有文本串入。新建任务不读旧广播。
- **前置与停止条件**：S01 通过。无法证明消费确认与历史重建一致，或需要重写 Harness/调度系统时停止并另立计划，不新增第四个 Slice。
- **交付物**：上下文接入及测试提交、记录失败与重试语义的 HANDOVER；交接 S03 后停止。

## S03：提供显式广播操作并完成真实群验收

- **目的**：用户有明确公共沟通入口，且能够验证隔离和广播同时成立。
- **完成后结果**：在群主聊天区发送明确广播，看到记录回执；任务 A/B 下次继续时收到相同公共通知，各自私有历史不混合。
- **实现方法**：在现有命令解析/处理链增加显式广播操作与帮助，复用发言授权和群模式状态。具体命令名按当前 parser 确定；回执说明目标任务数量、下一轮可见、不立即打断。任务话题里误用时给出提示，不自动改成群广播。
- **修改边界**：`src/lib/feishu-command-parser.ts`、`feishu-live-room-commands.ts` 或职责明确的广播 command 模块、对应测试；不新增网页、定时轮询或主动唤醒。
- **验收**：自动测试授权、关闭模式、空广播、重复发布、话题内误用、普通闲聊不广播。真实群按以下顺序验收：开启模式→创建 A/B→各发不同私有标记→群广播公共标记→分别继续 A/B→核对各 Agent 输入与正确话题输出→验证同房其他成员也可见→关闭模式→已有任务继续隔离且拒绝新广播→重新开启→重启恢复；另验证归档任务、后来新任务及另一个群不误收。运行前置计划受影响回归及长文件检查。
- **前置与停止条件**：S02 通过且有授权测试群/账号。没有真实飞书条件时仅报告自动测试结果，标记真实验收受阻，不把模拟接口结果当作上线证据。不得向未经授权的群发送测试信息。
- **交付物**：入口与测试提交、脱敏验收证据和终止式 HANDOVER；仅所有条件通过后标记完成并等待用户验收。

## 验收与退出

两个计划合起来的完成标准：任务输入、会话、结果和控制不串房；广播对目标任务各成员下一轮可见；普通闲聊不广播；开关切换和重启不丢绑定、不混历史、不漏已记录广播。隔离针对消息与会话，不保证共享工作目录的文件并发安全。

每个 Slice 独立完成行为测试与 `npm run check:long-files`，按合同生成 HANDOVER、暂存后 preflight、仅提交自身修改后停止；达到阻断阈值的文件不得增长。若单个 Slice 实施时发现超出 Session 能力，另立有限范围 PLAN，不继续拆碎本计划。

本次为候选 `ready / await_approval`，不会自动提审或接续前置计划执行；两份计划各自审批。存在的业务改动保持原样，禁止改写已提交历史。
