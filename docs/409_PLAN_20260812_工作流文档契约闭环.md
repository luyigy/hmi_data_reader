# PLAN · 工作流文档契约闭环（事前预防）

> 本 PLAN 是总设计稿 `docs/408_PLAN_20260812_三Harness进度流精准解析脱敏去重完整展示.md`
> 的 **C 组（文档契约闭环）** 拆出的独立可执行计划。408 作为四组（A 进度流 / B watcher
> 可靠性 / C 文档契约 / D 权限与会话）的总纲保留为评审稿；B/A/D 组各自另立可执行 PLAN。

## 背景与根因

经核验源码，一篇 HANDOVER 要过 **~20 条相互依赖的规则**（`workflow-validator.ts` + 合同）：
YAML 必须是 mapping；`doc_type` 与文件名一致、`doc_status`/`next_action` 在枚举内；**Prompt 标记是
最大地雷**——可执行动作必须**恰好一对**标记、终态动作必须**零对**（`promptFrom()` 靠
`split(start).length` 数次数）；Prompt 内容必须引用文档名；`slice` 必须是 PLAN 里真实存在的编号；
PLAN 的 kind/roadmap/父级 slice 校验……

**结构缺陷（链条脆的根因）**：这 20 条规则**只在两个边界生效**——`reference-transaction` 钩子
（commit 时，且只看 `$old..$new` 单提交）和 watcher 扫描（异步、事后）。而 Agent 拿到的只是
`AGENTS.md` 几条散文 + 一个占位符模板——**规则在代码里是严格的机器契约，给 Agent 时却退化成
“请读模板自己悟”**。失败回报是一行拼接字符串（如 `executable action requires exactly one prompt
marker pair`），Agent 得反推才知道“要删掉标记”。本计划作者写 408 时就连续踩了两次 `PROMPT_FORBIDDEN`。

**架构决策（@antigravity 拍板）**：骨架生成器治本且零运行时风险（优先），preflight 必须共用
`workflow-validator.ts` 校验核（SSOT，严禁分叉），收窄 Prompt 标记高频地雷。因 scaffold 的自检依赖
preflight，本 PLAN 切片顺序为 S01 Preflight → S02 Scaffold → S03 标记诊断。

## 目标

- 把“事后拒绝”前移成“事前对齐”：写作时可机器自检，提交前快循环修复。
- 从物理上消灭“Agent 手写格式敏感样板”这一整类失败（编号、frontmatter、Prompt 标记、slice 引用）。
- 维持**单一事实来源**：preflight 与钩子/在线校验共用同一套校验核，规则不漂移。

## 非目标

- 不改 watcher/cursor/调度（属 B 组）；不改 harness（属 A 组）；不改权限/会话（属 D 组）。
- 不改 append-only 历史保护；不改 PLAN/HANDOVER 模板正文内容。
- 不把原始规则重新发明；C 组只新增文件 / 新增 CLI 参数 / 抽象读取层 / 改 AGENTS.md 文字，不破坏
  现有钩子与在线校验行为。

## S01：Validator 工作区 Preflight + 结构化输出

**范围**（`src/lib/scheduled-jobs/workflow-validator.ts` + `scripts/validate-workflow-documents.ts`）

- 在 validator 内抽象文件读取层为一个 `Reader` 接口（`read(path): Promise<string>` +
  `exists(path): Promise<boolean>`），统一现有 4 处 `git show '${ref}:${path}'` 读取点
  （contract `:104`、exists `:202`、readPlan `:314`、candidate content `:550`）。
- 提供两个实现：`GitRefReader(cwd, ref)`（现状行为，钩子/在线校验用）与
  `WorkingTreeReader(cwd)`（从 `fs.readFile` 读工作区；引用的父级 PLAN 工作区不存在时回退到
  `HEAD`，保证跨文件引用校验不丢）。
- `validate-workflow-documents.ts` 新增 `--preflight <工作区文件> [--json]`：
  - `--preflight` 用 WorkingTreeReader 校验单个工作区文件，**提交前自检**；
  - `--json` 输出结构化 `WorkflowValidationIssue[]`（含 `code/severity/location/message/expected/
    actual/template`），供未来自动修复与 Agent 直接消费；默认仍为人机友好文本（高亮报错 + 修复模板）。
- **SSOT 保证**：钩子的 `--hook-batch` 与在线 `<ref> <doc>` 两种现有入口行为不变，共用同一校验核，
  防止“两套规则又漂移”。内部全用 `Reader` 抽象后，现有调用点行为应与改造前逐字节一致。
- `tests/workflow-validator.test.ts` 增补：WorkingTreeReader 与 GitRefReader 对同一文档结论一致；
  `--preflight --json` 输出可解析、字段齐全；父 PLAN 仅在工作区缺失时回退 HEAD；钩子 `--hook-batch`
  路径不回归。

**完成标准**

- `npm run workflow:validate -- --preflight docs/<工作区文件>` 可在提交前精确报出全部 issue；
- 钩子与在线校验行为不回归；`tsc --noEmit`、相关测试、长文件守卫（注意 800 行预警线，必要时抽
  `Reader` 到同目录小模块）、`git diff --check` 通过。

## S02：工作流骨架生成器（Scaffold CLI）

**范围**（新增 `scripts/new-workflow-document.ts`，封装为 `npm run workflow:new`）

- 参数化生成 PLAN / HANDOVER 骨架：`npm run workflow:new -- --kind handover --plan
  docs/<PLAN>.md --slice S02`（PLAN 同理 `--kind plan`）。
- **自动推算**（消除 Agent 手写格式地雷）：
  - 编号：读当前 ref/分支空间最大编号自增，对齐合同 `numbering.width`（3 位）；
  - 状态与动作：读目标 PLAN 的 slice 列表，判定 `--slice` 是否为最后一个 slice——非终态填
    `doc_status:completed / next_action:next_slice / plan_progress:in_progress` 并生成**恰好一对**
    Prompt 标记（标准 plan + handover 引用）；终态填 `next_action:await_acceptance /
    plan_progress:complete` 且**零 Prompt 标记**；interrupt PLAN 的父级字段按 kind 自动填。
  - frontmatter / 文件名 / Prompt 引用全部按合同模板生成，Agent 只需填正文。
- 生成后**调用 S01 的 preflight 自检**（共用校验核，不另写校验）：输出通过才落盘；未通过则报错并
  保留 `.tmp` 供定位。
- `tests/new-workflow-document.test.ts` 增补：末 slice 与非末 slice 的动作/标记差异；编号自增与
  位数对齐；生成结果过 preflight（绿色）。
- 更新 `AGENTS.md`：将“必须用 `npm run workflow:new` 生成骨架、禁止手工创建 PLAN/HANDOVER
  结构”列为强约束；`git add` 后必跑 preflight（S01）。

**完成标准**

- CLI 生成的骨架过 validator / preflight 全绿；末 slice 自动终态、非末 slice 自动可执行；
- 编号不重复、位数对齐；AGENTS.md 指令更新；`tsc --noEmit`、相关测试、长文件守卫、
  `git diff --check` 通过。

**非目标**：不做交互式 TUI；不改 PLAN/HANDOVER 模板内容；不改 watcher/钩子行为。

## S03：Prompt 标记高频地雷精准诊断

**范围**（`src/lib/scheduled-jobs/workflow-validator.ts` + preflight 输出）

- 对 `promptFrom()`（`:153-158`）的标记计数失败提供**精准诊断**：检测到非 0/1 对时，issue 的
  `actual` 填“检测到 N 个 start / M 个 end 标记”、`template` 给出“删除多余标记”或“补齐缺失标记”
  的定位（含出现行号），并把终态文档误含标记与可执行文档漏标记区分成不同 `code`。
- preflight 文本模式下，对标记地雷给出高亮 + 行号 + 一键修复指引；`--json` 模式带 `code` 供
  Agent / 自动修复按类处理。
- **软容忍评估（可选）**：评估是否允许终态文档保留惰性注释标记（避免正文提到标记串即被误拒），
  若改动风险低则纳入；否则只在诊断层加固，不改判定语义。
- `tests/workflow-validator.test.ts` 增补：多对/半对/终态含标记/可执行漏标记四类场景的 code 与
  定位准确性。

**完成标准**

- Prompt 标记类错误从“一行拼接字符串”升级为结构化、可定位、可机器消费的诊断；
- Agent 拿到 issue 可直接判断“删/补标记”；`tsc --noEmit`、相关测试、`git diff --check` 通过；
- 现有标记判定结果（仍按合同 0/1 对）不回归。

## 风险与守卫

- **SSOT 红线**：S01 preflight 必须共用 `workflow-validator.ts` 校验核（抽象 Reader 实现），严禁
  分叉独立校验脚本；S02 生成器只产文件、不改 watcher/钩子判定语义，生成后必跑 preflight 自检；
  S03 不改 Prompt 标记的判定结果（仍按合同 0/1 对），只升级诊断信息。
- **长文件守卫**：`workflow-validator.ts` 已较大，抽象 `Reader` 时优先抽到同目录小模块
  （如 `workflow-reader.ts`），不越 800 行预警线；开工前跑 `npm run check:long-files`。
- **Git 历史**：本仓库工作流历史只追加；本 PLAN 落地期间不 amend/rebase/reset/强推。
- **不阻塞**：本 PLAN（C 组）与 A/B/D 组文件集不重叠，可并行；C 组内部 S01→S02→S03 串行。
