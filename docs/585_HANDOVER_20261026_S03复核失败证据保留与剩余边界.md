## 实现与边界

1. `coordinator.ts` 不再用架构复核的失败改写业务检查；架构 Gate 单独失败。
   验收进程失败或协议补收耗尽时保留原检查，追加未通过的验收 Gate，摘要明确“未完成，已有测试结果保留”。
   真实业务否决、固定候选污染、人工批准仍按既有路径处理。
2. `store.ts` 在事务发布处单独核验复核是否完成。即使所有业务检查都为 passed，平台失败、协议失败或
   明确阻塞也不能放行；不依赖协调器人为把所有检查改成 false。固定输入、实际模型、逐项验收回执和
   `assertCandidateInputsIntegrated()` 仍保留。未完成复核不要求伪造一份成功验收回执。
3. `architecture-review.ts` 修复连续故障恢复：架构重试成功后进入验收，验收恢复只复用最近的成功架构记录，
   且须匹配原复核者、固定提交组合；agent_owned_v1 还须匹配 execution inputs。
   不再退回最初失败的架构 claim。协调器准备失败也沿已持有的验收阶段发布，不倒回架构阶段。
4. `card-status.ts` 将已停止的复核进程/协议/环境故障显示为“验收/架构审查未完成 · 执行异常”，
   区分业务“未通过”，不改执行状态机或审批结论。

四处生产修改属于同一链路：证据生成 → 事务 Gate → 固定阶段恢复 → 卡片呈现。
没有数据库迁移、预算重置或新恢复调度器。历史账本只读；旧合同在后续运行时也获得证据保留修复，
不会重写旧事件。agent_owned_v1 继续不执行平台业务测试。
