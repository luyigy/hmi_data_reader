# Kimi 失败退出残留锁修复

## 范围与实施依据

用户在 Feishu DM 08a216 读取 618 后要求“解决残留会话锁”。本轮仅修 Kimi 失败退出的锁清理时序，并对 618 指定现场锁进行独立核查和受控回收；不处理普通群回复路由、不重放业务请求、不恢复供应商额度。

基线 `348cf71`，隔离工作区 `/data1/code/agent-platform-v2-worktrees/kimi-stale-lock-20261102`。开工长文件守卫通过，无达到 1,000 行阻断阈值文件。

实施前实验：真实 Kimi 2.3.1、临时 home、Bubblewrap 沙箱和本地 429 模拟接口。第一次得到额度失败；同 Session 第二次新请求得到 `40931`。命令为 `KIMI_SERVER_NATIVE_BIN=/home/hello/.kimi-code/bin/kimi npm run test:kimi-quota-native`，断言期望第二次仍能访问模拟接口，实际占用错误，退出 1。正常完成后的沙箱续聊通过，问题集中于失败退出。

实施方案：先关闭原生服务再发送桥接错误帧，沿用原生服务的释放逻辑，不引入每次启动自动清锁。修改范围为 bridge、协议 fixture、针对退出清理和原生沙箱续聊的测试。验收为错误原因保留、失败后锁不存在、同会话下一条新请求只提交一次、占用锁保持原样、原有退出/steering/沙箱测试通过。若不能证明现场锁失效，则保留现场锁并报告，不强制接管。

## 根因

`bridge.fail()` 原来先 emit error 再 stop。宿主 `runKimiServer` 收到 error 会立即终止 Bubblewrap 进程组；PID namespace 随之关闭，打断 Kimi 的 SIGTERM 清理，留下原生锁。下一沙箱再次分配同样的 PID 9；Kimi 原生锁只判断 PID 存活和主机启动时间，无法辨别不同 PID namespace，因而错误报告另一个实例仍占用会话。

仅把错误帧移到 stop 的原生关闭步骤之后，真实复现即转绿。正常退出由 Kimi 自己释放锁；平台不按超时、PID 数值或错误码盲删锁。

- `npm run test:kimi-server` 通过。新增延迟 SIGTERM 释放的 fixture，断言宿主处理失败前原生清理标记已写出；原有错误脱敏、退出、超时、steering 和子进程清理通过。
- `KIMI_SERVER_NATIVE_BIN=/home/hello/.kimi-code/bin/kimi npm run test:kimi-quota-native` 通过。真实程序在沙箱内连续两次额度失败，第一次和第二次退出后锁均不存在，同 Session 两条新请求各提交一次。另植入代表占用者的锁，验证返回 40931、锁内容未变且无模型请求。共 2 次 loopback 模拟接口请求，真实模型请求 0。
- `KIMI_SERVER_NATIVE_BIN=/home/hello/.kimi-code/bin/kimi npm run test:kimi-server-native` 通过。新增正常完成后的沙箱同会话续聊；原有 Bash、两条 steering 各一次、print 回退和读写/网络沙箱检查通过。8 次请求全部到本地模拟接口。
- `npx tsc --noEmit --incremental false`、变更 TS 测试的 ESLint、两个 CJS 文件语法、`git diff --check`、长文件守卫均通过。

## 现场遗留锁回收

读取锁身份和所有者 namespace PID，检查当前用户全部进程的内核 `NSpid`，确认无 PID 9 的候选所有者、无 Kimi/bridge 进程；检查原生实例注册端口全部无监听。首次路径检查因会话实际位于 workspace bucket 而停止；另一次检查遇到 sshd 的 `/proc/.../exe` 不可读也停止，两次均未移动锁。后续采用可读的内核 NSpid 和 cmdline 核查，不依赖读取 sshd 可执行文件。
