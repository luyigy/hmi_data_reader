### 生成后的 BF16/Float 冲突

第二次试跑目录：`output/training-prep/small-sample-20260925-010850-1646186/`，同名 `.log` 为日志。首图完成 loss 和生成，第二图前向在视觉编码器 LayerNorm 报：

```text
RuntimeError: expected scalar type BFloat16 but found Float
```

根因定位：直接 loss 前向缺少混合精度上下文，而 Unsloth 的 `generate()` 内部使用 autocast，连续“loss→generate→下一次 loss”暴露精度不一致。修复在共享 `model_loss()` 入口使用 `torch.autocast("cuda", dtype=torch.bfloat16)`，训练前/后评估、重载评估及训练前向统一调用。`input_ids` 和 `labels` 保持 int64，不能把整个 batch 强制转成 BF16。

前一轮 GitNexus MCP 因数据库格式不兼容失败，本地 CLI 也未给出可用风险评级（UNKNOWN）；已报告限制并用源码调用核查补充。不能把它记作图分析通过或 LOW。本轮只写文档，未修改代码符号。

## 4. 经验教训

1. **用真实阶段定位故障。** 模型加载成功、日志更新、进程运行都不是开始训练；本次实际失败于 before 评估。监控应区分加载、前评估、TRAIN step、保存、后评估和重载，结合退出码、异常栈和产物判断。
2. **警告与致命异常分开。** torchao 版本警告并非本次 LayerNorm 报错的修复方向；当前使用 bitsandbytes，已有正反对照支持 autocast 修复，不为消除无关警告继续升级环境。
3. **回归要覆盖状态切换。** 单张前向或独立生成正常，不能覆盖生成后下一张 loss 和切回训练。最小回归应包含触发序列，并用旧实现证明它确实会失败。
4. **复用公共入口修复精度。** 训练、评估、重载都要一致；只在报错图片处转换 dtype 会漏掉其他入口，也可能破坏整数 token/label。
5. **区分数据事实、工艺语义和确认范围。** 保留有效零值；灰显按区域解释；缺输入就表达未知。用户确认一条公式不代表整张图、bbox 或其他读数均通过。
6. **三图拟合只是流程验证。** loss 下降不代表抽取正确，更不代表新机台泛化；当前 prompt 还包含日精布局专属知识，效果也不能全部归因于微调。
7. **失败目录保留，每次新建输出。** 脚本用 `exist_ok=False` 防覆盖；不要复用失败目录或把不完整 before.json 当成功报告。日志、数据及环境在 Git 外，迁移 session 到另一台机器需另行备份。
8. **机器人回报也需验证。** 接管消息、Typing 或 runtime 的“completed normally”不能代替训练成功。群内 Hermes 已回报监控退出且无自动汇报等待；这是对方回报，本轮没有检查远端进程，也没有重新派发监控。
