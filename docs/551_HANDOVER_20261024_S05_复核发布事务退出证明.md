# S05 可验证单元：复核失败发布不再等待事务外连接

## 交付、运行命令和通过标准

本轮修复 `submitNodeVerification` 的复核平台失败发布：在事务外观察实际 Writer 退出，
事务内使用已有 `taskRunExitMatches` 对照同一 TaskRun/参与者身份，再按原 claim、候选和预算规则发布。
未调大超时、扩大连接池、放松断言或改写上一单元的环境分类逻辑。

```bash
cd /data1/code/agent-platform-v2-manual-runtime-repair
node scripts/sandbox-postgres-session.mjs run task-graph-review-publication
node scripts/sandbox-postgres-session.mjs run task-graph-condition-recheck
```

第一条命令应有 acceptance / architecture 两条 PASS，沙箱退出 0，SQL/schema/端口/目录清理通过。
入口为这个窄回归固定 `connection_limit=1`，其他套件保留原连接配置；不增加事务超时。
单连接、真实 PostgreSQL 账本和真实 nonce 子进程下，已退出的复核发布应完成；
仍存活、未知或观察后身份发生变化的 Writer，以及旧 claim，必须被拒绝且不写执行状态/事件。
成功后原候选和 claim 不变，revision 从 7 到 8，平台预算从 0 到 1。
窄夹具的候选为固定格式值，不声称它执行了实际 Git 交付；真实协调器/Git/恢复行为由第二条旧回归覆盖。

第二条命令应保留 Deployment / Review / Conditions 三组成功结论，退出 0，**完整日志不得出现 P2028**。
本轮联合运行中该套件已达到这项标准，但同一命令后续的环境套件失败，不能把整条命令记作绿色。

**本轮只交付这个发布事务修复单元，S05 仍未整体完成。下一 Session 继续 S05，不进入 S06。**

## 根因证据及退出码区别

起点 `e7dc6e3`，分支 `manual/s02-runtime-repair-20261023`，开工工作区干净；长文件检查无 1000 行阻断项。

2. 加诊断后同样复现三次 P2028。独立观察连接每 100 ms 读取 `pg_stat_activity` / `pg_locks`：
   143 个长事务样本均为 `idle in transaction / ClientRead`，最长约 4.98 秒；
   `pg_blocking_pids` 为空，未获批锁数为 0。最后一条 SQL 是读取失败复核 TaskRun 的 id/status。

   对应源码正是 `submitNodeVerification` 在持有连接和节点行锁后调用 `observeTaskRunWriter`；
   该函数通过全局 Prisma 读取 TaskRun，而不是当前 tx。单连接池必须等外层事务释放才可完成读取。
4. 新窄回归在修改生产代码前退出 1，实际错误为相同的 P2028（5000 ms 超时、约 5015 ms 后查询）。
   修复后两条路径均通过，最终单独运行发布耗时分别为 44 / 34 ms；耗时仅描述本次实测，不作为性能承诺。

   这是历史事务边界缺陷，单连接测试使它稳定暴露，不能只归为测试并发或无关基线问题。

退出码取决于错误到达的调用边界：`runTaskGraphCycle` 给后台 verifyNode 安装 catch，记录错误后仍可继续；
前台 cycle/控制调用的事务启动错误若上浮到测试 main，则退出 1。550 的失败日志确有
`Unable to start a transaction in the given time`，符合连接被占用时的另一种后果。
本轮直接观察了后台吞错与窄发布调用退出 1；未确定性重放所有历史前台抢连接时序，
不声称已经量化 S05 修改对历史触发概率的影响。

## 锁顺序调查的边界

本轮观测到的单连接超时没有数据库阻塞者，因此不能把它解释成 SQL 锁死锁。
但源码另有值得继续验证的顺序差异：

- `publishReviewPreparationFailure` / `submitNodeVerification` 先锁 node，之后经 `applyReviewFailureTx` →
  `applyExecutionOutcomeTx` 请求 graph-control advisory lock。
- admission (`admitNode`) 和复核预留 (`reserveGraphReviewClaim`) 先取 graph-control，再锁 node。
- 单纯 pause 控制不锁 node，不能仅凭 control 名称声称它和 publication 已构成死锁。

这些顺序本轮未改。下一单元使用独立真实连接、明确会合点和 `pg_blocking_pids` 观察实际并发调用，
再决定最小修复；本轮的单连接通过不能证明多连接锁顺序安全。
同类源码搜索还发现 phase-worker 的部分事务内退出观察调用，是否触发外部数据库读取应按实际分支继续核对，
不把未执行的分支计入已修复范围。
