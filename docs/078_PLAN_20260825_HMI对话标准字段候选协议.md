# 078 PLAN 20260825 HMI 对话标准字段候选协议

## 1. 背景与仓库边界

当前 pilot 已在本仓增加 `/api/v1/draft`，但输出仍是屏幕自由
`label/value/unit`，无法让下游确定写入哪个标准字段。该协议的产生者是
`hmi_data_reader`，因此本 PLAN 只落在本仓；页面确认、`confirmed_fields`
和普通/科学试模接入属于 `mold-data-webpage-tool`，待本协议交付后在该仓
单独立 PLAN。

开工基线存在 4 个未提交 pilot 改动：`hmi_service.py`、
`scripts/vlm_qwen.py`、`tests/test_generic_extraction.py`、
`tests/test_vlm_text_mapping.py`。执行者必须先审计 diff 并保留已有工作；不得
reset、checkout 或覆盖，只在确认它们属于本 pilot 后作最小收敛。

## 2. 目标协议

请求由调用方提供当前目标和最小字段子集：

```json
{
  "message": "",
  "target": "normal_trial.holding",
  "current_structure": {"holding_segments": 3},
  "allowed_fields": [
    {"field_id": "holding_segment_pressure", "label": "各段保压压力", "unit": "bar", "shape": "array"}
  ]
}
```

响应只允许引用请求中的 `field_id`：

```json
{
  "candidates": [
    {
      "field_id": "holding_segment_pressure",
      "values": [360, 320, 280],
      "unit": "bar",
      "evidence": ["保压压力 360 320 280"],
      "status": "needs_confirmation"
    }
  ],
  "structure_suggestion": {"holding_segments": 3},
  "questions": []
}
```

服务端必须拒绝非白名单 `field_id`、错误 shape、非法值类型和无法追溯到
OCR 文本的证据。VLM 只做语义归位；不换算单位，不推导数据库路径，
不持久化任何内容。

## 3. S01：纯函数候选协议与校验

1. 按本仓 `AGENTS.md` 先对将修改的每个函数运行 GitNexus upstream impact，
   向用户报告直接调用者、受影响流程与风险；HIGH/CRITICAL 先警告再编辑。
2. 将现有 `draft_from_ocr` 收敛为最小的“请求上下文 → VLM → 严格候选”纯逻辑，
   复用现有 OCR evidence 与字段目录数据，不引入新依赖或新抽象层。
3. 只保留一组可运行的聚焦测试，覆盖白名单、scalar/array、用户纠正、
   证据引用、空 OCR 和非法 VLM JSON。

停止条件：纯函数协议与聚焦测试通过；不接线 HTTP，不修改 Web 仓，
创建 S01 HANDOVER 后停止。

## 4. S02：HTTP 接线与回归收口

1. 在 `/api/v1/draft` 接入 S01 请求/响应协议，保留已有 Bearer 鉴权、
   并发限制、图片校验和 OCR 失败语义。
2. 验证旧 `/api/v1/recognize` 响应零变化；验证 draft 不落库、不写文件且
   不允许 VLM 绕过字段白名单。
3. 运行聚焦测试和与改动相称的服务回归；提交前运行 GitNexus
   `detect_changes()`，核对只影响 draft 协议与预期鉴权流程。

停止条件：协议与回归验证通过，创建合同合规的 S02 HANDOVER，将本 PLAN
标记完成并停止。不部署、不重启服务、不自动进入 Web 仓实施。

## 5. 后续仓库接力条件

S02 交付的 HANDOVER 必须记录最终请求/响应示例、验证命令和 commit。
只有该交付完成后，才在 `/data1/code/mold-data-webpage-tool/docs/dev/` 建立新 PLAN，
负责候选确认、写入 `confirmed_fields`、普通试模候选复用与科学试模温度页接入。
