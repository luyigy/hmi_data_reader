# PLAN · HTML 计划最小试点

## 目标和边界

用户想阅读 HTML 计划，普通 HANDOVER 保持 Markdown。当前工作流合同、生成器和校验器以 Markdown PLAN 为前提，直接改文件后缀会让文档无法通过校验。先完成一个**可生成、可校验、可本地打开的 HTML PLAN 候选**，验证格式和使用体验，再决定如何接入 watcher、审批卡及飞书查看。此 PLAN 只覆盖这个试点，不承诺一次切换全平台。

| 本次 | 后续另立计划 |
| --- | --- |
| 定义最小 HTML PLAN 结构，生成并校验样例 | watcher、审批、飞书预览和所有现有 PLAN 入口切换 |
| 保持历史 Markdown PLAN 与 Markdown HANDOVER 可用 | 计划证据质量、伪阻塞和审查自动修订 |

后续工作以试点结论为输入，不预写多阶段代码清单。跨仓权限、worktree 和并行任务调度也是独立议题。

## S01：生成并校验 HTML PLAN 候选

- **目的**：先验证 HTML 文件能承载现有 PLAN 的元数据、Slice 和下一 Session Prompt，避免直接改动自动化派发链路。
- **完成后结果**：`npm run workflow:new` 有明确方式生成一个可在浏览器打开的静态 HTML PLAN 候选；校验器接受该格式，旧 Markdown PLAN 与 Markdown HANDOVER 继续通过。默认生产入口和 watcher 此时仍按原格式运行。
- **实现方法**：读取 `docs/workflow/workflow-contract.yaml`、PLAN 模板、`scripts/new-workflow-document.ts`、`src/lib/scheduled-jobs/workflow-validator.ts` 及直接调用方；用现有合同字段设计约束明确的 HTML 结构。只为 PLAN 候选增加格式识别与生成方式，复用已有字段和校验语义，不引入通用 HTML 解析器或新依赖。样例仅用静态内容；不包含脚本、事件属性、外部资源。
- **修改边界**：合同/模板、生成器、校验器及其直接测试或生成产物；HANDOVER 格式和 watcher 派发逻辑不变。若发现生成器与校验器之外还有必需调用方，一并核对，不能留下可生成却无法校验的入口。
- **验收**：生成 HTML 样例并在浏览器打开；运行 `npm run workflow:validate` 的相关测试，覆盖 HTML 候选、旧 MD PLAN、MD HANDOVER 和无效元数据；运行 `npm run check:long-files`。记录用户是否觉得该呈现比现有文档易读。
- **前置与停止条件**：从目标 HEAD 读取合同和调用链。若现有校验器无法在一个 Session 内安全兼容 HTML，保留生产默认行为，在 HANDOVER 说明具体阻碍和最小后续改动；不顺手切换 watcher 或审批入口。
- **交付物**：一个可独立验证的试点提交，以及按合同生成、校验的 Markdown HANDOVER。HANDOVER 给出样例路径、验证结果和下一步是否值得正式切换的建议。

## 验收与后续

本 PLAN 在 S01 完成后结束。正式把新 PLAN 全部改为 `.html`，需要基于试点单独规划生成、发现、审批和飞书查看的完整路径；旧 MD PLAN 的兼容性是该后续计划的验收条件。计划可靠性与“不要动不动阻塞”的改进也单独规划，避免两个问题互相拖住。
