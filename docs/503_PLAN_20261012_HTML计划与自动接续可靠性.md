# PLAN · HTML 计划与自动接续可靠性

## 目标、现状与路线

用户希望在飞书里阅读和批准易懂的 HTML 计划，普通 HANDOVER 继续使用 Markdown；计划应有事实依据，能自行解决的问题继续推进，只有确实不能安全继续时才暂停。

现行合同的文件名规则、PLAN 模板、生成器、校验器和多个任务入口都以 `.md` 为前提。现有 `/ap plan` 提示词要求列风险和未知项，但缺少先查证、自行排除和区分真正停止条件的要求。结构校验不能证明事实判断正确。多角色审查能识别 `CHANGES_REQUESTED`，但后续接续行为需要改为修订、复审通过后才实施。

本文件是平台自身的 Phase PLAN。每个 Slice 在一个 Session 内完成、验证、提交 Markdown HANDOVER。后续 Slice 开始时须以目标 HEAD 重新核对调用链。

| 阶段 | 障碍 | 可验收结果 |
| --- | --- | --- |
| S01 | 合同不识别 HTML | 新 HTML PLAN 与旧 MD PLAN 均可校验，HANDOVER 仍为 MD |
| S02 | 新建入口仍生成 MD | 新 PLAN 生成 HTML，旧计划仍能新建交接 |
| S03 | 消费入口仍寻找 MD | 自动化可发现、审批和接续 HTML PLAN |
| S04 | 飞书缺少 HTML 查看入口 | 用户可安全查看与待审提交一致的静态 HTML |
| S05 | 计划常把未知项写成阻塞 | 提示词和规范要求证据、自解及真正停止条件 |
| S06 | 审查不通过后的接续不可靠 | 自动有界修订、复审，实质变更重新审批 |

全部完成后，新 PLAN 只有一个 HTML 权威源；历史 MD PLAN 仍可执行，HANDOVER 仍为 MD。审批与所查看的 Git 提交绑定。之前讨论的跨仓写权限、worktree 和飞书话题并行调度属另一项架构工作，本 PLAN 不实施。

## S01：HTML PLAN 合同与校验

- **目的**：先让工作流安全识别 HTML，再切换生产入口。
- **完成后结果**：合规的 HTML PLAN、旧 MD PLAN、新 MD HANDOVER 均通过；无效元数据、Slice、动作和 Prompt 被拒绝。
- **实现方法**：在 `docs/workflow/workflow-contract.yaml` 中按文档类型定义扩展名和模板；定义最小静态 HTML 结构，包括机器可读的元数据、Slice 与 Prompt；复用现有校验语义，修改 `src/lib/scheduled-jobs/workflow-validator.ts` 及其生成产物链路。核对 watcher 对目标 Git ref 的扫描。拒绝脚本和外部资源。
- **修改边界**：合同、PLAN 模板、必要的格式说明、校验器及直接测试；HANDOVER 模板仅作必要引用适配。不重写历史文档。
- **验收**：运行工作流校验测试及 `npm run check:long-files`；测试新旧格式和恶意/缺失元数据。
- **前置与停止条件**：先读目标 HEAD 的合同、模板和校验链路；若无法定义无歧义的最小 HTML 语法，记录证据，不扩展为通用网页解析器。
- **交付物**：一个 S01 提交和按合同生成、校验的 MD HANDOVER。

## S02：新计划生成

- **目的**：让新建入口产出同一个格式正确的 HTML PLAN。
- **完成后结果**：`workflow:new` 和 `/ap plan` 新入口输出 HTML；HANDOVER 仍为 MD，旧 PLAN 不被改写。
- **实现方法**：以 S01 合同为规则源，先更新 `scripts/new-workflow-document.ts` 的模板读取和编号，再更新 `src/lib/live-room-workflows.ts` 的创建提示与路径解析；核对 `src/lib/live-room-handoff-plan.ts`、`src/lib/scheduled-jobs/workflow-roadmap-inbox.ts` 是否复用该生成入口。新格式的自动派发留给 S03，切换期间不提交会误触发 watcher 的执行型 PLAN。
- **修改边界**：生成入口及直接测试；HANDOVER 仍为 MD，消费入口留给 S03。超过一个 Session 能完成的范围时，在本 Slice 中保持旧默认格式，并另立明确的后续 Slice。
- **验收**：测试 HTML 创建、编号、路径、MD HANDOVER 和旧 MD PLAN 的兼容；运行工作流校验。
- **前置与停止条件**：依赖 S01；同一路径不得产生两份不同格式的权威计划，不改写已提交历史。
- **交付物**：一个生成链路提交和 MD HANDOVER。

## S03：调度和接续 HTML PLAN

- **目的**：让已生成的 HTML PLAN 能被现有 watcher、审批和后续 Session 正确消费。
- **完成后结果**：新 HTML PLAN 从提交走到审批和首 Slice；历史 MD PLAN 能继续走完流程。
- **实现方法**：核对并更新 `src/lib/feishu-new-session.ts`、`src/lib/scheduled-jobs/workflow-plan-completion.ts`、`src/lib/scheduled-jobs/git-history-guard.ts` 与 watcher 等消费入口中的后缀假设；确认 S02 涉及的其他创建入口均已切换。复用 S01 的格式判定，避免再次散落硬编码。
- **修改边界**：发现、接续、历史守卫及直接测试；不修改 HTML 预览 UI。
- **验收**：覆盖提交后发现、审批、首 Slice 派发、MD HANDOVER 接续、旧 PLAN 和历史守卫；检查重复事件不会重复派发。
- **前置与停止条件**：依赖 S02；若缺失某个生产入口，先补齐再启用 HTML PLAN 自动派发。
- **交付物**：一个完整消费链路提交和 MD HANDOVER。

## S04：飞书查看与审批

- **目的**：使 HTML 的可读性在真实审批界面生效。
- **完成后结果**：审批卡与查看入口可打开静态 HTML，显示文件和提交；MD HANDOVER 保持现有查看方式。
- **实现方法**：沿用现有认证、Git ref 读取和审批卡，核对 `src/lib/feishu-api.ts`、`src/lib/feishu-document-command.ts`、`src/lib/feishu-markdown-picker.ts` 与相关页面/路由；提供受控静态预览或附件。限制标签与样式，禁用脚本、事件处理器和外链；不假设飞书原生渲染 HTML。审批绑定预览的提交哈希。
- **修改边界**：查看与审批入口、直接测试；不改变批准权限。
- **验收**：检查新旧 PLAN 的链接、授权、版本一致性和恶意 HTML；人工在飞书客户端验证显示。
- **前置与停止条件**：依赖 S03；若无法通过现有认证安全预览，保留受控下载入口并记录限制，不显示不可信 HTML。
- **交付物**：查看/审批提交、验证记录和 MD HANDOVER。

## S05：证据与停止条件

- **目的**：减少未经查证的计划和把普通调查写成阻塞的倾向。
- **完成后结果**：新 PLAN 区分事实与推断，首 Slice 有证据和验收样本，后续 Slice 保持阶段粒度。
- **实现方法**：更新 `docs/workflow/PLAN-writing-standard.md`、HTML 模板、`/ap plan` 与审查提示词：先检索复现，能自解则写行动，能独立推进则继续；只有不可替代的业务裁定、凭据/权限或数据安全风险才暂停。区分正常 Slice 交接和 `blocked`。机器校验只管可确定的结构与引用，不按“阻塞”关键词数量设硬门禁。
- **修改边界**：规范、模板、提示词和直接测试；不改业务仓库的现有 PLAN。
- **验收**：用机台 OCR/模板及温度输入页案例人工走查；提示词测试和工作流校验通过。
- **前置与停止条件**：依赖 S04；真实 HMI 值或数据库写入规则未知时不可臆造，须记录缺口及仍可做的工作。
- **交付物**：规范/提示词提交、走查记录和 MD HANDOVER。

## S06：审查后的自动修订与复审

- **目的**：可修复意见自动处理，实质问题不能悄悄进入实施。
- **完成后结果**：`CHANGES_REQUESTED` 触发有界修订与复审；`APPROVED` 才实施；超限或需业务决定时说明具体原因。
- **实现方法**：沿 `src/lib/live-room-workflows.ts` 的 stage gate、`deferFailure` 和定稿链路区分已批准范围内的澄清与目标、数据/权限边界、验收标准的实质变更。前者本次执行内修订复审，后者生成新版 PLAN 并重新审批。核对持久状态、取消和重试，防止重复实施。
- **修改边界**：多角色工作流控制与直接测试；不扩成通用编排器，不把普通警告升级为硬阻断。
- **验收**：覆盖通过、一次修订后通过、重试上限、实质变更重新审批、重启接续和重复事件；未通过版本不得实施。
- **前置与停止条件**：依赖 S05 的审查标准；若无法可靠绑定提交与批准状态，先补最小链路再启用自动重试。
- **交付物**：工作流提交、失败场景记录和 MD HANDOVER。

## 总体验收

按 S01→S06 逐步交付，最终演练“新 HTML PLAN → 查看 → 审批 → 审查/修订 → 实施 → MD HANDOVER → 下一 Slice”，并回归旧 MD PLAN。每次只消费目标 Git ref 已提交文档；历史不改写，HTML 不执行不可信内容，正常交接不记为阻塞。
