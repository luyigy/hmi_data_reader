## 4. 必须保留的边界

1. 原用户身份、任务归属和原消息授权；Agent 输出不能充当人的批准。
2. 单 Writer、退出证明、幂等、暂停、角色权限及同卡回复；接话与批准分开。
3. 固定候选 SHA、Input Manifest、证据所属版本、日志摘要与环境指纹；读到归档不等于继承结论。
4. 自己的工作区/输出可写，源仓、其他任务及共享运行资源按现有能力策略隔离；凭据不进入证据。
5. Git 历史只追加、受控汇合和总资源/时长预算。无业务分类不等于无限重试。
6. 实施模型与验收模型按实际解析的运行配置区分，不用两个 Agent 名称或两个会话冒充不同模型。
   明确验收但模型不明/相同/不可用时，在配置入口说明问题，不静默跳过或偷偷选一个。
7. 新默认值只用于新提议。旧快照、正在运行的 Writer 和历史证据不被批量改写。

### S01：默认精简交付，自测后直接接续

**目的与结果：** 消除“未指定也自动安排验收”的分支；从新路线提议到 A 交付、B 可派发有完整演示。

**方法：** 沿提议 → 角色配置 → 已批准快照 → 实施结果收取 → 后继准入核对现有链路。
复用 `agent_owned_v1` 和 `ticketVerification`，未指定时默认整票自测、不配置独立验收者。
单 execution 可用已有唯一实施者规则；多 execution 使用计划中明确的整票自测责任，不能任意选第一人。
原有角色推荐不把房间中的 tester 自动变成用户已指定的验收者。
卡片明确“精简：实施自测，无独立验收”；已有状态与依赖规则优先复用，
`passed` 若沿用必须注明自测来源，不能呈现为独立验收通过。不要为了命名新增状态机。

**边界：** 优先 `role-configuration.ts`、`proposal-card.ts`，
核对 `proposals.ts` / `domain.ts` / `implementation-quality.ts` 的既有默认及结果合同。
测试优先复用 `task-graph-proposal.test.ts`、`task-graph-agent-owned-quality.test.ts`。
预计两处主要生产改动；只有现有自测链路确有缺口才补相邻合同，先记录原因，不改数据库。

**验收：** 隔离路线 A → B 中，未指定验收者不创建 review TaskRun，自测证据绑定候选后仅派发一次 B；
缺失/失败/过期自测不交付；明确指定验收者、人工批准、架构复核及暂停保持原意；
运行中和历史路线快照不受默认值影响。确认平台没有额外执行 pytest 等业务命令。

**前置与停止：** 当前工作区干净；没有自测证据或多仓责任不明时停在该票，不能把“精简”解释成无测试。
如果模型配置选择需要更广的入口改动，留给 S02；不在本票迁移 M6。

**交付：** 追加提交、测试及 A → B 演示回执、新 HANDOVER；然后停止。

### S02：显式其他模型验收，业务测试归 Agent

**目的与结果：** 用户选验收者时，对固定候选真正开展其他模型验收；平台只验证身份和证据，不再复跑业务测试。

**方法：** 复用角色运行配置中的 model 和现有复核派发；在确认路线前解析并记录实施/验收模型，
显式不同模型才标“独立验收”。检查项作为 Agent 的执行要求，记录命令、结果、日志位置/摘要、环境指纹及固定版本。
沿 `agent_owned_v1` 的既有质量链路补齐证据；哈希只能证明一致性，不能冒称平台亲自证明测试正确。
实施者仍自测；指定验收者依合同检查固定候选。平台不增加第三轮业务测试。

**边界：** 主要在 `role-configuration.ts` / `coordinator.ts`，视实际配置解析复用相邻 helper；
测试以 `task-graph-agent-owned-quality.test.ts` 和角色/提议测试为主。
模型解析、固定证据与派发属于同一验收入口；若触及更多生产文件，在交接说明原子性或留本票续做。
不修改 Reader/Mold，不删除 `assertCandidateInputsIntegrated()`，不靠节点名字猜最终集成职责。

**验收：** 精简票零 review；显式不同模型恰好一个 review；相同或未知模型不能假称独立；
验收者不能改固定候选，证据必须绑定正确 SHA；失败或缺项不通过，人工批准不被跳过；
同一候选的平台业务命令调用次数为零，规定的 Agent 检查真实执行并有可核对证据。

**前置与停止：** S01 完成。旧路线先形成策略差异与影响清单，保留旧合同执行兼容；
只有用户明确要求迁移具体路线，才使用现有合法规划入口及固定快照核验。
入口若无法表达变更，记录独立缺口，不直接改库、不默认取消 M6 的已有验收角色。

**交付：** 追加提交、显式验收与旧合同兼容回归、新 HANDOVER；阶段一完成后停止。

### S03：用明确结果结束本轮，业务重试留给 Agent

**目的与结果：** 对用户只说明交付、阻塞、失败及原因；认证或平台故障不再把 27 项通过改成 27 项失败。

`needs_human` 仅在确实需要人的输入时说明，不把全部基础设施异常归成人未批准。
Agent 在自己的会话与预算内修业务问题，平台停止根据业务错误 owner 分类自动重启实施者。
基础设施失败保留原测试结果，当前验收显示未完成；恢复只回到失败阶段，不重新做已完成实施。
沿现有结果结构兼容旧账本，不用三种业务结论取代 Writer/租约/暂停等执行状态。

**边界：** 首先核对 `coordinator.ts`、`execution-progress.ts`，以及
`retry-limits.ts` / `preparation-recovery.ts` 的调用者，删除不再必要的业务分类派发分支。

这是一个故障流转边界，若必须同时迁移多个独立入口，先完成“复核失败保留测试证据”子单元并交接，
仍保持 S03 未完成；不把分类清理升级为全库状态机重写。

**验收：** 注入验收 401：通过测试保持通过、验收未完成、后继不误放行、实施者不被重派；
恢复验收仅执行一次；业务测试失败如实失败；超预算停止；重复事件、暂停和 Writer 未退出均不能多启动。
分类计数不再驱动业务重做，但进程退出、租约、退避及幂等保护仍有回归。

**前置与停止：** S02 完成；必须区分业务重试和基础设施恢复，不能删除整个 admission/recovery。
不在本票复制/刷新生产凭据、不清空任务会话目录；认证修复若仍需要，按实际错误另行收口。

**交付：** 追加提交、故障注入证据及“不会重做实施”的回归、新 HANDOVER；然后停止。

### S04：项目拥有环境验证，平台保持通用

**目的与结果：** OCR、浏览器、控制器版本等知识由项目脚本或验证 skill 负责，平台不为每种业务增加环境分支。

**方法：** 复用已有项目运行声明及资源能力：固定源码/脚本版本、依赖与只读资源路径进入输入合同，
Agent 在隔离环境运行项目验证并提交环境指纹。平台核验声明、路径授权、哈希、预算和执行身份。
将 `runtime-preflight.ts` 中业务专属 OCR/浏览器启动检查从通用路径移出，先迁移实际调用者再删除旧分支。
沙箱不能因项目脚本声明就授予跨仓写权限；环境探测也受相同能力边界约束。

**边界：** 主要为 `runtime-preflight.ts` 及其现有声明解析入口；
测试优先 `task-graph-runtime-preflight.test.ts`、`task-graph-environment-outcome.test.ts`。
先用仓内 fixture 演示两类不同项目，真实 Reader/Mold 配置迁移另按仓授权，不代改其业务代码。
旧合同适配未完成时保留兼容入口，不能删除后让旧票无法重放。

**验收：** 固定候选与解释器路径可追溯；资源存在但源码版本错误不能被报成成功；
项目脚本发现缺依赖时返回清楚原因；授权资源可读、未授权路径和运行仓写入仍拒绝；
更换模型/浏览器业务项目无需在平台添加业务条件；平台不再重复运行同一业务验证。

**前置与停止：** S03 完成。遇到新跨仓写入或资源授权缺口如实记录，不以改挂载范围绕过。
若现有声明无法通用表达，先确定最小合同差异，禁止同时设计新环境调度器。

**交付：** 追加提交、两类项目 fixture 回归、环境来源演示、新 HANDOVER；阶段二完成后停止。

## 6. 验收、兼容与停止规则

- 每 Session 开始读 AGENTS、最新交接和本票，检查 Git 状态及 `npm run check:long-files`。
  涉及共享调度/权限时按仓库要求做影响分析；GitNexus 不可用须记录并用源码与回归补证，不能假称已分析。
- 先写能暴露当前问题的行为回归，再修改；测试脚本从 package.json 和现有隔离 PostgreSQL runner 读取，
  不猜 npm 名称，不把生产库作为测试库。类型检查、相关边界回归和文档校验通过后提交。
- 新/旧合同分别验收；检查范围包含默认角色、固定输入、权限、暂停、单 Writer、事件幂等、证据与后继准入。
  不为本包增加数据库迁移、恢复协调器或自动交接引擎。
- 隔离演示成功与生产部署分别记录。后续部署按该 Session 的实际用户授权和已有安全切换机制办理，
  本计划不授权自动部署实施产生的业务代码，也不恢复 M6 或自动启动 M07。
- M6 如迁移策略，先核对当前 run、snapshot、候选及测试证据，展示具体差异；
  没有完成真正的批准/验收/汇合时不得写为 passed。验收职责与最终集成职责另行明确，不借精简模式放宽 Gate。
- 运行方式为本项目 watcher 的 `semi_auto` + `implement`，执行者 Codex 自测后交付，不派独立测试者。
  首票必须经 PLAN 审批卡批准；后续 S01 → S02 → S03 → S04 使用 HANDOVER 自动接续。
  每票完成自测、提交代码和新 HANDOVER 后停止当前 Session，交给平台开新 Session，不在同一轮做下一票。
- S01/S02/S03 成功交付的 HANDOVER 使用 `doc_status: completed`、`plan_progress: in_progress`、
  `next_action: next_slice`；唯一 Prompt 标记块引用本交接和 581，并且只指定下一 Slice。
  S04 完成使用 `plan_progress: complete`、`next_action: await_acceptance`，停止整包自动推进。
  部分完成或失败使用 `next_action: blocked`，保留本 Slice 未完成及证据，等待处理，不自动越过。
- 最终回复原样重复下一 Session Prompt 并附 `WORKFLOW_READY`；文档必须先提交。
  不发布 Issues，不启动任务图，不在实施 Session 自行改 cursor/pending 或放宽审批。
- 本包完成需四票均有证据；部分票完成不能称整个平台已精简。阶段三、旧票自动迁移、Reader 原仓合并与业务修复不在范围。
