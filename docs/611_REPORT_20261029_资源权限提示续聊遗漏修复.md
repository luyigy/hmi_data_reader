# 资源权限提示在原生续聊中的遗漏修复

## 原因与责任

610 修复后用户反馈，同群 Codex 仍说读取 Model 后端必须等待授权卡。
核对 feishu 服务在 2026-10-29 17:55:44 CST 已重启，出问题的运行
`cmvtdj3a900k2sp60dqod8ekx` 于 18:01:47 CST 开始，权限仍为
`full_access / danger-full-access`。运行末尾已有新版“无须重复申请或等待审批卡”结果。
因此不是用户未重启，也不是平台缺少审批卡；610 对原生续聊的验证不完整。

610 将当前权限提示加到 task.description，但普通会话的原生 resume 会经
harnessContinuationInput 换成精简 continuationMessage，仅补回能力与长文件约束。
新权限提示及 resourceAccess.instructions 在这一分支丢失。新 Session 能收到提示，
既有 Session 的后续轮次仍保留旧的授权理解。610 的测试没有绑定原生 Session 并派发第二轮，
所以未覆盖该缺口。此前“重启后下一轮即可”的结论过早。

## 修复

基线 `e6127dd`；分支 `fix/resource-resume-prompt-20261029`；隔离工作区
`output/worktrees/resource-resume-prompt-20261029`。

- 本地 Harness 只生成一份当前资源说明，同时用于完整启动和 continuationContext。
- 普通会话 resume 精简输入补回这份说明，包含当前权限策略及实际补充授权目录。
- Graph 阶段仍使用完整的已验证 StageExecutionRequest，不替换其输入；
  远端调用未传此可选上下文，行为保持。实际权限、授权卡、Session 选择与接续身份均未改动。

## 回归证据

新增真实双轮断言：首轮通过 adapter 的 onSessionStarted 绑定原生 Codex Session；第二轮
走实际 processLiveRoomDelivery / Runner / executePreparedStageHarness，确认进入 adapter.resume、
Session ID 保持一致，并检查最终交给 adapter 的 task.description 与 continuationMessage。
飞书传输与模型用 fixture，不启动生产模型，不操作其他聊天室任务。

旧代码红灯：第二轮缺少当前 Full Access 提示，断言
`resumed native prompt must contain the current permission correction` 失败。
证据：`output/sandbox-postgres-runs/2026-10-29T180524-1565825`。

修复后验证：

- room-resource-card：Full Access 与受限但已覆盖目录两条路径的真实双轮 resume；
  保留新申请卡三个按钮、真实拒绝回调、旧版流、协议示例及最终卡片结果断言。
- stage-harness-dispatch：普通 resume 同时保留能力、长文件、当前资源策略及批准目录；
  Graph 首轮、续聊、阶段切换保持固定输入契约，失效 Session 回退到完整启动输入。
- task-resource-runtime：批准后真实 Bubblewrap 挂载、原生续聊和重复审批防重。
- task-resource-graph：Graph 实施、验收的原生接续、候选固定与人工暂停保护。
- 全量 TypeScript；改动源码及 room-resource-card 定向 ESLint；stage-harness-dispatch
  沿用既有 require mock，仅对该测试关闭 no-require-imports 后检查其他规则；长文件和 diff 检查。

最终数据库回归及构建：

```sh

```

证据位于隔离工作区 `output/sandbox-postgres-runs/2026-10-29T180611-1574940`。

harness-options 动态路由日志，接口最终标记为动态路由，没有阻断构建。
