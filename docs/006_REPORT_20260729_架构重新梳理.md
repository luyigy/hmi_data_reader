  ## 我建议的技术路线

  ### 1. 按整条记录识别控制器，不要逐张图片识别

  这是当前成本最低、收益最大的改动。

  同一条生产记录的 3–5 张截图通常来自同一台机器、同一个控制器。即使温度页没有 Logo，另一张监控
  页可能有。

  建议：

  同一 record 的所有截图
  → 分别 OCR
  → 汇总控制器特征
  → 得到 record 级 controller_family
  → 回填到该 record 的所有页面

  现有逐图关键词识别导致 87 张 OCR 图片中 27 张为 unknown，后处理也只降到 24 张。按记录聚合应
  该比继续扩充模糊品牌词典有效得多。

  已确认过的机台可以保存：

  machine_id → controller_family → hmi_variant

  以后把它作为先验，但仍用图片检查是否发生换屏、升级或传错图。

  ### 2. 伯乐内部必须重新标注控制器

  我查看了伯乐样本，至少能明显看到多种不同界面布局。当前全部归到 BOLE 会让模板互相污染。

  不要根据文件名猜 KEBA、弘讯、EST、B&R。应让熟悉设备的人对每个机台或记录标一次：

  位置 / 机台编号 / machine_brand / controller_family / hmi_variant

  只需要标一次机器级信息，不必重复标每张截图。

  ### 3. 先完成一个真正的端到端薄切片

  不要现在就建“7 家族 × 3 页面”的约 20 个模板。

  建议先选一个布局稳定、图片较清楚的家族，例如现有 ZizES 温度页，完成：

  图片
  → 屏幕裁切
  → OCR
  → controller + page 路由
  → 模板提取
  → 规范化字段 JSON
  → 范围及列数校验
  → 与人工真值比较

  目标输出应类似：

  {
    "controller_family": "ZIZES",
    "hmi_variant": "v1",
    "page_type": "temperature",
    "fields": {
      "barrel_temperature_set_c": [262, 290, 290, 290, 280],
      "oil_temperature_set_c": 0
    },
    "status": "review",
    "warnings": []
  }

  这个闭环准确后，再复制到伯乐的 KEBA、弘讯、EST、B&R。

  ### 4. 模板坐标必须相对屏幕归一化

  当前模板使用原图绝对像素坐标，而且只来自一张 1080×1920 图片。换手机分辨率、拍摄距离或裁切方
  式就会失效。

  建议先透视矫正、裁出屏幕，再使用：

  x / screen_width
  y / screen_height

  模板依赖“屏幕内相对位置”，不要依赖原照片像素。加热段数也不要固定死为 6，应允许按列头动态确
  定。

  ### 5. 先做业务字段真值，不要继续看 OCR 行数

  当前“识别了多少行、多少数字”不是有效准确率指标。

  应该建立小型、分层的真值集：

  - controller/HMI 家族；
  - 页面类型；
  - 每个业务字段名称；
  - 字段值和单位；
  - 图片质量等级；
  - 是否允许自动入库。

  第一轮不用很多：每个待支持的 controller_family + hmi_variant + page_type 选 5–10 张代表图即
  可。评价指标应是：

  - 控制器分类准确率；
  - 页面分类准确率；
  - 字段完整率；
  - 数值准确率；
  - 可自动入库比例；
  - 错误自动入库率——这个最重要。

  在真值集完成前，不建议换 PaddleOCR-VL，也不建议继续扩大模糊词典。

  ## 当前实现中需要注意的问题

    当成不同页面真值。
