# 224_PLAN_20260725_通用项目定时任务平台

## 目标

把现有 `coding-handover-watcher`、`long-file-checker` 和未来同类 CronJob 纳入 Agent Platform 的通用定时任务能力。

最终由统一的项目配置描述“项目—仓库—Git ref—飞书群—任务实例”，由独立 Job Runner 调度代码中注册的 Job handler，并通过现有 `/ap` 飞书入口管理。每个旧 CronJob 只有在对应平台 Job 验证稳定后才停用。

## 已确认的边界

1. Workflow watcher 和 long-file detector 都是通用 Job 的 handler，不各自建设调度框架。
2. 一个飞书 `chat_id` 第一版只绑定一个项目，避免群内命令无法确定目标仓库。
3. YAML 负责项目注册、任务声明和默认启用值；运行时启停状态、锁、游标和执行记录写数据库。
4. 飞书命令不能传入任意仓库路径，也不能直接修改 Git 中的 YAML。
5. 第一版只允许运行平台代码中注册的 Job 类型，不支持任意 shell command。
6. Job Runner 是独立常驻进程，不放进 Next.js Web 进程。
7. 旧 CronJob 与平台 Job 不得长期双写；shadow 阶段平台只观察，不发送消息、不创建审批、不 reset session、不投递 Slice Prompt。
8. 每迁移成功一个 Job，才停用对应旧 Job；不一次性关闭整个 `/data1/code/cronJob`。

## 建议配置

第一版继续使用 YAML 做静态项目注册，但配置文件应归 Agent Platform 管理。最终路径在实施前确认；建议为仓库根目录的 `config/projects.yaml`。

```yaml
projects:
  - id: mold-data-webpage-tool
    name: Mold Data Webpage Tool
    path: /data1/code/mold-data-webpage-tool
    ref: refs/heads/rebuild-postgres-auth-slice

    feishu:
      chat_id: oc_b4d2abbe3c16c3596631c3a9e756bd4f
      approver_open_ids:
        - ou_98a7adb2080847c990466f450943e1a3

    jobs:
      - id: workflow-watcher
        type: workflow_watcher
        schedule: "*/10 * * * *"
        enabled: false
        mode: shadow
        config:
          contract_path: docs/workflow/workflow-contract.yaml

      - id: long-file-detector
        type: long_file_detector
        schedule: "0 9 * * 1-5"
        enabled: true
        mode: shadow
        config:
          threshold_lines: 1000
          extensions: [.py, .js, .ts, .tsx, .jsx, .go, .java, .vue]
          exclude_paths: []
```

约束：

- `project.id`、同项目内 `job.id`、`feishu.chat_id` 必须唯一。
- `path` 必须是绝对路径并位于平台允许的 workspace roots 内。
- `ref`、schedule、handler config 在 Runner 接受配置前完成校验。
- Runner 每次调度周期重新读取 YAML；新增项目或任务不要求重启。
- YAML 删除一个已运行 Job 时，Runner 只停止后续调度，不删除历史运行记录。

## 最小数据模型

不要把 YAML 内容完整复制成第二套可编辑配置。数据库只保存运行态：

### `ScheduledJobState`

- `projectId`
- `jobId`
- `enabledOverride`：nullable；为空时使用 YAML 默认值
- `modeOverride`：nullable；`shadow` 或 `active`
- `lastScheduledAt`
- `lastStartedAt`
- `lastFinishedAt`
- `lastSuccessAt`
- `lastError`
- `cursorJson`：handler 的增量游标
- `updatedAt`
- 唯一键：`projectId + jobId`

### `ScheduledJobRun`

- `id`
- `projectId`
- `jobId`
- `trigger`：`schedule`、`manual`
- `mode`：`shadow`、`active`
- `status`：`running`、`succeeded`、`failed`、`timed_out`、`skipped`
- `scheduledFor`
- `startedAt`
- `finishedAt`
- `summary`
- `error`
- `idempotencyKey`
- 唯一键：`idempotencyKey`
- 索引：`projectId + jobId + startedAt`

第一版不增加独立 Project 表和通用日志表；项目真相保留在 YAML，运行摘要先放 `ScheduledJobRun`。只有出现 UI 编辑项目或大量结构化执行日志需求时再扩展。

## 运行架构

```text
config/projects.yaml
        |
        v
Project config loader + validator
        |
        v
独立 Job Runner ---- PostgreSQL（状态、锁、游标、运行记录）
        |
        +---- workflow_watcher handler
        |
        +---- long_file_detector handler
        |
        +---- future registered handler
        |
        v
现有 Feishu API / Live Room 能力
```

Runner 第一版职责：

- 按 cron schedule 计算到期任务。
- 使用 PostgreSQL advisory lock 或等价数据库锁保证同一 Job 单实例执行。
- 为每次计划执行生成稳定 idempotency key。
- 支持超时；失败只记录，默认不自动重试，避免副作用重复。
- 重启后恢复调度；不补跑所有错过周期，只执行当前周期之后的任务。
- 捕获 handler 结果并更新状态。
- `shadow` 模式禁止外部副作用，只生成检测结果和对比摘要。

第一版不做分布式队列、动态插件加载、任意脚本执行、复杂重试策略和 Web 管理页面。

## Handler 接口

保持最小接口，具体类型实施时按现有 TypeScript 风格确定：

```ts
type JobHandler = (context: {
  project: ProjectConfig;
  job: JobConfig;
  mode: "shadow" | "active";
  cursor: unknown;
  signal: AbortSignal;
}) => Promise<{
  summary: string;
  cursor?: unknown;
}>;
```

要求：

- handler 通过注册表按 `type` 查找。
- handler 不负责自己的 schedule、锁和运行记录。
- 所有外部副作用必须经过 `mode` 护栏。
- cursor 只在成功后提交。
- `workflow_watcher` 必须继续使用现有 workflow contract，而不是在平台重写另一套规则。

## 飞书命令

沿用当前 `src/lib/feishu.ts` 的 `/ap` 路由：

```text
/ap jobs
/ap job status <job-id>
/ap job enable <job-id>
/ap job disable <job-id>
/ap job run <job-id>
```

语义：

- 用当前消息 `chat_id` 唯一解析项目。
- `jobs` 列出当前项目已注册任务及状态。
- `status` 返回项目、仓库、ref、schedule、模式、最近执行、最近成功和最后错误。
- `enable/disable` 只写数据库 override，必须幂等。
- `run` 触发一次手动执行，但仍经过锁、权限、模式和运行记录。
- 未注册 job、重复绑定 `chat_id`、配置无效时明确拒绝。
- `enable`、`disable`、`run` 仅允许平台管理员或项目 `approver_open_ids`。

## 实施阶段

### Slice 1：配置与运行态骨架

1. 新增项目 YAML 和最小校验器。
2. 加入两个运行态 Prisma model 和 migration。
3. 实现按 `chat_id`、project id、job id 查询配置。
4. 增加配置校验的一个小型 runnable test。

验收：

- 示例项目配置可读取。
- 重复 `chat_id`、未知 Job type、非法路径、非法 cron 被拒绝。
- 不启动 Runner，不产生外部副作用。

### Slice 2：通用 Runner

1. 增加 handler registry。
2. 实现到期计算、数据库锁、超时、运行记录和 cursor 成功提交。
3. 新增独立启动脚本及 systemd user service。
4. 先注册无副作用的测试 handler，验证重启和并发去重。

验收：

- 两个 Runner 实例不会同时执行同一 Job。
- 失败、超时和成功均留下正确记录。
- 重启后继续调度，不重复执行同一计划周期。

### Slice 3：long-file detector 迁移

1. 复用现有算法行为，将其适配为 `long_file_detector` handler。
2. 把阈值、扩展名、排除路径和群绑定移到项目配置。
3. 平台先以 shadow 模式和旧 checker 对比结果。
4. 对比稳定后切 active，再停旧 long-file checker。

验收：

- 固定 ref 下的 offender 集合与旧脚本一致。
- 未变化文件不重复告警。
- active 模式消息发往项目绑定群。
- 平台成为唯一发送者后，旧 checker 才停用。

### Slice 4：workflow watcher 迁移

1. 抽取旧 watcher 的 Git/contract/approval 状态行为为 `workflow_watcher` handler。
2. 所有仓库、ref、合同、群和审批人从项目配置取得。
3. 将旧状态映射为数据库 cursor，保留事件幂等键。
4. shadow 对比 PLAN/HANDOVER 候选、审批状态和下一动作。
5. 单项目切 active，验证完整链路后停 `coding-handover-watcher`。

验收：

- PLAN review、HANDOVER 处理、reset session、Slice Prompt 投递行为与旧 watcher 一致。
- 平台重启不会重复创建审批或重复投递。
- ref rewrite 等异常继续要求人工处理。
- 任一时刻只有一套 watcher 能产生正式副作用。

### Slice 5：飞书管理命令

1. 在实际 `/ap` 路由加入 `jobs` 和 `job`。
2. 接入项目解析、权限、运行态 override 和手动触发。
3. 更新帮助文本并加命令解析/权限/幂等测试。

验收：

- 项目群可查询、启停和手动运行已注册任务。
- 其他群无法跨项目操作。
- 重复 enable/disable 不创建重复调度。
- 命令不能注入路径或 shell。
