# PLAN · 工作流条件触发与完成门简化

## 目标

把 HANDOVER 启动下一 Session 的条件收敛为一个持久事实：

> 目标 Git ref 中出现一份合同校验通过、已提交且 `next_action` 可执行的 HANDOVER。

删除聊天 `WORKFLOW_READY <SHA> <文件名>` 完成门，不再依赖消息发送者、消息类型、
发送时间窗或 pending 建立时锁定的旧 SHA。PLAN 的人工审批门保持不变。

触发采用“完成事件立即唤醒 + 定时低频补偿”：正常路径不再等待十分钟；漏事件、服务
重启或短暂故障时，定时扫描仍可根据 Git 和 cursor 恢复。

## 规模与影响

这是中小改动，不需要重写定时任务平台，也不新增 daemon、消息队列、数据库表或依赖。
预计修改 4—6 个文件：

- `src/lib/scheduled-jobs/workflow-watcher.ts`
- `src/lib/scheduled-jobs/runner.ts`
- 新建一个小型 workflow/live-room 桥接模块
- `src/lib/feishu.ts`（只做迁出，不得净增行数）
- Platform Local TaskRun 统一完成入口所在文件
- `tests/workflow-watcher.test.ts`
- 必要时 `tests/scheduled-job-runner.test.ts`

计划阶段对 `workflowWatcherHandler` 执行的 GitNexus upstream impact 结果为 LOW：
0 个图谱直连调用方、0 个受影响执行流程。实际注册入口是 `jobHandlers`，实施仍须对
最终选定的 TaskRun 完成入口和 runner symbol 重新执行 impact，避免索引未识别动态注册。
`src/lib/feishu.ts` 当前已有 2222 行；其中 `runWorkflowInBoundLiveRoom` 位于该文件，
GitNexus upstream impact 为 LOW（0 个图谱直连调用方、0 个受影响流程），文本调用点为
`workflow-watcher.ts` 的动态导入。实施时先迁出这一现有 workflow 桥接边界，再接新逻辑。

当前工作区已有 watcher、配置、runner 启动脚本等未提交修改。实施时必须先区分并保留，
不得覆盖或把无关修改混入本计划提交。

## 文件边界硬约束

- `src/lib/feishu.ts` 不承载 workflow 条件判断、TaskRun 完成判断、调度、锁或幂等逻辑。
- 先把现有 `runWorkflowInBoundLiveRoom` 迁到独立的小型 workflow/live-room 桥接模块；
  watcher 改为直接依赖该模块，不再动态导入整个 `feishu.ts`。
- 即时唤醒入口放在 `scheduled-jobs` 侧；飞书文件至多调用一个无分支的公共函数，不在其中
  新增流程代码。
- 本计划完成后 `feishu.ts` 行数必须低于当前 2222 行；若无法迁出，就停止 S02，而不是
  把新代码继续塞进去。
- 不为迁出新增 interface、factory、class 或依赖；只移动现有职责和复用现有函数。

## 方案选择

### 为什么不只用十分钟定时任务

单独轮询实现简单、恢复能力好，但用户可见延迟为 0—10 分钟；缩短到每分钟只是在用
更多空扫描换延迟，仍不是条件触发。

### 为什么不新建一套后台常驻 watcher

平台已有常驻 Scheduled Job Runner。再增加文件监听进程会重复生命周期、锁、日志和
恢复机制；目标 ref 还可能由外部进程更新，文件系统事件并不等于目标 Git 条件成立。

### 采用的方式

复用现有 runner 和数据库 advisory lock：

1. Platform Local TaskRun 成功完成时，只发出一次“立即检查 workflow”的唤醒。
2. 唤醒不携带 SHA、不宣称任务已完成，只让 watcher 重新读取目标 ref。
3. watcher 以合同、Git commit、cursor/event key 判断是否启动，事件只是降低延迟。
4. 原定时入口保留为低频 reconciliation，和事件入口调用同一个执行函数、共用锁与幂等。

因此后台常驻与定时任务不是二选一：已有常驻 runner 承载即时唤醒，定时扫描负责补偿；
不再新建第二个常驻进程。

## 实施步骤

### S01：删除 HANDOVER 聊天完成门

1. 对拟修改的函数、类和方法逐一运行 GitNexus upstream impact；HIGH/CRITICAL 先停止
   并告警。
2. `workflowWatcherHandler` 发现可执行 HANDOVER 后，在同一次受锁执行中直接调用现有
   `execute`，成功后推进 cursor/event key。
3. 删除 HANDOVER 的 `workflow_ready` pending、`expectedMarker` 和飞书历史消息匹配；
   PLAN review pending、人工审批、terminal action 和 shadow 行为保持不变。
4. 合同移除仅服务于聊天完成门的 marker 配置，文档说明同步为“Git 条件即完成门”。
5. 增加一个最小回归测试：HANDOVER 提交后单次扫描启动一次；同一 event key 重扫不再
   启动；HANDOVER 后续修订产生新合法事件时按新 commit 判断，不等待旧 SHA。

验收：

- 不发送 `WORKFLOW_READY` 也能启动下一 Session。
- 同一 HANDOVER 不重复启动。
- 未提交文件、合同不合法文档、不可执行 action、automation disabled 和 shadow 均不
  产生副作用。

### S02：接入完成事件即时唤醒

状态：已完成（`b2fc291`）。

1. 先迁出 `feishu.ts` 中现有 `runWorkflowInBoundLiveRoom` 及其最小必要 workflow
   桥接代码，更新 watcher 动态导入和现有测试；不得复制实现，也不得制造循环依赖。
2. 找到 Platform Local TaskRun 持久化 `completed` 的统一服务端入口；若不存在统一
   入口，只接当前 workflow 使用的 Live Room 完成路径，不顺手重构所有 Harness。
3. 将 runner 的“执行指定 workflow watcher”收为一个最小公共入口；事件触发和 cron
   触发共用 `executeScheduledJob` 的 advisory lock、cursor 和幂等逻辑。
4. TaskRun 成功完成后异步唤醒对应 room/project 的 workflow watcher。失败、取消、
   过程消息和普通聊天消息不触发。
5. 事件 key 使用稳定的 TaskRun ID；事件只负责唤醒，最终条件仍由 Git ref 决定。
6. 增加最小测试：完成事件可立即执行检查；事件与定时扫描并发时只产生一次 Session。

验收：

- 正常完成后数秒内开始检查，不等待十分钟调度点。
- Agent 即使没有最终飞书消息，只要 TaskRun 成功完成且 Git 已提交，仍可推进。
- 重复完成事件、服务重启重放和 cron 竞争不会重复启动。
- `feishu.ts` 低于 2222 行，且不包含新增的 workflow 判断、锁、调度或幂等分支。

### S03：保留低频补偿并受控上线

状态：已完成。补齐遗漏的 S01 后，完成事件 shadow 验证通过；active 已受控启用，
由当前 TaskRun 完成事件启动 S04 观察 Session。

1. 定时扫描保留为恢复保险，初始继续使用现有十分钟周期；它不再是正常触发路径。
2. 运行 watcher、Scheduled Job Runner 和完成事件专项测试、TypeScript 检查及
   `git diff --check`。
3. 运行 GitNexus `detect_changes()`，确认只影响预期 watcher、runner、完成事件和测试
   流程。
4. 先 shadow 验证一次“完成事件立即发现 HANDOVER”，再 active 验证一次 Session 启动；
   随后人为跳过一次事件，确认十分钟补偿扫描可恢复。
5. 观察无重复 Run、无 cursor 跳跃、无旧 SHA pending 后，再删除遗留 marker 文档说明。

验收：

- 正常路径延迟由 0—10 分钟降为事件处理时间。
- 漏事件最迟仍由补偿周期恢复。
- 任一重复启动或错误项目唤醒，立即恢复 shadow；不手改 cursor、不启用第二套 watcher。

### S04：上线后观察与补偿验收

1. 核对启动本 Session 的唯一 `task_run_completed` Run、cursor 和 event key，确认没有
   重复 Session、错误项目唤醒或旧 `workflow_ready` pending。
2. 提交一个合同合法、不可执行的 terminal 工作流文档，不发送完成事件，等待下一个
   十分钟周期确认 schedule Run 发现并消费该文档。
3. 再观察一个空闲周期，确认 `candidate=none`、cursor 不跳跃且没有重复副作用。
4. 异常时立即把 runtime override 恢复为 `shadow`；正常则完成 239 PLAN。

验收：

- 当前 TaskRun 完成后只启动一次 S04 Session。
- 漏事件由下一次十分钟扫描恢复。
- 后续空闲周期无重复 Run、无 cursor 跳跃、无旧 SHA pending。

## 回滚与停止条件

- 事件入口无法复用现有数据库锁和 cursor：停止 S02，先保留 S01 + 十分钟补偿，不引入
  内存锁或新队列。
- 找不到可靠的“TaskRun 已成功完成”服务端事实：不以飞书消息到达代替；先保持定时补偿。
- PLAN 审批、terminal action 或 shadow 行为出现变化：停止上线并恢复原 active 配置。
- 不提交当前工作区既有无关修改，除非逐项确认归属和验证结果。
