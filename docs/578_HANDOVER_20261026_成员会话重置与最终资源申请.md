## 单元二：有效成员重置

- `conversation-reset.ts` 按房间成员的角色、harness、backend 和 agent 身份寻找最近适用重置。
  新记录保存实际成员 ID 列表，兼容旧 targetMemberId/全员记录；重置其他角色不会覆盖本角色的有效边界。
- 实施消息寻址和 implementationConversation 复用该边界。首次不携带旧 resumeSessionId，随后读取新平台 Session 内的原生 ID；
  启动失败只在该边界内重试，不回退到重置前的原生上下文。
- 验收/架构卡回复保留原任务和固定候选；按重置、角色及候选派生独立平台 Session，避免把不同候选混入同一新会话。
  既有候选、原日志和隔离工作区不清空，不修改业务验收和交付算法。
- 重置前已捕获的输入产生幂等取消回执。新发的旧卡回复使用新边界；旧消息不能悄悄补投到新会话。
  原本投递结果未知的 steering 仍遵守旧回执规则，不重复投递。
- TaskSession 轮换与 TaskRun 创建使用相同 Task 行锁；启动绑定再次检查重置。
  图房间先保存未完成重置边界，再停止旧运行。边界未完成时拒绝新启动，不允许旧 ID 复活。
- 中断识别扩展到该图节点的原实施者和复核者，核对完整角色身份，不能因为同是 Codex 就串线。
  中断前捕获 writer，信号发送后继续核验实际退出；无法证明退出则保留未完成重置，不宣称成功。
- 同房间重置回调用数据库 advisory lock 串行化，rotationKey 在轮换事务内去重。
  已完成回调直接返回，不再次杀进程、清空新 thread 或覆盖后来改变的权限。

## 单元三：最终申请进入现有资源通路

- `AgentProtocolOutput` 单独聚合按消息 ID 标识的协议输入，支持 append/replace；不会借用卡片显示回退文本。
  阶段明确时只选唯一 final_answer。只有 commentary、未知阶段、多个 final 或最终阶段被改为未知时不推断申请。
  未提供消息阶段的适配器保留原整份输出合同。
- runner 继续转发原过程播报与最终消息；成功返回后把选定最终消息作为 protocolOutput 送入 submitRunnerResourceRequest。
  错误返回不触发最终申请。资源解析器的整消息约束保持，正文里的示例、引用和代码围栏不会触发。
- 复用现有资源申请、审批卡身份、授权应用与原会话接续。没有新审批层，没有改写批准规则或把自动接话当作批准。
  本轮不迁移 S05 的完整工具事件协议。

## 遇到的问题及保留项

1. 交互回归原断言固定三次 conversation 调度，但旧材料条件恢复可能先派发其中一次；追踪确认三条消息均直接绑定原实施者。
   测试改为先显式调用 conversation admission，并等到等待态，再核对该通路。未修改条件恢复或候选算法。
2. 新重置检查一度要求未重置历史任务具备新版启动配置，approved-continuation 报错；现仅在确有重置时解析该配置，回归通过。
3. 资源测试最初把批准/应用时更新同一张卡也算成新申请；现分别检查初次一次发布和后续同一申请 ID，并保留实际挂载验证。
4. 577 已记录的旧 task-graph-conversation 验收流基线失败、全目录 tsc 的忽略 output 历史夹具错误仍未处理；本轮没有宣称修复或全仓全套件通过。
5. 首轮停止夹具尝试调用飞书回传时因缺少 FEISHU_APP_ID 报错，未发送消息；已把夹具改为本地消息替身，后续回归通过。
6. 扩展运行 `tests/task-graph-reply-summary.test.ts` 在第 16 行失败：旧断言期待首段含批准说明，实际为“正在查原因”。
   已在 `.cache/unit-one-baseline` 的 `8861157` 原基线复现完全相同失败；本轮未修改该测试和 run-reply-card 实现，保留为既有卡片断言问题。
