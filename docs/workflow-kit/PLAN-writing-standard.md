# PLAN 写作与 Slice 划分规范

本文件是 workflow-kit 的跨仓规范源。目标仓库同步后由
`docs/workflow/workflow-contract.yaml` 的 `standards.plan` 引用；项目内的历史 DECISION
可以解释来历，但不得覆盖本规范。

## 1. PLAN 要解决什么问题

PLAN 不是函数清单，也不是把需求换成技术名词。它必须让不了解实现细节的人判断：

1. 最终要得到什么结果；
2. 当前为什么做不到；
3. 为什么按这个顺序推进；
4. 每一步如何实现、解决哪个问题；
5. 每一步是否能在一个 Session 内完成并独立验收；
6. 做到哪一步时，用户已经能看到或验证什么。

写作目标是可执行、可验证、可接力。无法用普通业务语言解释的术语，应删除或在首次出现时说明。

## 2. PLAN 的两种尺度

同一仓库可以同时存在多份 PLAN，但每份只能选择一种尺度：

| 尺度 | 适用情况 | 正文重点 |
| --- | --- | --- |
| Phase PLAN | 目标跨越多个能力阶段，需要先说明完整路线 | 阶段依赖、阶段结果、本 PLAN 覆盖边界；执行部分仍拆成可交付 Slice |
| Slice PLAN | 目标已经收敛，可直接拆成一个或少量 Session | 每个 Slice 的实现链路、修改边界和验收 |

大目标不应塞进一份超长 PLAN；用 Roadmap 或 Phase PLAN 管路线，每个可实施阶段另立 PLAN。
小目标也不必机械拆成多份文档：一个 Session 能理解、修改、验证、提交并交接时，一份 Slice PLAN 足够。

## 3. PLAN 必须按故事线展开

每份 PLAN 必须依次回答六层问题，不能直接从函数名或 S01 开始：

1. **总体目标**：最终用户要完成什么，用一句非技术语言说明。
2. **当前障碍**：现在为什么做不到，只列已确认事实，猜测必须标注。
3. **总体路线图**：从当前状态到目标经过哪些阶段，本 PLAN 负责哪一段。
4. **本 PLAN 结果**：全部完成后，用户、调用方或运维人员实际能看到什么。
5. **Slice 路线**：每个 Slice 如何承接上一步，又为下一步提供什么。
6. **验收与退出**：怎样证明完成；失败时停在哪里；明确哪些事情不做。

推荐使用最小路线表：

| 阶段 | 解决的问题 | 交付结果 | 是否属于本 PLAN |
| --- | --- | --- | --- |
| A | 为什么先做 A | A 完成后可验证的结果 | 是/否 |

## 4. 每个 Slice 的强制内容

每个 Slice 必须完整写出以下七项，缺一项不能申请审批：

| 项目 | 必须回答的问题 |
| --- | --- |
| 目的 | 为什么需要这一步；消除哪个障碍或风险 |
| 完成后结果 | 用户或下一层调用方能看到、拿到或验证什么 |
| 实现方法 | 修改哪条现有链路，复用什么，数据怎样从输入走到输出 |
| 修改边界 | 预计涉及哪些生产/测试文件；明确不碰什么 |
| 验收 | 哪些自动测试、合同断言或人工检查能证明完成 |
| 前置与停止条件 | 依赖什么；什么情况必须停止，不能扩大范围 |
| 交付物 | 一个提交、一份 HANDOVER，以及必要的测试或报告 |

若 Slice 只有内部结果、用户暂时看不到，必须解释它为何不能与下一步安全合并，以及独立验收降低了什么风险。

## 5. 一个 Session 的工作量规则

默认一个 Slice 必须能由一个 Agent 在一个 Session 内完成理解、修改、验证、HANDOVER 和提交。

- 一个 Slice 只有一个主要结果和一个主要失败原因；
- 默认只跨一个工程边界，例如算法、HTTP、UI、数据库迁移四者选一；
- 默认只改一组紧邻的生产代码和直接测试，通常不超过 2 个生产文件与 2 个测试文件；
- 必须不依赖下一个 Slice 也能运行本 Slice 的验收；
- 每个 Slice 只提交本 Slice，创建 HANDOVER，然后停止；
- 算法、HTTP、UI、数据库不得一次塞进同一个 Slice；跨仓工作默认分仓立 PLAN。

文件数量是预警线，不是机械目标。超过时必须解释为什么仍可在一个 Session 收口；无法解释就继续拆分。
也不能为满足数量，把一个原子修改拆成不可运行或不可验证的半成品。

## 6. 按可验证结果切 Slice

正确的切法是每一步产生一个可验证能力：

```text
总体目标
  -> 能力 A：建立可靠的核心结果
  -> 能力 B：接入真实调用入口
  -> 能力 C：提供用户操作与确认
  -> 能力 D：保存结果或进入生产流程
```

“改 util”“改 service”“补测试”是实现动作，不是 Slice 目的。测试归入对应能力，不单独堆到最后。

## 7. 状态、审批与并存规则

- 可评审 PLAN 使用 `doc_status: ready`，根据用户是否明确要求提审选择 `next_action`：
  - “先写 PLAN”“备选方案”或未明确提审：使用 `await_approval`，留在候选清单，不自动发审批卡；
  - “写好后提审”：使用 `start_first_slice`，提交后由 watcher 建立审批 pending 并发卡，批准前不实施；
- 不根据候选数量推断提审意图；默认模板继续使用 `await_approval`；
- “把刚才那个 PLAN 提审”：从当前对话确定唯一文档；有歧义时先明确目标。将该 PLAN 的动作改为
  `start_first_slice`，校验并单独提交，复用现有 watcher 审批流程，不要求用户再打开 Dashboard；
- 用户也可从 Dashboard 选择候选并点击“提交审批”，或使用指南中的已有 `job activate` 命令；
- 提审前确认目标监控 ref、watcher 启用状态及当前 pending；已有审批或实施任务时先处理当前任务，
  不为提审清空 pending、移动 cursor 或自动启用 watcher；多个候选需要指定提审时优先使用选择入口；
- 人工批准后，平台在持久 cursor 中把动作原子转换为 `start_first_slice`，只派发第一个 Slice；
- 修改、拒绝或审批超时都不得启动 Slice；
- 每完成一个 Slice：运行项目门禁，创建 HANDOVER，提交后停止；
- PLAN 全部完成后使用 `completed / none`；
- PLAN 创建或修订必须单独提交，不得夹带既有业务代码。

审批只改变平台运行状态，不回写或改写已被 watcher 读取的 Git 历史。

## 8. 申请审批前检查表

- [ ] 开头用非技术语言写清最终结果；
- [ ] 有从总体目标到本 PLAN、再到各 Slice 的路线图；
- [ ] 已明确属于 Phase PLAN 还是 Slice PLAN；
- [ ] 每个 Slice 都有目的、结果、实现、边界、验收、停止条件和交付物；
- [ ] 每个 Slice 默认可在一个 Session 内完成；例外已有理由；
- [ ] 相邻 Slice 能按“上一步产出 -> 下一步输入”读通；
- [ ] 示例覆盖真实范围，没有用单一样例冒充通用能力；
- [ ] scope out、风险和 breaking change 已显式说明；
- [ ] frontmatter 是 `ready`，动作按用户意图选择 `await_approval`（候选）或 `start_first_slice`（提审），Prompt 只指向首个 Slice；
- [ ] PLAN 修订已经提交，暂存区不含无关文件。
