# PLAN 写作与 Slice 划分规范

本规范在平台仓库的 `docs/workflow/` 与可分发的 `docs/workflow-kit/` 保持同步。
目标仓库通过合同的 `standards.plan` 引用本地副本。规划原则也适用于 Spec/ticket；
文档类型、审批及接续动作仍由各项目已选定的流程决定，不因采用本规范切换调度方式。

## 1. 先确定路线，临近实施再细化

初始计划必须让读者判断最终结果、当前障碍、路线选择及完成标准。
远期实现存在未知，不要求提前写完所有 Slice 的文件清单、函数设计或精确测试命令。
将已确认事实、待验证假设和初步设想分开记录，不把猜测写成承诺。

规划分三层，内容不重复维护：

| 层次 | 必须明确 | 细化时机 |
| --- | --- | --- |
| 路线计划 | 目标、非目标、架构方向、关键假设与论证、阶段结果、整体验收标准 | 启动前 |
| 初步 Slice / ticket | 要解决的问题、可验证结果、范围边界、预计依赖和未决问题 | 初定路线时 |
| 当前 Slice 实施方案 | 最新现场、具体实现、修改边界、验证办法与停止条件 | 该片真正实施前 |

PLAN 解释整体为什么这样走，票定义一块可交付结果，当前实施方案说明准备怎么做。
只有一片的小任务可以合并在一份简短计划中，不为满足层次额外制造文档。

## 2. 路线先有依据

路线论证优先验证最可能推翻方案的假设，按风险决定深度：

- 核对相关源码、真实接口、环境和输入，标明证据来源与适用版本；
- 对关键未知，用最小实验或原型打通关键链路，记录实际结果；
- 说明选择该路线的理由；存在实质取舍时简述替代方案及代价；
- 写明假设被什么现象推翻，以及需要调整路线或停止的条件。

已有充分证据时可直接引用，不重复做原型。尚未验证且足以决定方向的问题，应先安排探查，
其结果用于选择后续路线；不能把待探查的结论当成已确认事实。
论证支持当前选择，不保证所有远期细节永远成立。

## 3. 初始计划的内容

初始计划按以下顺序说明，篇幅以足够作决定为准：

1. **目标与非目标**：最终用户结果、整体验收标准、明确不做的事项。
2. **现场与路线依据**：已确认障碍、关键假设、证据和待验证问题。
3. **总体路线**：阶段结果、顺序理由、预计依赖及本计划覆盖范围。
4. **初步切片**：每片的目的、可验证结果、边界、前置和未决问题。
5. **调整与退出**：哪些证据会改变路线，如何保留已完成结果并报告变化。

推荐路线表：

| Slice | 解决的问题 / 可验证结果 | 范围边界 | 预计前置 | 未决问题 |
| --- | --- | --- | --- | --- |
| S01 | 本片结束能证明什么 | 负责与不负责什么 | 所需输入 | 实施前需确认什么 |

初始评审不以远期实现细节是否齐全为条件。验收标准描述要证明的行为和质量，
具体命令、测试数据与修改文件在当前片实施方案中确定；不能以尚未确定命令为由省略完成标准。

## 4. 当前 Slice 开始前

实施者先读取最新代码、前置交付与验证证据，核对本片是否仍有必要、前置是否满足，
再记录以下内容后编码：

- 本片目标、授权边界与需保留的行为；
- 最新事实及相对初始设想的变化；
- 当前采用的实现链路、复用点和预计修改范围；
- 用什么真实行为、测试或读回证明完成，以及失败或假设失效时如何停止。

方案可写在当前票、执行记录或项目现有计划的当前片说明中，不强制新建文件、增加 Agent
或另开审批阶段。原目标、授权与验收要求内的实现细化可直接推进；涉及第 6 节的路线变更时，
按既有流程处理。遇到新证据及时更新当前方案，不为服从过时猜测继续实施。

## 5. 按可验证结果切片

每片围绕一个清楚的可交付结果，规模以能理解、实现、验证和交付为准。
测试属于该结果，不集中拖到路线末尾。

- 允许为一个完整结果贯通必要的算法、接口、存储和 UI；涉及多个仓库时明确各仓职责与授权；
- 不按固定文件数量、技术层或 Session 数机械切片，不拆成不能运行、不能验证的半成品；
- 只有内部结果的片，说明其独立验证价值及为何不与相邻片合并；
- 项目若采用每 Session 一片，按该预算控制范围；做不完就如实保留进度，不能伪造完成；
- 后续细化可提出拆分、合并或依赖调整建议，但未生效的建议不能当成已获批路线执行。

## 6. 每片结束后的复盘与变更边界

交付时记录实际结果、验证证据、假设变化和对后续 Slice 的影响。
下一片的输入是批准目标加最新交付事实；不只照抄最初设想，也不提前替下一片写死实现。

| 变化 | 处理方式 |
| --- | --- |
| 原目标、权限和验收要求内的实现细化 | 在当前执行记录说明依据并实施，不重复申请路线审批 |
| 关键假设失效、改变目标、扩大权限、降低验收要求、拆并票或改变依赖 | 报告影响并提出路线修订，按该项目既有授权 / 确认流程生效后再执行受影响部分 |

保留原批准快照及已完成证据，不改写历史、不用新方案冒充旧验收。
任务图的当前实施方案记入执行记录，不回改冻结的 Spec / ticket；本规范不新增动态改图能力。
PLAN/HANDOVER 流程按既有合同引用真实存在的下一片；路线修订未生效时不能假装已完成并自动放行。

## 7. 状态、审批与并存规则

以下仅适用于项目已选用的 PLAN/HANDOVER 接续；任务图与手动执行继续遵循各自授权规则。

- 可评审 PLAN 使用 `doc_status: ready`，根据用户是否明确要求提审选择 `next_action`：
  - “先写 PLAN”“备选方案”或未明确提审：使用 `await_approval`，留在候选清单，不自动发审批卡；
  - “写好后提审”：使用 `start_first_slice`，提交后由 watcher 建立审批 pending 并发卡，批准前不实施；
- 不根据候选数量推断提审意图；默认模板继续使用 `await_approval`；
- “把刚才那个 PLAN 提审”：从当前对话确定唯一文档；有歧义时先明确目标。将该 PLAN 的动作改为
  `start_first_slice`，校验并单独提交，复用现有 watcher 审批流程，不要求用户再打开 Dashboard；
- 用户也可从 Dashboard 选择候选并点击“提交审批”，或使用指南中的已有 `job activate` 命令；
- 提审前确认目标监控 ref、watcher 启用状态及当前 pending；已有审批或实施任务时先处理当前任务，
  不为提审清空 pending、移动 cursor 或自动启用 watcher；多个候选需要指定提审时优先使用选择入口；
- 人工批准后，平台在持久 cursor 中把动作原子转换为 `start_first_slice`，只派发第一个 Slice；
- 修改、拒绝或审批超时都不得启动 Slice；
- 每完成一个 Slice：运行项目门禁，创建 HANDOVER，提交后停止；
- PLAN 全部完成后使用 `completed / none`；
- PLAN 创建或修订必须单独提交，不得夹带既有业务代码。

审批只改变平台运行状态，不回写或改写已被 watcher 读取的 Git 历史。

## 8. 初始评审检查表

- [ ] 目标、非目标与整体验收标准清楚；
- [ ] 路线选择有事实或实验依据，关键未知和推翻条件明确；
- [ ] 初步 Slice 各自有可验证结果、边界、预计前置和未决问题；
- [ ] 未把远期文件、函数或测试命令的猜测写成硬约束；
- [ ] 明确当前片实施前细化、每片交付后复盘的责任；
- [ ] 实现细化与路线变更的边界明确，不扩大既有授权；
- [ ] 文档类型、frontmatter 和接续动作符合该项目已选定流程。
