# 067_HANDOVER_20260812_热流道多排扩展与EST模板兜底召回

## 1. 背景

主仓 049/061 热流道线已验收 PASS（Z023 单排 6 通道），但现场陆续出现两类召回缺口：

1. **多排温控箱**：龙昌兴/YUDO 12 通道双排面板（每排 6 通道，上排 1~6、下排 7~12），
   原提取器只取首行 SV 行，下半排丢值；
2. **EST 整族 unknown 误拒**：EST 仅有 `est.injection_metering.json` 模板，
   `detect_family_from_templates` 早期 glob 写死 `*.temperature.json`，EST 永远走不到
   模板指纹兜底；同时部分 EST 照片 OCR 漏读"转保压方式/终止位置"标签导致组1 不命中；
3. **数码管面板 CLAHE 漏检**：PaddleOCR 默认对低对比数码管下行 SV 漏识别，
   `recognize_image` 分类失败时无召回变体；
4. **039_FIX 响应缺字段**：模板指纹兜底解析出的 `controller_family`/`page_type`
   未透出，Web 门禁拿不到家族信息误杀。

## 2. 变更内容

### 1) 契约 v2.7.0（`contracts/field_catalog.json`）

- 新增字段 `hot_runner_sv_c`（list[float]，°C，tolerance 0.5）——温控箱数码管
  面板 SV 设定值数组，多排面板按 y 排序拼接，黑屏通道 null，PV 实时值不入；
- 新增 Web 目标规则 `hot_runner_zone_temperature_set`——非 null 通道按面板顺序
  写入 `hot_runner_zones[*].set_temperature_c`，数量须一致；
- minor bump（2.6.0 → 2.7.0），向后兼容，字段集合与既有语义不变。

### 2) 热流道多排扩展（`scripts/extract_families/tact_hot_runner.py`）

- 重构为"按排拼接"：先按模板 `token_y_max` 过滤候选，按 y 聚行后判 SV 行；
- SV 行判别改为：含 `c/SV` 字母前缀或 `c3xx->23xx` 误识标记的行优先，标记覆盖
  全部模块排则采用；否则按位置兜底——每个模块排上 PV 下 SV，偶数行取 `rows[1::2]`；
- 抽出 `_row_slots(row, cands, n_ch)` 复用单排槽位分配（最优化槽距步长拟合 +
  本行 y 带近邻插补，跨行不补防 PV 污染）；输出 sv_c = 排数×channels 拼接。
- `_is_sv_token()`：识别 `c250/SV255.0/s255.0/W2550` 等字母前缀，区分 PV（纯数字）。

### 3) 模板与 profile 登记

- `templates/tact.hot_runner_temp.json`：新增 `token_y_max=0.85`（双排放宽，
  单排保留 0.40 默认）、`layout_variant=digital_sv`；`family_detect_groups`
  改单组 OR（龙昌兴/YUDO/HOT RUNNER/CW301 任一命中）；source/description 补
  多排扩展说明。
- `scripts/contract.py`：`_resolve_layout_variant` 对 `hot_runner_temp`/`mold_temp`
  页查模板 `layout_variant` 键（新增 `_template_layout_variant` lru_cache）。
- `contracts/profiles.json`：登记 `tact.hot_runner_temp.digital_sv`（candidate），
  证据：6 份自动整批接受真值（hr_Z023 rank01-06）+ 龙昌兴/YUDO 12 通道双排实拍。

### 4) CLAHE 召回变体（`scripts/ocr_variants.py` + `hmi_service.py`）

- `generate_clahe_sidecar(ocr, png_path, out_path)`：与 `ocr_one.py --clahe-output`
  同参数（clip 3.0, tile 8x8），生成 CLAHE 变体 OCR sidecar；
- `recognize_image` 在分类器返回 `ui_family ∈ {"", "unknown"}` 时生成
  `{stem}.ocr_clahe.json` sidecar（热流道温控箱等数码管面板补召回），
  失败仅 warning 不影响主路径；
- 同步透出 `controller_family`/`page_type`（039_FIX）：模板指纹兜底解析出的
  家族/页面必须出现在响应里，否则 Web 门禁只剩 unknown 误杀。

### 5) EST 兜底召回（`templates/est.injection_metering.json` + `scripts/extract_fields.py`）

- `family_detect_groups` 组1 追加"保压位置"——部分照片 OCR 漏读"转保压方式/
  终止位置"标签时仍可命中（EST1 实测），组2（输入值范围 290.0）继续承担与
  KEBA 的区分；
- `detect_family_from_templates` glob 从 `*.temperature.json` 放宽到 `*.json`，
  EST 等只有注射页模板的家族此前永远无法走该兜底；各组按模板文件名序取先命中者。
- 模板 JSON 同时格式化为多行（缩进规范化），无语义变更。

## 3. 验证

- `pytest tests/`：80 passed；`test_demag_stage_enabled`/`test_ocr_variants`
  预置问题（系统 Python 缺 cv2）与本次改动无关。
- 热流道双排：ground_truth/hot_runner 龙昌兴/YUDO 实拍各 1 张，模板指纹路由
  PASS，sv_c 长度 12 与通道数一致；hr_Z023 单排 6 通道回归无 diff。
- EST：bole_est 注射页经模板指纹兜底路由成功（classify 关键词表之外），
  `family_detect_groups` 命中，响应 `controller_family=EST` 透明透出。

## 4. 遗留事项

- 热流道 profile 仅 `candidate`（双排样本仅 2 张），晋级 verified 需契约真值
  门禁（holdout ≥5）或所有者豁免；
- CLAHE sidecar 与 moire sidecar 均为召回补充，未做端到端 UI 实测（仅提取器
  层验证），后续应补 Web 主仓回灌验证；
- EST 温度设定页仍无模板（EST 青绿 UI，2 张照片已盘点），下一迭代。

## 5. 对主线的影响

不阻塞当前 Phase。热流道线 Z023 单排 PASS 状态保持，多排扩展是能力增强；
EST 模板兜底召回修复的是 049 S9 之后现场反馈的整族误拒；CLAHE 召回 + 039_FIX
响应字段补齐是数码管面板通用兜底基础设施。
