# HANDOVER · S02交付：任务话题输入、输出与控制打通

## 完成范围

按 466 PLAN 顺序仅实施 S02；S03（管理员开关与任务创建入口）未启动，任务隔离仍默认关闭，未向普通用户开放任何创建入口。S01 的 `resolveFeishuTaskConversation` 成为所有输入/控制通道的唯一归属入口。

- 事件解析：`parseWsIncomingMessage` 按 `im.message.receive_v1` 契约提取 `thread_id` / `root_id` / `parent_id`（三个独立字段，互不转换），经 `buildFeishuTopicIdentity` 进入普通消息、命令与水位警告的全部 `FeishuConversationContext`。
- 共享解析：`resolveFeishuConversationTarget`（`feishu-live-room.ts`）统一收口。群消息带话题标识时必须经 S01 解析器：task 命中返回房间，unknown_topic / archived_task 抛出带明确文案的拒绝；无话题标识或 p2p 走原 scopeKey 原始查询，旧行为逐字节保持（mock 型旧测试不受影响）。
- 接线消费方：`getBoundLiveRoomId` / `getBoundLiveRoom` / `getBoundSourceTaskId` / `setFeishuBoundRoomMode` / `postFeishuMessageToBoundLiveRoom` / `tryRelayNonCommandToLiveRoom` / `ensureFeishuConversationBinding` 全部改为先走共享解析器；`/ap stop`、`/ap new-session`、`/ap add`、`/ap chat`、approve/answer 等经上述入口自动获得话题范围。
- `/ap room` 话题守卫：话题内返回已绑定任务房间提示或 unknown/archived 文案，绝不创建或改写群级绑定。
- 卡片映射校验：`isFeishuRoomBoundToChat` 以持久化绑定证明 room↔chat（任务行须匹配当前 `FEISHU_APP_ID`，legacy 行 appId 为 NULL 仅当前 app 可读）；handoff-plan 卡片先同步校验再放行，伪造跨房卡片直接拒绝。approve/deny/answer 交互卡按服务端 pending requestId 解析，无客户端 room 输入，无伪造面。
- 会话隔离分析：同 Agent 在两房间是两条 `LiveRoomMember` + 两个 `sourceTask`；`ensureMemberSession(roomId, member)` 与 `findLatestParticipantSession(taskId, participant)` 均按 room/task 键隔离，续聊恢复不会串房。

## SDK 契约与回复通道

以本地官方 SDK 类型为唯一依据（未做真实群实测）：`im.message.receive_v1` 的 message 含 `root_id` / `parent_id` / `thread_id`；`im.v1.message.reply`（`POST /im/v1/messages/{message_id}/reply`）支持 `reply_in_thread` 并返回 chat/root/thread；create-message API 的 `receive_id_type` 合法值包含 `thread_id`，且 create body 没有 `reply_id` 字段——旧代码传给 create 的 `replyId` 从未真正生效（发送侧无操作）。因此：

- 直接应答（命令回复、话题拒绝提示、修订反馈回执）改用真正的 reply 接口，天然落在原话题；reply 失败且消息带话题标识时只记录错误，绝不降级为群根广播；无话题消息失败时回落 plain send（与旧目的地一致）。
- 房间输出（assistant 卡片、图片、系统文本）与进度/最终卡按绑定行 `threadId` 以 `receive_id_type=thread_id` 定向发送；交互卡失败回落文本也发到同一 thread；thread 发送整体失败仅记录，禁止群广播。

## 通道覆盖与验收证据

新增 `tests/feishu-task-thread-loop.test.ts`（真实 PostgreSQL 独立随机 schema，从 baseline 起执行全部迁移，结束删除自身 schema）预置同群 A/B 双任务绑定后验证：

- 输入：A/B 消息各入各房，A 私有标记绝不出现于 B 上下文（反之亦然）；消息 metadata 记录所属 binding id；同一 messageId 重放不产生第二条帖子（事件重放）。
- 输出：A/B assistant 卡片分别进 thread-A / thread-B（thread_id），无任何 `chat_id` 群广播。
- 进度卡/最终卡：`attachLiveRoomProgress` 优先按消息 metadata 的 binding 定位（跨房伪造 binding id 被忽略并回落房间绑定）；卡片与 finalize 失败重试均留在原 thread。
- 控制：stop 分别命中 A/B 房间成员且互不提及对方；new-session、add 流程经共享解析器定位各自房间；`/ap room` 话题守卫不新建房间。
- 拒绝：unknown thread（含 parent=thread 伪装）与归档任务分别返回专属错误；A 正常工作不受 B 归档影响。
- 卡片：`isFeishuRoomBoundToChat` 跨群伪造返回 false，legacy 行仍可被当前 app 校验通过。
- 回归：旧群（无话题标识）与 DM 路由、未绑定提示行为不变；`tests/feishu-live-room-relay.test.ts` 扩展 thread 目标、失败回落与“无群广播”断言；`tests/live-room-handoff-plan.test.ts` 改为 mock 新的服务端映射校验并新增伪造跨房拒绝断言。
