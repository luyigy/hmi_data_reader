# 资源授权提示与卡片结果同步

## 问题与证据

用户在 Feishu DM 08a216 要求修复：群 `oc_5c8067219168958335bfc59d5fbb2b11`
的 Codex 申请仓库外两个只读目录，回复显示申请 JSON，却没有可点击审批卡。

只读核查发现，运行 `cmvtc4vjl04kpemz30qtf5qmf` 已配置
`full_access / danger-full-access`。后端识别了完整 resource-request，
按既有 Full Access 策略返回“所申请目录已在当前授权范围内，无须重复申请”，未创建待审批记录。
但最终飞书卡 `om_x100b610548f374b4b0b4af8a247522f` 仍使用流式原生 final 中的 JSON，
没有反映平台处理结果。下一轮 Agent 又将该申请解释成等待授权。

原因是所有 Codex 均注入同一份申请提示，未明确当前 Full Access；另外资源处理只改写
Runner 返回文本，卡片展示优先使用独立 final_answer，二者未同步。
真正缺权限时已有补充授权卡，包含“批准并继续／调整范围／拒绝”，无需新建审批系统。

## 实现

隔离分支 `fix/resource-request-feedback-20261029`，基线 `f3d114a`，工作区
`output/worktrees/resource-request-feedback-20261029`。

- 根据当前实际 permissionConfig 注入资源提示。Full Access 明确不要仅因目录在仓库外而申请，
  已覆盖的申请无需等待卡片；用户任务范围、只读输入及受控资源限制仍须遵守。
  受限权限继续使用原来的结构化申请协议。
- 资源申请被平台处理后，通过可选 onResolved 回调返回用户可读结果。
  本地 Harness 以相同 final message ID、replace 操作同步展示；旧版无分段输出使用独立平台结果 ID。
  因此最终卡片显示“已有权限”或“申请已提交”，而非原始请求 JSON。
- AgentProtocolOutput 暴露唯一 final 的 ID 和正文。仍要求唯一 final，保留多 final、
  未知 phase、commentary、引用示例不能触发动作的原有契约。
- 不修改管理员权限判断、目录覆盖逻辑、审批按钮、原生 Session 续接或卡片 terminal 防护。
  补充资源审批仍由真人决定。本轮未补造审批、修改历史卡片或触发其他聊天室的业务运行。
