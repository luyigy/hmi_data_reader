# 84 房间消息三层可见性与 per-agent 会话隔离设计

## 日期

2026-04-04

## 概述

本文档是 `/ap new-session` 行为讨论的延续（详见 83 号文档），聚焦于**消息可见性模型**的设计。核心问题：

1. 当前房间消息是否在 agent 间共享？
2. 如何平衡"协作共享"与"上下文爆炸"？
3. 三层可见性模型如何与 `new-session` 的 per-agent / task-global 两种重置模式配合？

## 当前状态：名义上有 targetType，实际上全量共享

### Message 模型已有的字段

```prisma
model Message {
  targetType            String?   // 'task' | 'participant' | 'all'
  targetParticipantKey  String?   // 如 'deepseek', 'claude'
  targetParticipantLabel String?  // 显示名
  ...
}
```

### 实际过滤逻辑

`src/lib/task-room.ts` 中的 `shouldIncludeTaskRoomPromptMessage`：

```typescript
const shouldIncludeTaskRoomPromptMessage = (msg: Message) => {
  // 只过滤系统/内部消息，不过滤 targetType
  if (msg.type === 'system' || msg.type === 'internal') return false;
  return true;
};
```

`buildTaskRoomPromptContext` 完全不接受 `participantKey` 参数，也不按 target 过滤。

### 结论：当前所有 agent 看到完全相同的房间上下文

无论消息是定向发给 deepseek、claude 还是 room 全体，所有 agent 的 prompt 里都会包含它。`targetType` 字段已存在但未被上下文构建逻辑使用。

## 问题分析：全部共享 vs 完全隔离

### 全部共享（当前实现）

| 优点 | 缺点 |
|------|------|
| 实现简单，无需 per-agent 过滤逻辑 | 上下文极易膨胀（N 个 agent × M 条对话 = N×M 条消息涌入每个 agent） |
| agent 可以看到其他 agent 的讨论，利于"多视角协作" | 与用户直觉冲突——用户对 deepseek 私聊的内容，claude 不应该看到 |
| 心智模型统一：房间 = 一个共享频道 | `new-session "deepseek"` 想要精准重置，但做不到 |

### 完全隔离（每个 agent 只看自己的）

| 优点 | 缺点 |
|------|------|
| 上下文精准可控 | 失去多 agent 协作感——agent 之间完全不可见 |
| `new-session` per-agent 自然成立 | 用户对房间说的全局指令、任务目标，需要额外广播机制 |
| 隐私明确 | 架构上等同于"多个独立 chat room 拼在一起"，失去 Live Room 的联合空间语义 |

### 折中：三层可见性模型

不在"全部共享"和"完全隔离"之间二选一，而是为每条消息显式指定可见性层级。

## 设计方案：三层可见性

### 层级定义

| 层级 | targetType | 可见范围 | 典型用途 |
|------|-----------|----------|----------|
| **房间公告** | `room` 或 `all` | 所有 agent | 用户指令、任务目标、房间状态变更、`new-session` 全局重置通知 |
| **Agent 定向** | `participant` | 仅目标 agent | 用户对特定 agent 的追问/纠错、手递手、私密指令 |
| **Agent 间对话** | `participant` + `senderKey` | 目标 agent + 发送者自己 | agent A 问 agent B 的问题、agent 间协作 |

### 消息发送规则

```
用户 → agent (公开指令)      → targetType: 'room'
用户 → agent (私密纠错)      → targetType: 'participant', targetKey: 'deepseek'
agent → agent (协作提问)     → targetType: 'participant', targetKey: 'claude', senderKey: 'deepseek'
系统事件 (new-session)       → targetType: 'room' 或 'participant'（取决于全局/per-agent）
```

### 上下文构建逻辑（改造后的 `buildTaskRoomPromptContext`）

```typescript
const buildTaskRoomPromptContext = async (
  taskId: string,
  taskName: string,
  participantKey: string,  // ← 新增参数
) => {
  const allMessages = await getTaskRoomMessages(taskId);
  const afterReset = sliceMessagesAfterLatestSessionReset(allMessages, participantKey);

  const visibleMessages = afterReset.filter(msg => {
    // 1. 房间公告：所有人可见
    if (msg.targetType === 'room' || msg.targetType === 'all') return true;

    // 2. Agent 定向：只有目标可见
    if (msg.targetType === 'participant' && msg.targetParticipantKey === participantKey) return true;

    // 3. Agent 间对话：目标 + 发送者可见
    if (msg.targetType === 'participant' && msg.senderKey === participantKey) return true;

    // 4. 其他：不可见
    return false;
  });

  return formatTaskRoomContext(visibleMessages, taskName);
};
```

### agent 视角示例

假设房间内有 deepseek 和 claude，消息序列如下：

| # | 发送者 | 内容 | targetType | 目标 | deepseek 看到? | claude 看到? |
|---|--------|------|-----------|------|---------------|-------------|
| 1 | 用户 | "今天的任务是重构 auth 模块" | room | - | ✅ | ✅ |
| 2 | 用户 | "deepseek 你先看 schema" | participant | deepseek | ✅ | ❌ |
| 3 | claude | "deepseek 你那边 db 连上了吗？" | participant | deepseek | ✅ | ✅ (发送者) |
| 4 | 用户 | "claude 你写测试" | participant | claude | ❌ | ✅ |
| 5 | 系统 | "new-session deepseek" | participant | deepseek | ✅ (reset point) | ❌ (不受影响) |

- **deepseek** 看到：1, 2, 3（但 3 之后被 reset 切掉，仅保留 5 之后的新对话）
- **claude** 看到：1, 3, 4（完全不受 deepseek 的 reset 影响）

## 与 `new-session` 的配合

此设计与 83 号文档中建议的"两层操作"完全匹配：

| 命令 | 行为 | 受影响的消息 |
|------|------|-------------|
| `/ap new-session`（无参数） | 全局重置：所有 agent 上下文清空 | 插入 `targetType: 'room'` 的 reset 标记，所有 agent 的 `sliceMessagesAfterLatestSessionReset` 都从这里切断 |
| `/ap new-session "deepseek"` | per-agent 重置：仅 deepseek 上下文清空 | 插入 `targetType: 'participant', targetKey: 'deepseek'` 的 reset 标记，仅 deepseek 的过滤逻辑识别 |

其他 agent 在 `/ap new-session "deepseek"` 后：
- 仍然看到所有 room 级别公告
- 仍然看到自己的 participant 消息
- 不受 deepseek 的 reset 标记影响

## 上下文爆炸的进一步缓解策略

三层可见性本身只是减少了"不必要的可见消息"，但 room 级别公告仍会随时间累积。补充策略：

### 1. Room 公告层的"摘要"机制

当 room 公告超过阈值时（如 20 条），不直接删除旧公告，而是由系统自动生成摘要后替换：

```
旧 room 公告（1-20 条）→ LLM 摘要 → 单条 "room-summary" 消息
新 room 公告（21-40 条）继续追加
```

### 2. 每条 agent 定向消息携带"上下文锚点"

participant 定向消息中，自动引用最近的 room 公告摘要，避免 agent 在 participant 对话中失去对全局任务的感知。

### 3. `new-session` 时选择性保留

`/ap new-session "deepseek"` 后，deepseek 的新 session 自动注入：
- 最近的 room 公告摘要
- handover 文件内容（如果通过 `--handover` 指定）

这样 deepseek 既获得了干净的上下文，又不丢失关键的任务信息。

## 实现路径

### Phase 1：消息过滤（低成本，高收益）

只改 `buildTaskRoomPromptContext`，加上 `participantKey` 参数和三层过滤逻辑。
不改 session 模型，不改 reset 机制。

- **影响**：agent 不再看到发给别人的 participant 消息 ← 立即减少上下文噪音
- **风险**：低。纯读取路径，不改写入

### Phase 2：Per-agent Reset 标记

改造 `postTaskRoomSessionResetMarker` 和 `sliceMessagesAfterLatestSessionReset`，
支持 per-agent reset 标记。

- **影响**：`/ap new-session "deepseek"` 真正只重置 deepseek
- **风险**：中。需要改 session 标记格式和过滤逻辑

### Phase 3：Room 公告摘要

实现 room 公告的自动摘要和注入。

- **影响**：长对话场景下的上下文控制
- **风险**：中。需要额外的 LLM 调用（摘要生成）

## 待决策事项

1. **默认 targetType**：当前通过飞书 `/ap` 命令发送的消息，默认 targetType 应该是什么？
   - 建议：`room`（用户指令默认全员可见，符合"房间 = 指挥中心"的心智模型）
   - 后续可通过语法扩展支持定向，如 `/ap @deepseek xxx`

2. **agent 间自发对话的 targetType**：agent 是否可以主动向另一个 agent 发送 participant 消息？
   - 当前无此机制
   - 如引入，需要 agent 有权限发送 `targetType: 'participant'` 的消息

3. **历史消息迁移**：现有数据库中所有消息的 `targetType` 可能为 null，如何处理？
   - 建议：null 视为 `room`（向后兼容，不丢消息）
