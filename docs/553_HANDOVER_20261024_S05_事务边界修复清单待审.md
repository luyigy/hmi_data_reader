## 保留与防止误修

- 551/552 的两个发布入口已有局部动态证据，保留并做后续兼容回归；本轮未重跑。
- 单独拿 N 的结果保存、人工决定、Worker 释放与消息封口，不能只因没有 G 就判为锁倒序。
- graphRunCanStartTx 的“拿锁”与 requireGraphRunActiveTx 的“暂停即拒绝”不同；不统一新增 active 限制。
- applyExecutionOutcomeTx 对 checkpoint/integrated/waiting_for_user 的语义必须保留；修调用链首次拿锁顺序。
- Prisma 数组事务通过 prisma 构造请求属正常形式；completed-workspaces 的 existsSync 在数组构造时执行。
- runtime-continuity 的 approvedProjectTools 实际传了 tx、registeredPolicy 和 executionId：
  context 中 Git 和配置文件读取分支被这些参数排除。此分支不是仅凭函数名就能判定的外部 I/O。
- assertExecutionWriterExited 虽收 tx 参数，当前 preparation-recovery 生产调用传 prisma 且位于 admission 事务外；
  将它作为未来复用边界审查，不声称这个调用已自锁。
- 目录外 acpx/runner 先 createRun(tx)，再绑定单一种 graph authority；模型启动在事务外。
  TaskRun/participant 隐式锁和 Node→TaskRun 的其他路径仍需兼容检查，不能只关注显式 G/N。
- 清理前快照核对不等于文件删除全过程已证明；第5步保留 Writer 变化与清理竞态验证。

## 预算调查的证据标准

当前源码支持三个需要区分的假设，而不是一个已定根因：

1. 候选保存后，结论记账失败进入兜底 platform_retry。
2. 准备边界确实遇到暂时平台故障，预算增加属于真实平台恢复。
3. 并发 claim/revision 变化引发拒绝，错误进入兜底；检查对应幂等键与归属。

executeJob 的兜底有未暂停、current.status===claimed 及具体分类条件；不能说所有异常无条件加 1。
普通 continue_work 不应消费平台预算；真实暂时故障使用既有预算，不把“计数必须始终为0”作为新规则。
需要同时检查 platform_retry 的指纹分支/有界分支与 review_retry；不同 outcome 不能混淆。
人工安排故障只能证明该机制可发生，不能自动关闭 551 中没有捕获 outcome 的历史异常。
保留 550/551/552 对候选、原 Native Session、真实退出、claim/revision、授权及有限重试的要求。
