## 实现与必须保留的边界

- `conversation-routing.ts` 集中选择原实施身份的输入：校验原消息身份、归属、角色及原会话，
  一次选择同一根消息，其他角色与旧会话不混入实施。它调用既有目标校验，没有保存另一套 Session ID。
- `conversation-followup.ts` 在普通实施等待时调用既有 `admitNode(source: 'conversation')`。
  只读预约不再抢走这些输入；完成后问答、历史复核卡及受授权边界限制的问答仍走只读原会话。
  已删除该运行路径里的恢复口令提示与模型输出恢复动作处理；历史材料 handoff API/回执兼容代码未清理。
- `preparation-recovery.ts` 对 conversation 来源补齐实施阶段、权限/范围决定、资源应用失败、
  能力缺失、所有权及受控冲突边界，普通消息不能替代批准；暂停、依赖、writer 退出、固定输入和版本重验仍在原 admission 内执行。
- `conversation-inbox.ts` 的实施输入读取复用同一选择规则，避免把其他角色或未经核实的输入混入原实施启动。
  运行中仍使用原 `deliverConversationSteering`，没有新增一轮意图分类或关键词确认。
- `coordinator.ts` 给收到输入的实施轮追加明确指令：按本轮内容回答或工作，遵循“只解释、先别改”。
  既有 answered / waiting_for_user 处理及候选算法保留；无变化的回答不制造新提交，也不变成 delivered。
- Admission 唤醒 ID 使用实际投递输入 ID；回复 epoch 使用根消息 ID。
  已绑定但失败的输入可凭现有恢复证据重新接续，同一用户消息的原生失败重试仍共用卡片身份。
  原生投递结果 unknown 的 steering 不重复发送，仍由原 writer/回执对账恢复。

会话重置边界仍在原 `conversation-target.ts`、`conversation-session.ts` 与 `conversation-continuation.ts`。
本轮没有修复它们选择旧 Session 的缺陷，也没有改变 runner 输出阶段或 resource-request 解析。
