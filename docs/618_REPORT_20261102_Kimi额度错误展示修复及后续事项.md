# Kimi 额度错误展示修复及后续事项

## 本轮范围与依据

Feishu DM 08a216 用户要求“先改第一个，然后我重开会话改后面的”。按最近一次三项排序，本轮仅修额度错误展示；会话锁和普通回复路由留到新 Session，不启动自动接续。

目标：Kimi 原生服务已返回明确的额度错误时，平台失败结果和飞书失败卡正文保留原因，不再只显示 `Kimi turn ended: failed`。本轮不恢复额度、不重发原业务需求、不解除锁、不重置或删除真实会话、不修改群话题绑定。

现场：群 `oc_2184f0fb1209d3944a80e2798f57401a`，LiveRoom `cmvyxqg0a0mwy5zpshdcm7k6j`，原生会话 `session_1d9e85de-1a7a-446a-b26f-49e039c01258`。2026-11-02 17:01 原生日志返回 429 和 5-hour usage limit；平台只保留了结束状态。

实施方案：在 Kimi 专用 transcript 适配中读取本轮主 Agent 的结构化失败原因，经现有桥接错误与脱敏链传到失败卡；没有具体原因时保留原结束状态兜底。验证包括本地协议 fixture、真实二进制加本地模拟模型接口，以及卡片正文构造。若真实协议与 fixture 不同，以原生实验为准。

## 实际发现与修复

- 初始 fixture 成功复现：预期包含 `429 ... 5-hour usage limit`，实际是 `Kimi turn ended: failed`。
- 原生服务落盘事件有 `turn.ended.error`，但当前 `subscribe_v2` 订阅传来的是转换后的 `transcript.ops`。直接读取原始事件的尝试在真实二进制测试中仍失败，已移除该尝试。
- 真实协议提供 `turn.upsert.turn.error` 和 `step.upsert.step.endMessage`。最终实现优先采用当前失败 turn 的具体原因，缺失时采用同 turn 的错误步骤原因。
- `transcript.reset` 的旧历史、其他 Agent 的事件不进入本轮失败；后续 turn 不继承旧额度错误，恢复完成的 turn 不保留错误。
- 明确含 429 与 quota/usage limit 的错误标为“**Kimi 额度已耗尽**”，保留原始说明；普通 429 限流保留“执行失败”，不误称额度用完。
- 错误说明限制为 2,000 字符，继续经过桥接令牌遮蔽、平台错误脱敏与卡片正文脱敏。不发布原生启动日志或私有思考。

示例后续失败正文：

> Kimi 额度已耗尽：429 You've reached your 5-hour usage limit. Your quota will reset when the current 5-hour window ends.

## 生效与修改文件

桥接脚本由 `runKimiServer` 在每次运行时启动新进程读取，因此合入运行目录后，后续 Kimi 轮次自动加载本补丁；本项无需重启飞书服务。已在执行中的进程不声称热更新。

- `scripts/kimi-session/bridge.cjs`：失败时采用 transcript 的具体原因。
- `scripts/kimi-session/transcript.cjs`：主 Agent 当前 turn/step 错误提取和展示。
- `tests/fixtures/kimi-web.cjs`：实际 v2 协议的额度失败场景。
- `tests/kimi-server.test.ts`、`tests/kimi-transcript.test.cjs`：回归及脱敏断言。
- `tests/kimi-quota-native.test.ts`、`package.json`：原生程序的隔离额度测试入口。
- 本报告：本轮结果和下一 Session 入口。
