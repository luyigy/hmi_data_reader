# PLAN · 网页平台登录认证与 2-Tier 鉴权

## 背景与决策

本 PLAN 承接 `docs/inbox/357_ISSUE_20260801_网页平台登录认证与RBAC.md`，并收敛首版目标为无
RBAC 的双层身份模型：Web 人工操作员使用 Single Admin Session Cookie；Feishu、Gateway 与后续
Remote Agent Daemon 使用现有签名或 Bearer Secret。所有受保护入口解析为统一 `AuthContext`，但按
`operator` 与 `machine` 区分允许的路由，避免用白名单绕过认证。

当前基线：Web 页面和大多数 API 没有统一 middleware；Gateway 已支持 Bearer / `X-Gateway-Token`；
Feishu Webhook 已校验签名与 verification token；Socket.IO 握手未鉴权且允许 `origin: *`。实施必须复用
既有机器凭证，不能削弱其校验，也不能在本阶段新增用户表、RBAC、OAuth、JWT 服务或第二套状态机。

## 最终 Roadmap

1. **Phase 0.1（本 PLAN）**：Auth Middleware + 2-Tier `AuthContext`。
2. **Phase 0.2**：Watchdog 误判长任务修复；代码实施在本 PLAN 完成后开始，复用身份上下文和
   Process Registry，避免并行修改长连接边界。
3. **Phase 1.0**：Attention Feed 与统一阻塞交互协议；只读聚合 Workflow 文档，动作落为标准 Git
   提交或 CLI，并绑定 Commit SHA、HANDOVER 路径或 Room 日志。
4. **Phase 2.0+**：Task Attempt Fencing → Remote Daemon ACK → 并行 Worktree。

## 信任边界与统一结果

| 入口 | 凭证 | `AuthContext` 主体 | 失败行为 |
| --- | --- | --- | --- |
| Web 页面与 Dashboard API | 签名、限时、HttpOnly Session Cookie | `operator:admin` | 页面跳转登录；API 返回 401 |
| Gateway / 机器 API | 既有 Bearer 或 `X-Gateway-Token` | `machine:gateway:<id>` | 返回 401；主体不匹配返回 403 |
| Feishu Webhook | Lark 签名 + verification token | `machine:feishu`，保留 sender Open ID | 返回 401，不进入命令处理 |
| Feishu 长连接 | 已认证 SDK 连接事件 | `machine:feishu`，保留 sender Open ID | 未建立可信来源时不分发 |
| Browser Socket.IO | 同一管理员 Session Cookie + 同源校验 | `operator:admin` | 握手拒绝，不注册事件 |
| 后续 Remote Daemon | Bearer Secret（复用 machine adapter） | `machine:daemon:<id>` | 本 PLAN 不实现 daemon，仅保留可复用入口 |

公开面只保留登录、健康检查和需要自行验证签名/Token 的机器入口；“公开”表示由入口自身完成认证，
不是跳过身份校验。状态变更型 Cookie 请求必须校验同源，登录必须有最小限流，敏感比较使用恒定时间
比较，日志不得输出密码、Session、签名或 Bearer Secret。

## S01：建立 AuthContext、配置约束与路由策略

新增最小认证内核和单元测试：定义 `operator | machine` 的可辨识 `AuthContext`；集中校验管理员账号、
Session 签名密钥与生命周期配置；使用平台原生密码学实现 Session 签名、验签和过期判断；建立覆盖全部
页面、API、Webhook、Gateway 与 Socket 的显式路由策略。配置缺失或生产配置不安全时 fail closed，开发
模式只允许有边界的本地兼容。不得新增依赖或数据库模型。

完成标准：有效、篡改、过期和错误用途凭证均有最小可运行测试；路由盘点中的每个入口明确要求
`operator`、`machine` 或入口自验证，且默认策略为拒绝。

## S02：交付管理员登录与统一 HTTP 保护

实现 Single Admin 登录/退出和最小登录页；成功后签发限时、签名、HttpOnly、SameSite Cookie，生产环境
启用 Secure。统一 middleware 保护 Web 页面与 Dashboard API，并区分页面重定向和 API 401；对 Cookie
认证的状态变更请求执行同源校验。登录失败不泄露用户名是否存在，并提供适合 Platform Local 单实例的
有界限流。

完成标准：匿名访问敏感页面被送往登录页，匿名或跨源访问敏感 API 被拒绝；有效登录可使用现有
Dashboard，退出、过期或篡改 Cookie 后立即失去访问；健康检查与机器入口仍可按各自凭证工作。

## S03：统一现有机器凭证并保持主体约束

让 Gateway Bearer / `X-Gateway-Token`、Feishu Webhook 签名与 verification token、Feishu 长连接可信事件
输出统一 machine `AuthContext`。Gateway 必须继续绑定具体 gateway id；Feishu 必须保留 sender Open ID
供现有 DM 准入判断使用。共享解析结果但不合并不同协议的验签规则，不引入全局万能 Token。为未来
Remote Daemon 提供同一 Bearer adapter 的调用边界，但不实现 daemon、心跳或 ACK。

完成标准：现有有效机器调用保持兼容；缺失、错误、跨主体复用的凭证在业务逻辑前被拒绝；Feishu
Webhook 与长连接仍执行相同用户准入语义；回归测试证明机器入口不依赖管理员 Cookie。

## S04：保护 Socket.IO 并完成全链路验收

在 Socket.IO 握手阶段验证管理员 Session 和 Origin，把 `AuthContext` 绑定到连接，未认证连接不得注册
join/message 等事件；移除无条件 `origin: *`，浏览器客户端继续复用同源 Cookie。完成全路由负向矩阵、
构建、关键回归测试和部署配置说明，确认认证改动未夹带 Watchdog、Decision Hub 或 Remote Daemon
实现。

完成标准：匿名、过期 Cookie、错误 Origin 的 Socket 握手均失败；合法管理员实时功能正常；HTTP、
Gateway、Feishu、Socket 四类入口的成功与拒绝路径均有自动化证据；`npm run check:long-files`、认证相关
测试与 `npm run build` 通过，并创建完成本 PLAN 的 HANDOVER。

## 非目标与后续边界

- 不实现多用户、RBAC、OAuth/SSO、权限数据库、刷新 Token、凭证管理 UI。
- 不实现 Watchdog 修复、Attention Feed、Decision Hub、Remote Daemon、ACK 或并行 Worktree。
- 如出现多实例登录限流、即时 Session 吊销或多管理员需求，再引入共享存储；首版保持 Platform Local
  单实例与配置驱动。
