Matt：需求 → Spec → Ticket、验收要求和真实依赖。Issue 是工作内容和依赖的来源；批准快照保存本次工作范围。无需设计一套覆盖所有任务的通用业务判定器。

Matt 的实施流程和 pstack 的工程方法交给职责 Agent 执行：读要求、实现、验证、修复、报告。有测试者时由测试者负责验证；没有时实施者自查。两种结果明确区分，不把自查写成独立验收。

提供原 Session、Worktree、只读技能及执行工具；保留权限、Sandbox、单写者、Writer 退出证明、固定候选、revision/CAS、幂等和依赖资格。结果归属、权限安全属于平台；业务是否合格由配置的职责 Agent 判断。

目前堵塞在哪里

1交接格式变成业务关口。一轮结束本应先识别进度、交付或问题，当前缺字段会在进入检查前卡住。

2验证负责人没拿齐材料。同一张票的细则没有直接交给测试者，独立验证可能遗漏要求。

3技能能读取，职责仍未贯通。资源装配已有预检，流程仍同时受技能指令、预设检查配置和回执格式支配。

M6 的此前证据：真实修改与 12 项专项通过已出现；回执 blocked 缺 blockerKind，进入补收；独立验收尚未完成。另有附近回归错误，不能据此宣布整票完成。

ticket-behavior 背后有真实 pytest argv，不是空门槛。问题是其覆盖范围不等同于 Ticket 的全部业务要求。

以下均为目标设计，当前代码尚未实现。选择的是质量判断的负责人，不能直接等同于旧“仅实施、未验收”模式。

  1. 平台把完整 Ticket、Spec、已有材料、Matt/pstack 技能入口交给实施者。
  2. 实施者自主实施 → 选择适用验证 → 发现缺陷 → 自己修复，继续这个循环。
  3. 实施者根据任务要求与真实证据判断完成，并交回成果和说明。不是把一轮结束或出现 diff 当成完成。
  4. 平台核对结果归属与运行安全，保存、受控集成，记录“实施者自查完成”，释放依赖已满足的后继。
  1. 平台把完整 Ticket、Spec、已有材料、Matt/pstack 技能入口交给实施者；候选就绪后交给配置的测试者。
  2. 测试者对固定候选自主选择验证方法：测试、读回、浏览器、项目 verify。验证职责由测试者承担。
  3. 发现范围内缺陷 → 平台把反馈送回原实施者修复 → 测试者复验。只测自己写的测试、复述旧报告均不等于合格。
  4. 测试者判定通过 → 平台核对身份与候选绑定，完成受控集成与账本记录，按依赖继续。实施者自报完成不能越过已配置的测试者。

目标设计并不强制把 pstack 每个子技能或独立审查步骤都跑一遍；按任务及配置角色使用。用户已明确允许实施者自查，不能再因某个技能默认要求独立审查而凭空增加测试者关卡。

Agent 判断

做什么、怎么验证、证据是否足够、是否还需修复。只有真正缺少业务决定、必要材料或额外权限时，才向用户说明具体问题。

平台保证

工具可用、反馈送回原会话、候选不被调包、没有两个 Writer、结果不重复消费、后继不抢跑。格式错误是交接故障，不能冒充业务不合格，也不能默认为通过。
