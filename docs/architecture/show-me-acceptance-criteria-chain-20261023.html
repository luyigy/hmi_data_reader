为什么有了 Acceptance criteria 和 verify 技能，任务图还是会卡住

历史讨论稿，不是当前施工方案。用户随后明确要求由已配置 Agent 按 Matt/pstack 自主实施和验证，平台不再额外设置业务门槛。本页新增 automatic 校验、verify 注册为平台门禁等建议不再作为当前方向。通用 ticket-behavior 名称背后已有真实 pytest argv，不能理解为空检查。当前方向见 Agent 负责工程判断的现状与改善方案；本页保留作讨论记录。

一句话定位：不是"完全没有实现"，而是两套资产都进口了、都没接进门闩。Matt 票里的判据全文进了快照和实施者的提示词，但验收者只拿到 Issue 编号，确认卡不显示判据，机器门槛另配了一个通用名；verify 技能真实存在，但只在提示词里被"建议阅读"，平台自己从不执行它。卡住的两道门闩恰好都不是这两套资产。

第 1 层 · 房子鸟瞰：判据住在哪层，门闩装在哪层

4F 确认卡（人）FOCUS人批准路线的地方。判据全文不上卡（proposal-card.ts:51-56 只显示 自动/人工/Agent），目标截断 24 字（:19-22）。人确认的是角色矩阵，不是验收标准。
3F 运行快照（冻结）KEEPIssue 正文逐字冻结进 executions[].instructions（含 Acceptance criteria），哈希锁定不可改。判据在这里存得完好。
2F 实施会话（worktree）KEEP实施者提示词包含判据全文（coordinator.ts:134 引 instructions）。判据对实施者可见、被要求执行。M6 五项 pytest 就是它跑的（539 报告）。
1F 平台集成检查CONTEXT平台在受控环境跑 launchConfig.checks（coordinator.ts:619）。可选配置，不是每票都有。verify 技能不在这一层——平台从不调用 scripts/verify_hmi.py。
0F 验收复核（独立 Agent/人）FOCUS验收者提示词只有：目标标题、Spec 引用、Issue 编号（coordinator.ts:303），没有票的判据正文。机器门对照的是快照里的 acceptance.checks 名单（store.ts:315 按名字匹配证据行）。
