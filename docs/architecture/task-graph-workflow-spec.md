# 任务图工作流规格（草案）

状态：首版任务图运行时已落地；`docs/prototypes/task-relay-prototype.html` 是交互讨论原型，只模拟状态。Agent 将 JSON 路线提交为待确认提议，平台在父任务飞书话题发送确认卡。网页任务图页面可用于查看运行状态与管理路线。

## 目标

人在父任务话题确认一次路线：目标、依赖、可并行的仓内执行任务、执行 Agent、每个纵向 Slice 的验收方式。平台保存不可变的运行快照，自动创建当前可执行的子任务并分配 Agent。前置结果通过后，后续任务自动出现和启动；关键进度回到父任务话题。

目标运行时只有一套调度机制。新流程不要求、也不生成 PLAN/HANDOVER；历史文档保留为只读材料，不再通过 `next_action`、Prompt 标记或文件名触发下一 Session。实施说明写在定稿 Spec、任务节点和执行账本中。`workflow-watcher` 的计划任务配置和派发处理器已退役。

## 权威数据与身份

- **Spec**：经原型审查后定稿的产品和验收约定。可以由 Matt Pocock 的 `to-spec`、`to-tickets` 流程整理；飞书父任务链接到它。
- **运行快照**：人启动时冻结的 Spec 版本、任务图、各仓目标 Git ref/起始提交、Agent 分配、验收策略和合入策略。运行中的调度只读此快照；修订生成新版本并记录变更，不悄悄改写已启动任务。
- **父任务**：路线、审批、总体状态与进度汇总。子任务与父任务保持结构化关联。
- **纵向 Slice**：可独立验证的用户结果。节点依赖的是前置 Slice 的完整通过状态，而非某个 Agent 的“已回复”。
- **仓内执行任务**：一个仓库内交付提交和验证证据的工作项。前置未满足时仅保留在排期图；满足后才创建子任务话题、工作区和 Session。
- **执行账本**：持久记录领取、Session、提交、测试、评审、合入、纵向验收和异常。它代替 HANDOVER 作为事实来源，不要求 Agent 写接力 Prompt。

## 排期与状态

任务图必须无环，所有依赖指向已定义节点。启动时校验仓库、ref、Agent、验收条件和写入权限；只允许确认后的图进入运行。图中所有前置节点通过才放行当前节点。007 的示例是 `V1 → V2 → {V3, V5}`、`V3 → V4`。

节点状态为 `未放行 → 执行中 → 待集成/验收 → 已通过`。执行、测试、验收或合入失败时进入 `需处理`，只阻断依赖它的后继；独立分支继续。人工验收策略进入 `待人工验收`，等待指定审批人。状态变化由持久事件和幂等键保护，服务重启后重建 frontier，不能重复创建子任务或重复派发同一 Session。

每个节点预先选择验收策略：

1. **自动检查**：运行 Spec 指定的测试和纵向用例，保留输入、结果、提交与版本；检查通过后自动放行。
2. **指定 Agent**：由指定 Agent 复核相同证据，提交结构化结论；通过后自动放行。
3. **人工验收**：证据就绪后在父任务话题发卡；批准后放行。

无人工验收不等于无验证。缺失基准、真图或必须人工裁定的分歧时，自动策略不能把节点标记通过。

### 按片执行模式与 Spec 包

新卡片按 Slice 选择 `full`（实施、架构审查、测试）、`lean`（实施、测试）、`implement`（仅实施）。旧快照未指定模式时保留原先架构配置的行为。完整模式须指定架构审查者才可确认；精简不调用架构审查；仅实施自动集成后写 `delivered_unverified`，按事先批准的模式释放后继，整条运行结束时标为 `completed_unverified`，不能显示成已验收。修改模式不删除预先准备的验证命令，因此改回完整/精简后仍可校验。

项目使用 `docs/specs/<主题>/spec-package.json` 登记提审包：`title`、`status: ready`、`spec: spec.md`、`issueRoute: { parent, repositories, slices }`、`artifacts: [route-review.html, feature-prototype.html]`。所有引用局限于同一包目录，最多六个附加 HTML/MD。ready 表示可提审，不能派发。飞书 `/ap menu` → 任务图 / Jobs → 提出任务路线，会列出 HEAD 已提交的 ready 包；选择后由平台直接读取 Issues 生成可执行图。包内只登记执行配置，格式见 `issue-route-packages.md`。未经提交或列表版本变化的材料不得被选择。

Agent 提交命令支持 `--spec-repository=<仓库>`、`--spec-package=<manifest路径>`，冻结整个包的提交和内容哈希。提议发送原始 HTML/MD 附件到父话题，然后发送含角色矩阵的路线卡。矩阵可按房间角色建议分配、设置项目默认架构审查者、逐片覆盖并保存；未保存的选择点击确认时先更新卡片，须核对后再次确认。角色保存会更换快照哈希，旧卡动作不能启动新配置。

文件只作为审议输入；自动推进始终由数据库任务图与执行账本驱动。首次业务试运行包位于 mold 仓 `docs/specs/hmi-screen-projection/`，包含 S03→S04→S05→Reader R02→S06；R02 若需细分由提审 Agent 在整条路线中表达，不另立 PLAN/HANDOVER。该业务路线没有并行支线，不能替代隔离并行调度验证。

Issue 的自动发布/结果对账与异常恢复卡尚未接入本轮入口改造；当前不得把已连接 tracker 的 CLI 描述成任务图已完成 Issue 同步。已有中断与合入失败仍停在需处理，不自动重跑不确定的 Agent Session。

## 工作区、合入与失败

并行执行的每一个仓内任务都使用独立 Git worktree，包括分属不同仓库的任务。第一版可统一让任务图中的所有写入任务使用 worktree，以避免动态放行时重新判定是否并发。每个 worktree 从运行快照指定的仓库集成分支提交创建，记录路径、分支和基线提交。不得让两个 Agent 写同一检出目录。

独立 worktree 不占用原仓目录的长期写锁。同仓独立任务在依赖就绪后可同时实施；创建工作区、读取或推进集成引用使用仓库短锁，Agent 实施阶段不持有该锁。只有获批 `extraRepositories` 原目录参与全平台读写互斥：读者可并行，写者排斥其他读写者；同一 Slice 内共享可写 extra repo 的仓内任务也须串行领取。暂停的独立 worktree 不阻塞同仓其他任务。

同一 Slice 的每个仓内任务只使用一份 worktree，实施、测试、架构审查和验收按阶段复用，不按角色另建检出。Agent 在该 worktree 提交结果。平台按仓库串行集成，将最新集成基线以追加合并或快进的方式纳入该任务分支，在原目录运行仓内验证，通过后原子更新集成引用；验证失败保留原工作区及测试产物。同仓并行分支须吸收最新基线并重新验证。架构审查和验收固定该任务记录的提交，代码目录只读，临时测试数据使用隔离环境，原始截图和读回文件继续从该工作区读取。跨仓纵向验收只读挂载各仓对应的现有工作区，使用已记录的固定提交组合，不随集成分支后续移动而改变。合入冲突、失败检查或历史不一致进入 `需处理`，保留 worktree 和证据，首版由人核对现场并创建修订版路线继续，尚无原地恢复按钮；不得强制删除或自动改写已被 watcher、cursor 或其他 Agent 读取的历史。

## 飞书体验

首版由人在父任务飞书话题发送 `/ap graph propose [Spec 路径]`，或在 `/ap menu` 的「任务图 / Jobs」点击「提出任务路线」。Agent 根据 Spec 生成或导入 tickets 后，运行 `npm run task-graph:propose -- --parent-task-id=<id> --spec-repository=<repo> --spec-package=docs/specs/<slug>/spec-package.json --agent=<name>`。依赖只从 Issues 读取。平台在父任务飞书话题展示依赖关系图、仓库、Agent 和验收方式；卡片顶部先列出启动节点及具有相同前置的并行分支，再展示详细图与仓库授权。图的层级仅辅助阅读，不是整批等待屏障；每票只等待自身前置，并受并发上限和共享目录互斥限制。人通过卡片确认一次后启动。飞书群聊中的子任务话题在节点放行时创建；未放行节点仅显示在任务图中。关键进度同步到父任务话题。预设人工验收会发卡，也可在任务图页面决定。子话题可发送 `/ap graph resume` 登记已集成节点的验收恢复请求；不会重做实施。

路线卡同时列出每个仓内任务的实施者、每个 Slice 的验收者，以及架构复核者。实施者按仓内任务分配，可选择不同的本机 harness；验收者按 Slice 分配，支持自动检查、指定本机 Agent 或人。架构复核者可作为全项目默认值，也可由单个 Slice 覆盖。人在卡片确认前，可在父任务话题发送 `/ap graph role <Slice|all> <仓内任务键|acceptance|architecture> <Agent selector|automatic|human>` 改派，例如 `/ap graph role V3 collector local:pi-agent`、`/ap graph role V3 acceptance local:kimi-code`、`/ap graph role all architecture local:codex`。平台更新原卡与快照哈希，旧卡动作失效；确认后冻结角色。

仓内任务提交并集成后，平台先在对应任务的固定工作区执行纵向检查，再由指定架构 Agent 检查实施范围、共享接口和架构影响。架构结论写入事件账本；只有架构复核与验收均通过，依赖节点才放行。复核失败或中断会停在需处理状态，不能自动重试不确定的 Agent 运行。旧的已确认路线若没有架构配置，沿用原有验收路径。

## 与当前实现的切换

当前 `docs/workflow/workflow-contract.yaml`、`workflow-watcher` 和 completion gate 以 PLAN/HANDOVER 及单个 `pending` 游标驱动线性接力。它们不能充当任务图调度器，也不能与新调度器同时消费同一结果。

切换记录：已核对旧 watcher 没有待处理游标或正在派发的任务；关闭数据库中的旧 watcher 覆盖，删除项目配置中的 watcher 作业和运行时派发处理器。历史 PLAN/HANDOVER 代码与文档暂留供审计，入口已停止派发。新代码不从 HANDOVER 推断节点通过。任务图的首版运行条件是服务已启动、父任务负责人已确认路线、Agent 为本机执行后端、仓库 ref 与提交仍匹配。

## 平台实施 Slice

1. **路线启动**：父任务从定稿 Spec 建立运行快照，校验依赖图；人一次确认后仅派发无前置的节点。服务重启不会重复派发。
2. **自动接力**：仓内任务结果进入执行账本，验收策略决定节点通过或暂停；前置通过后自动创建下一批子任务，并把进度写回父话题。
3. **并行隔离**：跨仓与同仓任务都在独立 worktree 执行；并发失败不影响独立分支，暂停/恢复可重放。
4. **集成验收**：同仓结果串行合入并复验，跨仓固定版本组合做纵向验收；冲突保留现场并人工恢复。
5. **旧链退役**：切断 HANDOVER 派发，迁移文档约束和界面，清理旧 watcher 与相关配置；验证旧文档提交不会再启动 Session。

每个 Slice 的验收都通过父任务可见行为和持久状态验证，不以内部函数或文档生成数量代替。平台实施 Slice 的顺序可以按运行依赖细化，但最终必须完成退役切换，不能停在双调度状态。

## 路线卡的展示与发送

- 路线卡默认展示窄屏文本线框及简短角色摘要。串行箭头、分支和汇合来自实际依赖，不生成 PNG。Spec 和说明 HTML 作为附件发送。
- 展开角色配置后按 Slice 纵向显示模式和各职责下拉框；翻页提交并保存当前页，其余节点保持原配置。建议分配作用于整条路线，最终确认仍批准整条路线。
- Card 2.0 表单按钮通过 `name` 和 `form_value` 提交，禁止同时设置 `behaviors`。发送前检查元素数量和载荷大小，不能通过删除职责选项规避飞书限制。
- Spec 附件按父任务、话题、路径和内容哈希记录发送回执。审批卡重试和相同附件的路线版本更新复用回执；发送结果不确定时停止重发，核对实际消息后恢复。

## 子任务的 Harness 回复与历史

任务图执行的正文和系统事件来自 `TaskRunEvent`，通过独立的 `agent-platform-task-graph-feishu.service` 更新到子任务绑定的话题。目标群按仓库原路径精确匹配活跃群绑定，优先项目级注册，同群多个话题去重；多个不同项目群时报歧义，不按群名或路径前缀猜测。仓库无注册时才回退父任务的群绑定；父任务是私聊时不得向私聊回退详细输出。节点放行时在目标群创建可对话的子话题，私聊只保留路线摘要和群话题入口。历史私聊进度迁入子话题须追加 `reply_target_migrated` 事件，保留旧回执，再使用绑定独立的幂等键创建群内进度卡；原私聊卡改为迁移摘要，不删除执行历史。

每次执行保留一张卡片，显示 Harness、职责、正文、状态和可展开的系统历史；架构与验收会话映射到对应 Slice 的子话题。会话完成不等于 Slice 验收通过。

`TaskRunFeishuRelay` 保存绑定、飞书消息 ID 和已展示事件序号。数据库锁阻止重复派发，固定消息 UUID 覆盖短期重试；卡片更新失败不推进游标，回执长期不确定时停止重发并要求核对。旧执行账本可回放，不伪造过去没有记录的工具事件。回复经过凭据脱敏和长度限制，实时输出按五秒轮询合并，避免逐 token 刷屏。

### 发布与进程核验

工作流相关代码发布后，必须同时核对以下三个独立服务。只更新 Git 检出或重启聊天接收器，不能证明卡片转发器已加载新代码。

- `agent-platform-task-graph.service` 负责派发和恢复。
- `agent-platform-feishu.service` 负责消息接收、房间会话和卡片动作。
- `agent-platform-task-graph-feishu.service` 负责执行进度卡持续更新。

`scripts/reload-task-graph-workflow-when-idle.mjs` 在没有 running TaskRun 时重载这三个服务，并逐一确认 active 和非零的新 MainPID。应从独立 systemd 作业运行；在飞书服务子进程中直接重启接收器会中断当前会话。该脚本的 running 检查不等于全平台排空，调用者仍须避开待派发/待恢复任务并等待当前操作退出。只修卡片转发时，可单独重载转发器，不重启执行中的模型。

部署回执应包含被重载的服务名、旧/新 PID，并通过真实后台服务更新已登记 messageId 后回读原话题。不能只调用宿主渲染函数或检查当前 HEAD 就宣布运行进程已更新。历史段落卡保持原样；同一 TaskRun 后续只更新其受管卡。

权限请求显示在执行记录中；新请求的独立审批卡也发送到同一话题，审批仍沿用现有身份与执行边界校验。消息转发服务只负责可见性，不自动批准或重试实施任务。

现有运行迁移时，只允许将任务分支快进到其已记录的集成提交；不改写历史；旧集成/验收副本只在确认无人使用、提交匹配且无未保存产物后迁移清理。不能强制执行只读边界的 Harness 不得承担该只读复核阶段。


## 完成后的工作区清理

任务通过验收，或按预先批准的仅实施模式完成后，平台保存提交引用、执行账本和必要产物，再用 Git 清理该任务 worktree。忽略的截图、读回 JSON、报告等移入仓库旁的 `.agent-platform-task-graph-results/`，带提交号及文件摘要；可重建的依赖缓存丢弃。清理结果写账本，运行器每分钟补查因进程退出而未完成的清理。失败、待补材料、尚有运行会话、未提交改动、提交号变化或证据保存失败时保留工作区并记录原因，不把清理失败冒充为任务完成。结果目录独立于 worktree，当前保留供审计，不自动过期删除。

### 子话题图片材料

任务问答与 Agent 验收由平台读取该子任务已绑定的飞书话题历史，提取用户发出的独立图片和富文本内图片。群主时间线查询不会展开话题，不应从技能示例或历史模型上下文猜群 ID。只读取已记录的 chat/thread；返回归属不匹配时失败，不导入外部群材料。

平台将原图复制到任务专属输入目录，记录原消息 ID、发送者、时间和 SHA-256，向问答与验收沙箱提供同一只读目录。飞书应用配置与令牌不挂载到 Harness。索引不是验收结论；Agent 必须打开原图核对，图片和历史内容也不能覆盖执行权限或批准条件。

每次最多扫描最近 200 条话题消息并提供 12 张用户图片，下载调用限制 20 秒。超出范围、权限或网络失败应明确说明，保留已取得材料，不将未检索到解释为用户未发送。取得图片不自动恢复、验收或放行节点；恢复仍由已授权的原工作流处理。

### 补材料后接续与自动回修

父话题和 Slice 子话题都可补材料并说“用这张继续验收”。平台按子任务绑定、显式 Slice 键或父任务唯一暂停节点定位；有多个候选才询问一次，随后回复任务代号即可。候选选择有效期十五分钟，可取消。普通问答、否定继续和仅发送图片不触发恢复。`/ap graph resume [Slice]` 保留为备用入口。

确定性入口接收明确的继续指令；上下文表达由话题 Agent 输出 `<graph-control>{"action":"resume_acceptance","nodeKey":"实际节点键"}</graph-control>`。平台核对原始 Feishu 发言者、绑定话题、管理员权限、批准的节点与运行状态，再写入恢复账本。模型不能自行改变状态，控制块不向用户作为操作命令展示。按入站消息 ID 去重，同节点同时到达的请求合并，运行中不会重复派发。父子话题中的用户图片按原消息和资源键去重，保留来源与哈希，毋须转发。

问答和架构审查保持只读。动态验收使用独立可写的测试运行目录、隔离临时文件系统与网络；原任务代码工作区、Git 元数据、工具链和原图只读挂载。允许启动临时服务、写 SQLite/测试 JSON 和报告，禁止修改交付源码或共享业务数据。测试运行目录不是另一个 Git worktree。每轮目录和固定提交组合入账；上轮通过项、原始报告与新材料同时传给验收者。旧脚本若不能指定输出目录或不支持新输入，应作为范围内的验证入口缺口回修，不要求用户放开整仓写权限。

`TASK_GRAPH_REVIEW` 失败结论包含 `failureKind` 和批准清单中的 `failureKey`。`in_scope_defect` 自动将原实施任务重新排到 frontier，传入失败报告和材料。`blocked_require_human` 用于材料缺失或歧义、范围变化、权限越界；缺少可靠结论也暂停，不猜测放行。每片最多自动回修两轮，无有效代码变更立即停下；两轮仍不通过时保留失败与尝试记录，向原话题报告。

回修复用原工作区和房间，保留旧交付的提交、证据、TaskRun 和派发信息，再释放该轮领取状态。平台合入最新集成基线，受控提交并运行检查，然后自动复核。集成和进入验证的幂等键按提交或领取轮次区分；架构结论绑定具体提交组合，不能把旧提交的通过复用到新修复。已通过的独立 Slice 不重跑，后继仍仅按真实验收完成条件放行。
