# 任务图为什么反复暂停，以及如何形成自动完成闭环

状态：评审收敛后的实施方案，2026-10-18。已核对 Antigravity 评审与当前代码；方案尚未实施，不改变原审批、业务验收标准或运行状态。

## 结论

当前任务图已经使用 ready 队列拉取工作。缺失的是一张票从实施到检查、回修、验收的连续责任：普通失败在多个出口被变成人工暂停，恢复又从旧事件推测该回哪一步。实施与检查的运行目录契约不同，使本可预见的环境问题反复触发这些出口。

建议保留依赖图、现有领取机制、worktree、受控集成和独立验收，集中每个仓内执行的阶段结果与恢复决策。正常情况由平台持续处理，真正需要人的决定或自动处理耗尽时才升级。

### 两点需要纠正

- 不是一张票失败就硬停全图。`runTaskGraphCycle` 继续处理 running/attention 图的 ready 节点；R01 是本路线共同前置，所以它停住使其余票都等依赖。
- 本地 Qwen 被用于辅助标注，不代表产品 OCR 被整体替换。但将这个可选实验的失败当成实施前置确实是错误。

重复 mention 日志不足以证明重复派发；频繁重启可能增加交互等待，但目前未有独立测量将其确定为本次节点停住的主因。

## 目标责任边界

任务图决定哪些票可以开始；每个仓内执行负责在批准范围内走完实施、检查和修复；Slice 汇总仓内结果并完成既定独立验收。Session 是一段执行过程，不是任务是否完成的权威。

```text
领取就绪执行 → 准备运行现场 → 实施 → 平台检查 → 受控集成 → 独立验收 → 放行后继
                              ↑         │                          │
                              └─ 修复 ──┘                          │
                              └──────── 同票回修 ──────────────────┘

临时平台故障 → 本阶段有限重试
需要范围、权限或必要材料的决定 → 只暂停受影响分支并给出明确请求
自动修复耗尽 → 带失败证据升级处理，不能无限循环或伪造通过
```

合并最新集成提交后，仍须在合并结果上执行既定检查；不能因预检查通过跳过合流验证。人工验收节点仍按原审批等待人确认。

## 收口后的执行契约

### 1. 一份阶段运行上下文

实施自测、平台检查和独立验收共享项目解释器、必要输入、检查命令、输出目录约定与服务声明。源码写权限按角色区分，不能为了让测试通过开放所有目录。

每个 attempt 提供明确的可写运行目录，测试将报告、缓存和临时业务数据写入其中。项目确有固定相对路径时，用登记的映射接到该目录。平台先验证必要输入可读、报告可写，再启动昂贵的实施阶段。可选输入不可用记录警告，不能冒充必要条件。

### 2. 一份当前 attempt 记录

当前阶段、候选提交、原始基线、运行上下文、错误和重试预算必须持久化，不能事后通过错误文字或若干旧事件猜测。

复用 `TaskGraphExecution` 行及类型化、带版本的 `dispatchMetadata` 保存阶段进度，不新建 attempt 表或独立 context 实体。以现有 claimToken 标识当前执行轮次，记录 `phase / workspaceBase / candidateCommit / runtimeDirectory / lastFailure / retryBudget`。历史轮次与原派发参数写入追加事件。先记录候选提交再做检查，检查失败也能从同一现场恢复。当前 dispatchMetadata 具有重复派发一致性约束，必须新增专用的阶段状态转移入口，以 claimToken 和版本比较更新，不能用任意 JSON 覆写绕过旧约束。

Node 聚合状态、仓内执行状态和 TaskRun 进程状态可保留各自用途，但阶段推进只能有一个写入入口。旧事件用于审计和一次性的迁移核对，不再是每次恢复时动态猜测阶段的规则。

### 3. 一份失败处理规则

| 结果 | 平台动作 |
| --- | --- |
| 必要检查通过 | 推进当前阶段，完成原要求后放行后继 |
| 本票范围内代码/测试缺陷 | 带原命令、错误和候选提交交回实施，再执行相同检查 |
| 可恢复平台故障或外部临时超时 | 修复运行准备或退避后重试同一阶段，不重做已成功阶段 |
| 结构化结果缺失/格式错 | 有限补收结果，不能第一次就要求用户重新启动整票，也不能直接判完成 |
| 可选工具未配置或辅助实验失败 | 使用已批准的可用路径，记录警告 |
| 真正需要改变范围、权限或取得无法替代的必要材料 | 明确等待哪项决定，只影响该分支 |
| 重试预算、时间预算耗尽或失败无进展 | 保留全部现场，说明已尝试动作并升级处理 |

具体重试额度和超时由项目/运行策略决定，先复用已有回修上限，再根据故障指纹与进展判断停止。避免单纯提高次数掩盖缺陷。沙箱错误由平台准备负责，不能让实施 Agent 擅自扩大权限。

### 4. 通知作为独立投递

群话题创建、进度卡更新和技术日志使用持久投递队列及幂等回执。投递失败重试投递，不把已经领取的业务执行标成实施失败。若原审批明确要求先建立审计通道，则属于明确的运行前提，须在启动前准备并清楚展示。

## 两种方案的取舍

| 方案 | 评价 |
| --- | --- |
| 保留现有任务图，收拢 attempt、运行契约与完整回修循环 | 推荐。能复用 ready 拉取、CAS 领取、检查、回修、验收和账本；需要迁移现有多个状态写入口 |
| 新建独立持久 ticket-owner worker，替换现有编排 | 责任更集中，但与已有 coordinator/claim/recovery 重叠。单换拉单方式并不能解决目录契约和保存点错误，当前不值得先重写派发器 |

借鉴 poteto 的重点是：一个工作单元持续对结果负责，先复现、修复、验证，再消费下一票。它不是永久保持同一个大模型 Session，也不是删除依赖图或独立验收。此次采用 Attack the Premise：否定“再增加一段提示就能修复生命周期缺口”；采用 Encode Lessons in Structure：把反复纠正变为运行契约与状态转移；采用 Laziness Protocol：复用现有调度和回修，减少入口。

## 实施顺序及验收门槛

1. 先建立真实端到端故障回放，覆盖当前已知四类停止；不是只测单个函数。
2. 统一运行目录契约，并在同一上下文运行实施自测与平台检查，修正测试写死源码输出目录的问题。
3. 将候选提交和失败阶段写入 attempt，打通集成前检查失败的回修，保留已成功的兄弟执行。
4. 将独立验收、手动恢复和重启恢复收拢到同一状态转移入口；接入有限格式补收和平台重试。
5. 拆开通知投递和业务推进；卡片只呈现执行中、自动修复中、等前置、需决定或已完成。

每一步都须有可运行的行为场景，尚未获得实际证据前不称为已修好：

- 暂停期间补文件，保留文件并成功继续；不要求用户重新口述上下文。
- 测试首次失败，自动回修后通过并放行后继；不需要人工 resume。
- 报告、缓存和临时数据库在平台只读源码环境可写，不污染原仓。
- 外部超时与尾注格式错误能有限恢复；真正权限不足给出具体决定项。
- 重启调度器后不会重复启动 Agent、集成或测试服务；旧写入者未确认退出前不接管。
- 一条品牌支线修复时，独立就绪支线继续工作。
- 同一故障持续无进展会停止并升级；没有证据的交付仍不能通过。

R01 用作回归样例，不在平台逻辑里硬编码 Reader、品牌、output/r01 或特定测试名。迁移仅作用于新 attempt；保留原审批快照、原 TaskRun、历史证据和原仓文件。


## Antigravity 评审收敛决策

### 已确认新增的覆盖范围

1. 架构复核失败当前绕过 `scheduleGraphRepair`，复核协议也缺少失败归属。架构复核和测试验收统一返回范围内缺陷、必要决定、协议错误或平台故障，再走同一处理策略。
2. `failureKey` 目前只逐字匹配 acceptance.checks，遗漏 integrationChecks 和命名误差。检查产生稳定 ID 并随失败结果传递；模型从已提供 ID 中选择，不能模糊匹配后放行。模型引用无效时先补收/核对，不把普通措辞差异直接交给用户。
3. 多执行回修目前重置所有执行，未改动兄弟又会触发“无代码变化”。回修要指向实际受影响的 execution，保留成功兄弟的提交和证据；跨仓接口确实变化时，对依赖结果重新检查，不能把旧证据无条件当成新证据。
4. 重启恢复不能只看内存 activeJobs/activeReviews 是否还在。记录当前阶段及已启动 TaskRun，确认旧写入者退出或被可靠隔离后再接管；旧进程仍存活时重连观察，不启动第二个写入者。
5. 阶段恢复需采用本轮候选提交，而非旧 blocked 事件里的 checkpoint。缺失提交/归属证据时核对现场并追加采纳记录，不删除保护或覆盖原现场。

### 对评审建议的限制与纠正

- **脏目录拒绝已修过**：48820fe 已允许同一分支和保存点上的未提交补充，并让脏回修保留原基线。剩余问题是新提交现场与旧 checkpoint 分裂；不能再次把已修问题列成尚待删除的 cleanWorkspace 检查。独立验收及清理的干净检查不在删除范围。
- **新增提交采纳需验证所有权**：核对平台登记的仓库、run/job 分支和路径、原基线与最近候选的祖先关系、没有未结束写入者、没有待解决合并状态，再保存本地改动并追加新 candidateCommit。仅“以 workspaceBase 为祖先”不足以证明新提交属于本次执行。无法证明时保存现场并明确升级原因。
- **不按未跟踪目录自动放权**：untracked 可能是用户原图、真值或新建源码。默认给 attempt 独立的 AP_GRAPH_OUTPUT_DIR，项目旧输出路径只在明确声明、无外部软链接和受跟踪输入保护的条件下映射到该目录；不扫描任意 tmp/artifacts 后全部挂为可写，不删除原仓内容。
- **格式错误不等于完成**：先补收一次结构化结论。即使代码有变化且硬检查通过，也不能仅据此合成 delivered 或 passed。仍无有效结论则按协议故障进入有限处理/升级，保留候选代码和全部证据；独立验收仍执行原批准要求。
- **无进展判定分阶段**：代码回修比较候选 tree、检查 ID 和归一化失败指纹；平台修复还须比较运行配置/输入身份。不能因为源码 tree 未变就判平台修复无效，也不能因为一轮仍出现同个错误便认定无进展。重复相同现场、相同故障且没有有效动作才提前结束，否则由既定预算限制。
- **不用一个长循环代替持久化**：executeJob 可以负责有界实施/补收/检查循环，但每次进入下一阶段前持久化状态。独立架构/测试角色仍独立执行，重启也能从已记录阶段接续，而不是从头重复。最新集成基线合并后仍重跑合流检查。

### 最小接口草图

下面是设计接口，不是已增加的运行时 API。使用现有 execution 和 claimToken，阶段类型统一放在单一模块，避免 coordinator、repair、恢复入口分别解析旧事件。

```ts
type Phase = 'prepare' | 'implement' | 'collect_result' | 'check' | 'integrate' | 'architecture' | 'acceptance';
type Outcome =
  | { kind: 'phase_passed'; evidence: EvidenceRef[] }
  | { kind: 'repair_required'; executionIds: string[]; checkId: string; diagnostics: EvidenceRef[] }
  | { kind: 'platform_retry'; failureCode: string; diagnostics: EvidenceRef[] }
  | { kind: 'result_incomplete'; diagnostics: EvidenceRef[] }
  | { kind: 'decision_required'; reason: DecisionReason; request: string; diagnostics: EvidenceRef[] };

// 读取类型化进度，校验 claimToken 与版本；旧数据仅在入口做一次受控归并。
readExecutionProgress(executionId): ExecutionProgress;
// 每次接收结果均追加事件，并以 claimToken + revision 比较更新当前阶段。
applyExecutionOutcome(executionId, claimToken, revision, outcome): ExecutionProgress;
// 使用现有运行上下文、检查器及回修机制推进一个可恢复阶段。
advanceExecution(executionId, claimToken): Promise<void>;
```

具体类型的 EvidenceRef、DecisionReason 和 ExecutionProgress 在实现前按已有领域类型收敛；此草图不引入第二套派发器、next_action 接力文档或新审批入口。Slice 级架构/验收结果关联本次所有相关 execution 的候选提交，不能任意落到某个兄弟执行。

### 最终实施批次

| 批次 | 实施内容 | 可审核的完成证据 |
| --- | --- | --- |
| 1. 固定故障回放与运行上下文 | 用隔离 Git/PostgreSQL/Bubblewrap 复现只读报告失败；提供每次执行的输出契约并让测试入口使用它 | 自测与平台检查运行同一命令，报告能写，源码/原图不受写入，旧报告保留 |
| 2. 持久阶段与集成前闭环 | 收口现有执行进度；在检查前记录候选提交；实施、结果补收、检查失败在同票内有限处理 | 代码缺陷及一次缺尾注无需人工 resume；新提交与补充文件不丢失，不读取旧 checkpoint |
| 3. 统一架构/验收/多仓回修 | 扩展既有修复调度，提供稳定检查 ID 和目标 execution，保留成功兄弟 | 架构缺陷、integrationChecks 失败和多仓局部缺陷均自动回修；成功兄弟不因零改动报错 |
| 4. 重启与投递隔离 | 当前阶段可恢复；确认旧进程所有权后接管；群消息投递采用独立回执重试 | 重启不重复执行/集成/服务；消息临时失败不变成实施失败 |
| 5. 现有运行接续验证 | 在核对当前现场、采纳最新候选并记录迁移后接续 R01 | 从修复部署后的既定运行自动推进到平台检查、独立验收和实际可运行的后继，无需额外人工 resume |

上述第 5 批是实施后的验收目标，不是本次评审汇总立即启动生产任务的动作。若真实业务验收发现未实现或错误，须在批准范围自动修复并重新验收；不能为了展示后继 running 而豁免原标准。不得用生产 R01 代替前四批的隔离故障注入测试。

端到端测试至少包含：一次检查失败、一次格式补收、暂停期补文件、架构复核缺陷、失败检查 ID 核对、多仓只修一侧、重启接管、通知超时，以及真正需要人工决定的独立支线。分别断言 human resume 次数为零或只在明确决定点出现；调度循环可执行多次，不要求异步实施/回修/验收在同一次轮询内全部结束。

### 修复工程本身如何采用 poteto-mode

按 Bug fix 流程先保留红色故障回放，设计共享类型/边界后分批实现，每批运行真实行为回归，再审查改动。项目工作流仍负责路线审批、依赖和派发；poteto-mode 负责每批的工程质量，不把技能的内部代理、提交或 PR 习惯叠加成另一套任务图。当前页是评审后方案，不宣称上述机制已经实现。
