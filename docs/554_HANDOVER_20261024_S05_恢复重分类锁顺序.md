## 实验及根因

G = graph-control advisory，N = Node 行锁，R = TaskRun/Participant 行锁。
旧 L1 存在 N→R→G 或 N→G；旧 L2 先多节点 N 后 outcome 取 G。
预留/admission 是 G→N。确定性安排 holder 已取得真实 G、尚未请求 N；
contender 从实际业务入口进入，观察到它在 SQL 层等待 holder 后，释放 holder 会合点。
修前两者相互阻塞并由 PostgreSQL 检测死锁，恢复/重分类事务回滚。

| 场景 | 实际竞争入口 | 修前 | 修后账本 |
| --- | --- | --- | --- |
| workspace | recoverGraphExecution 工作区身份失败 / reserveGraphReviewClaim | 死锁 | revision 7→8，预算0，ownership_attention |
| retry | recoverGraphExecution checkpoint→platform_retry / reserveGraphReviewClaim | 死锁 | revision 7→9，预算0→1，ready |
| blocked | 完成结果 environment_failed→decision_required / reserveGraphReviewClaim | 死锁 | revision 7→9，预算0，attention |
| question / answered | checkpoint→waiting_for_user / reserveGraphReviewClaim | 原本通过 | 均 revision 7→9，预算0，原候选与归属保留 |
| review-ready | recoverGraphReview 预留后未绑定 / reserveGraphReviewClaim | 死锁 | revision 7→8，预算0→1，原候选新复核 generation |
| review-running | recoverGraphReview 运行中旧 Writer 已退出 / reserveGraphReviewClaim | 死锁 | revision 7→8，预算0→1，TaskRun/Participant interrupted |
| reclassify-review | 三节点重分类 / 独立 sibling 的 reserveGraphReviewClaim | 死锁 | revision 7→8，预算0，目标 attention，后继 ready→planned |
| reclassify-admission | 三节点重分类 / 独立 sibling 的 admitNode(operator) | 死锁 | 目标重分类；sibling 准入 ready、预算0、revision7→8，且仅一个 operator receipt |

实施场景的复核预留代表陈旧竞争者：原本必须拒绝 `Review reservation no longer owns verification`，
修后仍拒绝，不把它改成合法启动。复核场景已有 durable claim，预留返回 false；真正的 L2 sibling
admission 返回 admitted。所有场景断言实际状态、候选、claim、revision、预算、原会话标识、事件和重放结果。

三个带 R 的场景增加两个独立数据库连接，分别对原 TaskRun、Participant 请求 FOR UPDATE。
修前它们均被 contender 的事务 ID 阻塞；修后 holder 持 G 时这些探针可完成。
`pg_locks` 同时保存 advisory、relation、tuple、transactionid 等锁，不只记录源码调用顺序。
这证明目标旧 R 锁参与持锁等待，不把“有 UPDATE 语句”直接等价于完整行锁证明。

解释按证据排序：锁顺序倒置直接吻合双向 pg_blocking_pids 和服务端 deadlock；
连接池排队不能解释 SQL blocker 环；claim/revision 拒绝也不能解释数据库死锁。
本轮死锁不追认为 551 的单连接 P2028 或历史预算异常的已定根因。

代理仅设置事务路由和会合点，所有锁 SQL、生产回调和账本结果原样执行，未 mock 锁结果。

本轮没有调用 applyExecutionOutcome 的自定义 db 参数，故不声称其事务外读取已改为独立连接。

admission 先执行实际准备事务；测试按回调中的 receiptKey 定位实际准入事务，再在其 G SQL 后会合。
完成结果恢复会先正常运行 completeConversationTurn，再路由恢复事务；该前置事务只 N、不再取 G。
锁路径变动不会被无会合静默当作通过：须观测 SQL 等待，问答反例则允许先完成并核验账本。

这些源码核对与新 R 探针支持本次顺序选择，但不是所有外键/更新竞争的完备证明。
