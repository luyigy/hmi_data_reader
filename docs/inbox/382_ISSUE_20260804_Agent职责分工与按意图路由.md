# ISSUE · Agent 职责分工与按意图路由（“我专写文档”由平台保障）

## 优先级与状态

- 优先级：P1（实现成本中低、日常收益高，建议排第一梯队，与 375 配对）。
- 状态：draft，记录于 Git Inbox，等待排期实施。
- 提出时间：2026-08-04。
- 配对议题：375（AP 命令卡片增加角色工作流入口）——本 ISSUE 提供职责维度与路由能力，375 提供卡片入口 UX；两者一起做才完整。

## 问题背景

### 1. 现状：平台“角色”只控制流水线顺序，不控制“谁干哪类活”

经代码核对，现有 `role` 体系只有 6 个开发流水线角色：

- 枚举（`src/lib/feishu-live-room-commands.ts:156`）：`planner / researcher / implementer / reviewer / tester / custom`。
- `role` 只参与两件事，都是“顺序”：
  - `/run feature|debug`、`/plan` 的阶段排序（`ROLE_PRIORITY`，`src/lib/live-room-workflows.ts:47`）；
  - 普通消息回复的排队（`ROLE_ORDER`，`src/lib/live-room-scheduling.ts:24`）。
- Schema（`LiveRoomMember`）只有 `role`（流水线角色）+ `roleLabel`（展示名），**没有任何“职责/专长”字段**。

**结论**：现在的角色控制的是“谁先谁后”，不是“谁干哪类活”。一个 `planner` 照样能改代码，平台不会因为某成员是 `implementer` 就拦着他写文档。因此“某 Agent 专门负责写文档/记录”目前只是口头约定，平台没有保障。

### 2. inbox 相关文章各自只覆盖一块，都不解决此缺口

| 文章 | 覆盖 | 是否能保障“某 Agent 专写文档” |
|---|---|---|
| 375（AP 命令卡片增加角色工作流入口） | 角色工作流的卡片入口 UX（feature/debug 按钮） | ❌ 假设角色已有意义，不新增文档职责，也不做意图路由 |
| 349 / 357（网页登录 + RBAC） | **人类**谁能操作平台（鉴权/权限） | ❌ 与“哪个 Agent 干哪类活”正交，管的是人不是 Agent |

三者都不是“Agent 职责分工/能力划分”，这是缺口（第 4 块）。

## 处理思路与优化方案

### 1. 新增正交的 `specialty` 维度，而不是往 `role` 里塞

现有 6 个 `role` 全是开发流水线语义（规划→研究→实现→评审→测试）。塞一个 `documenter` 进 `ROLE_PRIORITY` 很别扭——文档角色不在 feature/debug 流水线的某道工序里，硬排会破坏现有排序逻辑；且扩 role 枚举也解决不了“用户说‘写进 inbox’时平台自动派给文档专员”。

因此推荐：

- `role` 继续管开发流水线顺序，**不动**；
- 每个 `LiveRoomMember` 新增一个 `specialty` 字段（如 `documentation / diagnostics / implementation / general`），可叠加在任意 `role` 上；
- 平台按**消息意图路由**：检测到“记录/写进 inbox/出文档/写 FIX”这类意图 → 路由给 `documentation` 专员，与谁被 @ 无关；
- 375 的卡片按 `specialty` 展示“文档与记录”作为一等职责入口。

这样“某 Agent 专写文档”才真正由平台保障：不是靠该 Agent 自己记得，而是平台看到文档类意图就派给它。

### 2. 落地最小可用形态

- **意图识别 + 路由到文档专员**：让“写进 inbox / 出文档 / 记录 FIX”不再依赖 @谁；
- **卡片把“文档与记录”做成一等入口**（依赖 375 的卡片能力，但不等于 375）；
- **RBAC 不混进来**：357 的人类权限单独走，与本议题正交。

### 3. 不做的事

- 不引入通用“技能市场”或动态能力发现；首版用静态 `specialty` 枚举即可。
- 不改现有 `/run feature|debug`、`/plan` 的阶段编排顺序（那是 `role` 的职责）。
- 不把“分工”做成人能配的复杂权限矩阵；首版目标是“平台按意图把活派给对的人”，不是细粒度权限。

## 验收目标

1. 可为房间成员指定 `specialty`（如 `documentation`），独立于 `role`。
2. 用户发出文档/记录类意图（如“写进 inbox”“出个 FIX 文档”“记录这次决定”）时，平台将该请求路由给 `documentation` 专员，即使该成员未被 @。
3. AP 命令卡片（375 落地后）把“文档与记录”作为一等职责入口展示。
4. 现有 `/run feature|debug`、`/plan` 的流水线角色排序不受影响。
5. 357 的人类 RBAC 与本议题互不干扰。
