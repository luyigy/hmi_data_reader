# 服务监控、Agent 决策审计与历史保留策略研究

来源：2026-09-28 Live Room「Feishu DM 08a216」。本文件记录现状、建议和待办，不代表已实现或已授权自动删除；不是执行 PLAN。

## 结论

在现有 AP Dashboard 上扩展主机/服务视图，将运行、审计、存储三个视角关联起来。先明确可保留的审计证据，再设计日志清理；原始日志不能无限增长，也不能因为清日志失去决策和执行证据。

2026-10-01 决策更新：监控模块建设在 AP 平台内，AP 负责统一入口、运行异常判定和告警；Hermes 等外部系统以后按实际接口接入。此决定取代 09-28 聊天中“独立建设监控面板，AP 作为接入方”的建议。第一阶段优先解决运行无有效进展却无人知晓的问题，服务总览、审计和历史保留分阶段推进，不作为告警上线的前置条件。

平台内置监控仍有自身故障盲区：AP 采集/通知进程停机时，不能依靠同一进程自报故障。后续可由 systemd 或外部探针检查 AP 可用性，监控入口仍保留在 AP；不因此另建一套管理平台。

## 事故驱动的第一阶段：运行异常提醒

事故背景（来自本房间 2026-10-01 已完成的诊断，本次未重新读取生产日志）：Agent Swarm 的一次 Codex 运行约 1385 分钟，模型连接反复被拒绝，无正文或工具执行记录；平台定时心跳仍显示处理中，最终由用户停止。

本次源码核查补充：

- `src/lib/live-room-execution-timeout.ts`：Platform Local 的 codex/claude/kimi-code 未设置房间超时时，默认无限运行。
- `src/lib/feishu-runtime-cleanup.ts`：watchdog 对仍有注册进程的上述本地运行直接跳过；这不是有效进展检测。
- `src/lib/acpx/runner-participant.ts`：stdout 和 stderr 都会刷新 `lastActivityAt` 并标记 streaming，持续错误输出不能靠此字段识别。
- `src/lib/live-room-progress.ts`：心跳由定时器生成，并刷新自身使用的 `lastVisibleActivityAt`；该时间不能直接作为最后有效进展时间。

第一阶段验收目标：

1. 分开记录和展示进程/连接存活、最后有效进展、最近错误、等待用户或审批。平台心跳、重试提示和 stderr 不重置有效进展计时；正文、工具及子 Agent 的实际进展按后端事件语义识别，不能简单把所有 stdout 当成工作成果。
2. 无首个有效输出、执行中长期无进展、持续连接失败分别提示；阈值可配置，初值待实现时确定。长工具调用标记耗时并提供上下文，等待用户/审批显示待处理，不误判执行卡死。
3. 告警同时在 AP 中可查，并主动通知原房间/话题，包含运行链接、已运行时间、无进展时间和脱敏错误摘要；不只修改旧进度卡。重复扫描去重，持续异常按冷却间隔提醒，恢复或结束后关闭告警；发送失败可重试且可见。
4. 告警由后台运行，不依赖浏览器打开。扫描失败或数据过期标记未知/采集异常，不能显示健康；重启后恢复未解决告警，避免漏报或重复刷屏。
5. 告警与停止执行分开：首版异常提醒不自动杀长任务；显式房间超时继续按既有规则执行。模型连接与沙箱网络隔离的修复单独处理，监控不会修复网络权限。

验收需覆盖：模拟持续 Connection refused 且进程不退出、全静默、正常持续进展、长工具调用、等待输入/审批、告警发送失败、恢复后再次异常、进程重启及结束与扫描并发。关键结果是无人打开页面时，异常仍能在配置时限内到达原房间，且错误日志与平台心跳不能掩盖它。

实施顺序：运行异常提醒 → AP 服务/主机总览及外部系统接入 → 审计证据补齐 → 保留策略 dry-run 与恢复验证。Hermes 暂只保留接入边界，不预建未知 API 的适配层。

统一关联建议：host/account → service/agent → room/task → session → run/participant → action/approval/result。各后端保留原生标识；无法关联的记录标为未关联，不凭进程名称猜测所属任务。

## 本次核查的事实

| 现有能力 | 证据与边界 |
|---|---|
| Dashboard 已展示 Agent、Gateway、Remote Runner | `src/app/page.tsx`、`src/components/dashboard/RemoteRunnersPanel.tsx`；不是服务器全部服务的清单 |
| 飞书进程监控 | `FeishuRuntimeMonitor.tsx` 每 10 秒请求指标；`src/lib/feishu-runtime-status.ts` 读取 /proc 的线程、句柄、RSS，当前没有在该链路存储趋势样本 |
| AP 健康入口 | `src/app/api/health/route.ts` 直接返回 healthy，只能说明该路由可响应，不代表数据库、队列和全部 Agent 健康 |
| 运行详情已有持久化 | `src/lib/acpx/event-bus.ts` 写 TaskRunEvent 后推送 WebSocket；stdout/stderr 为 detail，其他事件为 summary；summary 只是分类，不等于合格决策审计 |
| 运行活动状态可复用 | TaskRun/Participant 有活动时间、waiting_user、stalled 等字段，不应把等待用户判断成死进程 |

| 删除有关联风险 | `prisma/schema.prisma` 中 Task → Run → Event 等是级联删除；独立审计不能依赖会被一起删除的父记录 |
| 定时记录兼有去重职责 | `src/lib/scheduled-jobs/runner.ts` 创建 ScheduledJobRun，以唯一 idempotencyKey 拒绝重复执行；不能整行按年龄删除后重新允许旧事件执行 |
| 存在局部清理 | `src/lib/feishu-message-dedup.ts` 对消息去重记录保留 7 天，按消息到达触发、最多每日尝试一次；这不是聊天和 session 的统一保留策略 |

本机只读运行快照：当前账户 systemd user 有 61 个 running 服务，系统级有 47 个，Docker 有 29 个运行容器；包括桌面和基础设施，不能相加称为 Agent 数量。业务范围包含 AP 网页、飞书、定时任务、Remote Runner Gateway，以及其他 Bot、推理服务、数据库等。这里只用于确认监控覆盖面，不保存私有地址、密钥或完整部署清单。未检查所有进程、其他用户的 user service 和远端节点；running/容器 Up 也不等于业务探针通过。

上一轮报告的数据库约 761 MB、各 CLI 会话目录占用和磁盘余量是此前快照，本次没有重新测量，不用于预测保留成本。尚未验证备份恢复。

## 可视化面板的最小范围

1. **主机/服务总览**：按主机分组，列出已登记服务、所属账户、来源（systemd user/system、Docker、AP 子进程）、状态、最近采样时间、CPU/RSS/磁盘、重启次数和探针结果。区分 stopped、failed、unknown、stale；采样断开不显示假绿。
2. **Agent 运行视图**：谁在处理哪个房间/任务、实际 provider/model、运行时长、最近活动、等待输入/审批/工具/失败、原生 session 关联和最近动作；token/费用仅在后端确实提供时展示，否则显示未知。
3. **审计时间线**：从 run 下钻到授权、动作、结果与证据；支持按 Agent、时间、动作、失败筛选。历史详情归档后显示归档入口，删除后显示到期时间与策略，不能表现为空白丢失。
4. **存储与保留视图**：按主机及数据类别展示体积、最旧记录、增长趋势、保留期限、保护项、待归档/待清理数量和估算字节、最后成功备份及恢复演练时间。

复用现有 Dashboard、运行事件和主机登记。第一版读取显式登记的服务，以只读采集为主；通过现有 SSH/Runner 按主机权限读取远端状态，不为每个临时 CLI 进程新增守护程序。扫描到未登记服务只提示待纳管。采集端设置超时、限流和新鲜度，采用后台定时采样，避免浏览器打开数量放大服务器采集压力。重启/停止等管理按钮后续单独处理权限与审计。

## “决策留痕”的具体含义

留存可观察、可核对的决策依据和动作，不以模型内部思考链作为审计要求，也不能靠事后生成的摘要补造历史证据。

最低记录：唯一事件 ID、schema 版本、发生/接收时间、主机/账户/Agent、room/task/session/run/participant、触发指令引用及必要的脱敏快照、实际 provider/model 与配置版本、动作类型、目标、脱敏参数、显式理由摘要、适用规则版本、审批人/批准范围/时间、执行开始与结果、退出码、产物/commit/证据引用、关联动作 ID。

- 用户指令、平台自动规则、Agent 建议、人类批准必须区分来源；重试保留尝试编号和因果关联，不能只覆盖最终结果。
- 在执行边界记录动作意图，再追加结果；进程中断后显示未知/待核实，不能推断成功。受控高风险动作审计写入失败时应阻断执行，监控采样失败则标告警。
- 从 AP 调度、工具调用和配置变更处记录实际可见事件；未接入的 CLI/服务显示覆盖缺口，不能声称所有操作已审计。
- 首版审计只追加、业务读写权限分离，保留对象名称快照和稳定 ID，删除任务不连带删除审计。校验和能检测文件损坏，但单独的 hash 不能证明防篡改；如要求抵抗数据库管理员篡改，另需异地受控归档/签名或不可变存储。
- 参数、日志、证据入库和归档前脱敏，避免凭据、认证头和无关个人数据；查看/导出/策略修改本身留审计，权限沿用房间/项目边界。
- 与 [481 Pi 切换 TODO](481_ISSUE_20260928_Pi主机级供应商与模型切换TODO.md) 联动：记录切换前后配置和应用结果，每次 run 固化实际采用值。

## 建议保留分层（讨论初值，未启用）

| 类别 | 在线保留建议 | 到期处理 |
|---|---|---|
| 主机/服务指标 | 细粒度 7 天，小时聚合 90 天 | 先生成并校验聚合再清细粒度；容量和增长趋势保留聚合 |
| stdout/stderr、详细工具输出、服务调试日志 | 成功运行结束后 30 天；失败运行结束后 90 天 | 需要长期审计的证据先提取独立保存，其余到期可删；与 journald/Docker 日志轮转一并核查 |
| 运行概要、决策/审批/配置变更审计 | 在线 180 天，归档后总计 365 天 | 到期复核；调查或用户标记保留的记录暂停到期，不视为法规期限 |
| 聊天、交接结论、产物索引 | 默认不自动删除；长正文可在 180 天后归档 | 保持可检索和恢复入口；敏感数据删除需求另行处理，不把“默认保留”变成永久不可删 |
| 原生 CLI session | 活跃或仍可续接时完整保留 | 确认无引用且静默 90 天后归档，归档至少 30 天隔离观察并完成恢复验证，再考虑删原件；归档总保留期限建议 365 天 |
| 游标、派发状态、去重键 | 单独按正确性要求管理 | 首版不随日志 GC；7 天飞书消息去重按现有实现单独评估；定时任务去重键需保留或建立可靠重放截止边界 |

期限依据运行终止时间、最后活动或归档时间分别计算，不统一按 createdAt。预计回收量必须实测：用每日新增量 × 期限初估，再加索引、归档和备份空间；数据删除不保证数据库文件立刻缩小，不将危险的数据库重写维护绑进日常清理。

## 清理闭环与故障处理

1. 生成只读 dry-run：分类、数量、范围、估算体积、命中策略及豁免原因；首版默认仅报告。
2. 排除 pending/running/waiting_user、待审批、当前会话、续接引用、调查保留项和共享文件。引用来源包括 LiveRoomMemberSession、TaskSession、Participant metadata/continuation 及各 CLI 的原生会话关系；路径必须受主机允许目录约束，不能跟随任意符号链接删除。
3. 需归档的数据按批次导出，写清单（ID、时间范围、格式版本、校验和、策略版本）；验证可读与恢复，保留索引。归档不是备份，至少有独立于源磁盘的可恢复副本。
4. 在实际删除前再校验状态和引用，并与续接/新建引用使用同一互斥或事务保护，避免预览后会话被重新使用。无法证明无引用就跳过。
5. 小批次、限速、可重入；保存批次进度和删除收据，归档失败/远端离线时不删源文件。不能通过删除父对象间接清理审计。
6. UI 保留到期/归档标记；数据库恢复后需重放删除清单，避免已按策略删除的数据从备份重新出现。清理动作本身进入审计，并保留策略变更前后版本。
