# 通用 HMI 结构化候选协议实施计划

## 1. 先看最终故事：我们到底要走到哪里

总体目标不是“改一个 JSON 合同”，而是让用户上传任意 HMI 页面后，能够看见、修正并保存页面上
真实存在的工艺参数。

完整路线分为三段：

| 阶段 | 要解决的问题 | 完成后得到什么 | 所属计划 |
| --- | --- | --- | --- |
| A. Reader 看懂图片 | 图片里的字段不一定在预设目录中，现有 draft 会漏掉未知字段 | Reader 返回完整、可追溯、待确认的结构化候选 | **本 PLAN** |
| B. Web 让人确认 | JSON 还不能直接给现场人员使用 | 上传后展示通用结构，允许增删改和确认 | 后续 Web PLAN |
| C. 保存与业务映射 | 确认后的现场字段不一定能映射到既有标准字段 | 完整结构可保存；能映射的进入既有 mapper，不能映射的仍保留 | 后续 Web PLAN |

所以本 PLAN 是第一段：先让 Reader 成为可靠的“眼睛和整理员”。本 PLAN 完成后，API 调用方能拿到
正确候选，但还没有最终 review 页面，也不会自动写数据库。

## 2. 为什么现在做不到

078 PLAN 已建立“Reader 返回标准字段候选 -> Web 确认 -> 既有 mapper”的闭环，但候选受调用方
预先提供的字段目录限制。遇到新品牌、新页面或目录外参数时，Reader 可能看到了文字和数值，却不能
用原结构完整返回。

本 PLAN 把字段目录从“输出白名单”降为“canonical 提示”：

- 目录内字段可以得到 `canonical_id`；
- 目录外字段也必须返回，只是 `canonical_id: null`；
- 温度、射胶、保压、熔胶、冷却时间和未知页面共用一种结构，不再各造一份协议；
- `setpoint/actual` 是所有工艺参数的通用角色，不是温度字段的特例；
- 所有候选保持 `needs_confirmation: true`，不能直接写库。

现状审计也说明为什么不能继续沿用温度特例：`contracts/field_catalog.json` 虽然已有通用 `role`
元数据，但当前 `actual` canonical 字段只有温度类；射胶、保压、熔胶、冷却时间目录项目前都是
`setpoint/limit`。本 PLAN 不顺带扩字段目录，而是先保证这些工序的屏幕实际值能以
`role: actual, canonical_id: null` 完整返回；后续确认确有稳定业务映射时再登记 actual canonical 字段。

## 3. 本 PLAN 完成后能看到什么

一张图里同时出现下列内容时，同一个响应必须全部保留：

| 页面内容 | 必须返回的例子 |
| --- | --- |
| 射胶 | 射胶速度、压力、位置的设定值与实际值分别返回；1 段/2 段保持对齐 |
| 保压 | 保压压力、速度、时间的设定值与实际值分别返回；1 段/2 段保持对齐 |
| 熔胶 | 熔胶转速、背压、位置的设定值与实际值分别返回；1 段/2 段保持对齐 |
| 温度 | 料管温度喷嘴/前部，设定值与实际值分开 |
| 冷却时间 | 屏幕显示什么角色就返回什么角色；只有设定值时不得编造实际值 |
| 目录外字段 | 原样保留分区名、字段名、逐项标签、值和单位，`canonical_id` 为空 |

返回只有一种形状：

```text
图片 + OCR evidence + canonical 提示
  -> sections（页面分区，例如射胶/保压/熔胶/温度/冷却）
     -> fields（一个参数的一种角色，例如“射胶速度 + setpoint”）
        -> items（分段或温区，例如 1段/2段/喷嘴）
```

字段身份固定为“分区 + 屏幕参数 + `role` + 单位”。`role` 与工序正交，统一使用
`setpoint/actual/limit/unknown`：

- 同一参数同时出现设定值和实际值时，返回两个并列 field；不得塞进同一个 items 数组，也不得互相覆盖；
- `items` 只表达段位、温区等参数轴，不承担设定/实际语义；
- 只有“设定/目标”和“实际/当前/反馈”等屏幕文字或空间表头证据时才能确定 role；证据不足就用
  `unknown`，不能因为数值位置或经验猜成设定值；
- 冷却时间通常可能只显示设定值，此时只返回 `setpoint`；只有屏幕明确显示实际/经过时间时才返回
  `actual`。

最小示例（省略 sources/evidence 等重复字段）：

```json
{
  "label": "射胶",
  "fields": [
    {
      "screen_label": "射胶速度",
      "canonical_id": "stage_velocity_mms",
      "role": "setpoint",
      "unit": "mm/s",
      "items": [{"label": "1段", "value": 80}, {"label": "2段", "value": 60}]
    },
    {
      "screen_label": "射胶速度",
      "canonical_id": null,
      "role": "actual",
      "unit": "mm/s",
      "items": [{"label": "1段", "value": 78}, {"label": "2段", "value": 59}]
    }
  ]
}
```

这里实际值的 `canonical_id` 为 `null`，是因为现有字段目录没有对应 actual 字段；数据仍须保留，
不能错挂到 setpoint 的 canonical ID。温度目录已有独立 set/current ID，也仍遵守同一规则。

## 4. 为什么拆成两个 Slice

```text
S01：先证明 Reader 能把图片内容整理正确
  产出：可离线测试的 sections/fields/items 核心结果
     ↓ 作为 S02 的稳定输入
S02：再把结果安全放到现有 HTTP 入口
  产出：Web 可调用的 POST /api/v1/draft
```

S01 处理“看懂和整理是否正确”，主要风险是丢字段、合错值或接受坏模型输出；S02 处理“真实请求
是否安全可用”，主要风险是输入越界、错误状态、并发和旧接口回归。两者的失败原因和测试方法不同，
各自控制在一个 session 内，比一次同时修改算法和服务边界更容易审阅和回退。

S01 是内部能力，用户暂时不能从 HTTP 使用；它必须独立成 Slice，是因为 VLM 输出校验包含大量
不可信输入边界，先用纯函数测试封闭这部分风险，S02 才只需验证传输和服务行为。S01 不部署。

## 5. S01：建立通用候选整理核心

### 5.1 目的

让 `draft_from_ocr` 不再把字段目录当白名单，能够从 OCR 和原图 VLM 结果中整理出温度、射胶、
保压、熔胶、冷却时间及未知字段，且对每种工艺统一区分设定值与实际值，并拒绝不符合合同的模型输出。

### 5.2 完成后结果

直接调用 `draft_from_ocr(...)` 时，可稳定得到唯一的 `sections/questions` 结构；同值证据会合并，
冲突值会并列保留，所有候选都要求人工确认。S02 可以把这份结果原样暴露给 HTTP 调用方。

### 5.3 怎么实现

只修改 `scripts/vlm_qwen.py` 中 `draft_from_ocr` 直接使用的 prompt、响应解析、融合与校验：

1. 把 OCR 行、可选原图和 canonical 提示交给现有 `_text_completion` / `_chat_completion`；
2. 要求模型按 `sections -> fields -> items` 返回屏幕原文，并把每个参数的 setpoint/actual 拆成
   并列 field；
3. 在本地严格校验 key、类型、枚举、数量、长度和有限数；
4. 仅当 section、screen label、role、unit、item label 和数值都一致时合并 observation；
5. canonical hint 只有在 label、unit、shape、role 都一致时才能绑定；目录外字段或角色不匹配字段
   保留并设置 `canonical_id: null`；
6. 没有图片也没有 OCR 时不调用模型，返回空 sections 和重拍问题。

复用现有图像编码和 completion helper；不拆类、不建 schema 模块、不加依赖。

### 5.4 输入和输出合同

保留现有函数签名，避免本 Slice 同时改服务层：

```python
draft_from_ocr(evidence, user_message, target, current_structure,
               allowed_fields, image_bytes=None)
```

- `allowed_fields` 名称暂不改，语义改为 canonical hints；空数组表示“没有提示”，不是禁止输出；
- `target` 非空且最多 200 字符，`user_message` 最多 2000 字符；
- `current_structure` 最多 64 个键，键最多 200 字符，值只允许正整数；
- hints 最多 256 项，仅允许 `field_id/label/unit/shape/role`，字符串最多 200 字符，shape 只允许
  `scalar/array`，role 只允许 `setpoint/actual/limit/unknown`，`field_id` 不重复；role 是必填匹配条件，
  避免把实际值绑定到设定字段；
- `image_bytes` 必须是非空 bytes，最多 20 MiB；
- OCR 最多 2000 行，每行只允许 `text/confidence/bbox`；text 非空且最多 1000 字符，confidence
  是可选 0..1 有限数，bbox 是可选 4 个有限数。

顶层只能有 `sections/questions`：

- section：`label/fields`；
- field：`screen_label/canonical_id/role/unit/items/sources/evidence/needs_confirmation`；
- item：`label/value/sources/evidence/needs_confirmation`；
- role 只允许 `setpoint/actual/limit/unknown`；source 只允许 `ocr/vlm/user`；
- role 适用于所有 section；同一 field 的全部 items 必须共享同一 role；
- value 只允许有限 JSON 数字，布尔值不是数字；`needs_confirmation` 必须为 `true`；
- sources 去重且非空，evidence 为非空字符串数组；field 的来源和证据汇总其 items；
- 无逐项标签的标量用 `item.label: null`；无法确定是否同一字段时保留两个 field；
- 不使用浮点容差、模糊匹配或自动翻译。

边界固定为最多 32 sections、全局 256 fields、全局 1024 items、32 questions；标签、单位、
canonical ID、问题和单条 evidence 最多 500 字符；每个 field/item 最多 32 条 evidence、3 个 sources。
未知 key、空白 label/evidence、未知枚举、非有限数、完全重复候选和任何超限结果都抛 `VlmError`。

### 5.5 修改边界与工作量

- 生产文件：`scripts/vlm_qwen.py`；
- 测试文件：`tests/test_vlm_text_mapping.py`；
- 一个 session 内完成：影响分析 -> 实现 -> 聚焦测试 -> HANDOVER -> 提交；
- 不改 `hmi_service.py`、`/api/v1/recognize`、模板识别、Web、部署配置。

### 5.6 验收

测试必须逐条证明：

1. 同一响应同时保留温度、射胶/保压、熔胶和冷却时间；前三类各至少一个参数同时包含
   setpoint 与 actual，冷却时间只有 setpoint 的样例不得生成 actual；
2. hints 的 role 相符时才能绑定 canonical ID；actual 不得绑定到 setpoint ID，目录外字段、角色不匹配
   字段和 `allowed_fields=[]` 时的字段仍返回且 `canonical_id: null`；
3. `1段/2段/喷嘴/前部` 原样保留；同参数 setpoint 与 actual 是并列 field，items 按同一段位/温区
   对齐但不互相覆盖；
4. OCR/VLM 同值合并来源，不同值保留两个 item；
5. 有图无 OCR 走图像 VLM；两者皆空时不调用模型；
6. 坏 JSON、额外 key、空 evidence、未知 role/source、布尔/非有限数和各级超限都抛 `VlmError`；
7. questions 可以返回，但候选不能变成已确认。

### 5.7 停止条件与交付物

若现有 helper 无法满足合同，停止并在 HANDOVER 说明证据，不借机扩成新 VLM 框架。完成后运行
GitNexus 变更检测、workflow preflight 和 diff 检查；创建 S01 HANDOVER，只提交本 Slice 代码、
测试和 HANDOVER，然后停止。S01 不部署，下一 session 从 HANDOVER 进入 S02。

## 6. S02：把核心结果接到现有 HTTP 入口

### 6.1 目的

让 Web 通过现有 `POST /api/v1/draft` 安全拿到 S01 结果，同时保持认证、并发限制和
`/api/v1/recognize` 合同不变。

### 6.2 完成后结果

调用方上传图片和可选 OCR evidence 后，收到 S01 的 `sections/questions`；输入错误得到明确 4xx，
VLM 输出或网络错误得到 502，不会返回半份候选。到这一步，本 PLAN 的 Reader 交付完成。

### 6.3 怎么实现

只修改 `hmi_service.py::draft_image` 的请求解析、边界和错误映射：

1. 保留 multipart 字段 `file/target/current_structure/allowed_fields/message` 和可选 `ocr_evidence`；
   `allowed_fields` 每项按 S01 合同携带 role；
2. evidence 合法时不重复 OCR；未提供时复用 `recognize_image` 的 evidence；
3. 两条路径都把同一图片 bytes、上下文和 hints 传给 `draft_from_ocr` 一次；
4. 继续使用 Bearer middleware、`asyncio.to_thread` 和现有 semaphore；OCR 与 VLM 分段获取信号量，
   不嵌套获取；
5. 用现有 `np.frombuffer + cv2.imdecode` 拒绝空文件和坏图片；
6. 原样返回 S01 的 `sections/questions`，不在 endpoint 二次过滤字段。

不新增 `/draft/v2`、队列、缓存、持久化、后台任务或 helper 层。

### 6.4 HTTP 合同与 breaking change

- multipart 缺必填字段：422；空文件或坏图片：400；Bearer 不合法：401；并发忙：429；
- context、hints、OCR evidence JSON 或边界不合法：422；
- VLM 网络、坏 JSON、schema/上限错误：502；不得夹带半份候选；
- OCR/VLM 都无候选不是 HTTP 错误，返回 `200 {"sections":[],"questions":[...]}`；
- `allowed_fields` 只是过渡字段名，语义已经是 canonical hints；后续 Web PLAN 再改名；
- 每项 hint 新增必填 role；旧的四字段 hint 会得到 422。这是请求合同变化，Web 切换时必须同步补齐；
- 旧 `candidates/structure_suggestion` 被 `sections/questions` 一次替换，这是 breaking change。
  Web 切换前不得部署该 Reader 提交。

### 6.5 修改边界与工作量

- 生产文件：`hmi_service.py`；
- 测试文件：`tests/test_generic_extraction.py`；
- 一个 session 内完成：影响分析 -> HTTP 接线 -> 接口/回归测试 -> HANDOVER -> 提交；
- S01 代码只有发现合同缺陷时才允许最小修正，并须在 HANDOVER 解释；
- 不改 `/api/v1/recognize` 实现、模板、Web、数据库和部署。

### 6.6 验收

测试必须逐条证明：

1. 有 `ocr_evidence` 时不调用 recognize，图片、hints 和上下文只传一次；
2. 没有 evidence 时复用 recognize 结果，新结构原样返回；
3. endpoint 不过滤目录外字段或角色不匹配字段，空 hints 仍可返回候选；setpoint/actual 原样透传；
4. 空文件、坏图片、坏 JSON、坏 evidence、401、429、`VlmError -> 502` 状态正确；
5. 同一 recognize 样例修改前后顶层 key 集合相等，既有聚焦测试通过；
6. endpoint 不写文件、不落库、不自动确认候选。

测试不访问真实 VLM，不部署，不重启服务。

### 6.7 停止条件与交付物

如果 `/api/v1/recognize` 合同发生变化，或必须修改 Web 才能验证 Reader，立即停止并记录，不扩大
本 Slice。完成后运行 GitNexus 变更检测、workflow preflight、diff 检查和相称回归；创建终态 S02
HANDOVER，附请求字段表、curl、完整成功/失败响应、限制、测试命令和提交 SHA，只提交本 Slice 后停止。

## 7. 后续怎么接到最终目标

S02 完成后，在 `mold-data-webpage-tool` 单独立 PLAN，继续按一个 session 一个 Slice 拆分：

1. Web 后端代理并保存整份未确认结构，优先复用现有 capture JSON；
2. 上传后自动请求 draft，按“工艺参数 + 段位/温区”对齐展示设定值和实际值，并允许人工增删改；
3. 保存确认结果，能映射的进入既有 canonical mapper，映射不了的仍保留；确认出稳定的非温度
   actual 业务字段后，再单独评审并补充 canonical 目录，不以本次候选协议猜测建字段；
4. mock 全链验收；得到测试环境授权后再做真实 Reader smoke。

Web 计划必须先审计其既有未提交改动，不能把临时的 confirmed 绕门禁行为带入最终写库。

## 8. 全计划红线

- 不把 VLM 文本直接变成数据库路径或生产写入；
- 不因 OCR/VLM 一致而跳过人工确认；
- 不为单一调用方新增接口版本或第二份字段目录；
- 不提交当前工作树里的 TACT 温度路由、模板及其他既有代码改动；
- 修改任何函数前按 AGENTS.md 做 upstream impact；HIGH/CRITICAL 先警告；
- 每个 Slice 提交前运行 `detect_changes(scope=compare, base_ref=master)`，区分既有 TACT 基线；
- 每个 Slice 一个 session、一个 HANDOVER、一个聚焦提交，完成即停止。

## 9. 批准后如何启动

当前状态是 `draft / await_plan_approval`，因此没有执行 Prompt。用户批准本路线后，才把 PLAN 改为
`ready / start_first_slice`，加入只派发 S01 的 `WORKFLOW_PROMPT`；不能在同一 session 顺带开始实现。
