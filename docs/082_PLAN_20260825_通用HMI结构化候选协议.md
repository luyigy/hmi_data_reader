# 082 PLAN 20260825 通用 HMI 结构化候选协议

## 背景与决策

078/170 两个已完成 PLAN 建立了“Reader 白名单标准字段候选 -> Web 确认值 -> 既有 mapper”
闭环，但它只能处理调用方预先知道的字段，不能实现任意 HMI 页面的开放结构发现。

本 PLAN 不新增平行端点：当前 `/api/v1/draft` 只有 Web 这一条受控调用链，直接在跨仓版本
接力中升级合同即可。`/api/v1/recognize` 保持不变，继续提供低延迟 OCR/模板结果；Web
后续在上传识别后自动调用 draft，使产品主链形成 OCR + VLM 双管道。VLM 失败不得抹掉
OCR 结果。

标准字段目录仍可作为 canonical 建议输入，但不再作为输出白名单。无法映射的字段以
`canonical_id: null` 保存候选，由人 review；采集阶段不执行品牌、页面用途或 Profile 的
业务写入门禁。

## 1. S01：把 `draft_from_ocr` 改成开放结构纯函数合同

### 本 Slice 实际修改什么

只允许修改 `scripts/vlm_qwen.py` 中 `draft_from_ocr` 直接使用的 prompt、响应解析与校验逻辑，
以及 `tests/test_vlm_text_mapping.py` 中对应的聚焦测试。现有 `_encode_image_bytes`、
`_text_completion`、`_chat_completion` 能满足调用时直接复用；除非测试证明无法复用，不拆类、
不建 schema 模块、不加依赖。不得修改 `hmi_service.py`；现有 endpoint 虽会透传新返回值，但在
S02 完成请求边界、错误映射和回归前不视为可用 HTTP 合同，不能部署。

开工先逐项查看 6 个未提交文件的 diff。S01 提交只暂存上述两个文件中属于 draft 合同的 hunk；
`extract_fields.py`、TACT template、TACT 路由测试和任何 `/recognize` 改动原样留在工作树。修改
`draft_from_ocr` 及其调用的既有 helper 前，分别运行 GitNexus upstream impact，报告直接调用者、
命中流程和风险；HIGH/CRITICAL 必须先警告。

### 输入如何处理

保留当前函数调用参数，避免 S01 同时改服务层：

```python
draft_from_ocr(evidence, user_message, target, current_structure,
               allowed_fields, image_bytes=None)
```

- `allowed_fields` 字段名暂不改，但语义从白名单改为 `canonical hints`：其 `field_id/label/unit/shape`
  只帮助填写 `canonical_id`，返回目录外 `screen_label` 时必须允许 `canonical_id: null`。
- `target`、`current_structure`、`user_message` 只作为 VLM 上下文；不得据此过滤屏幕上真实存在的
  section、field 或 item，也不得生成数据库路径。
- `evidence.lines` 只传 `text/confidence/bbox`；`image_bytes` 存在时走现有图像 VLM，不存在时走文本
  VLM。两者都不存在时不调用 VLM，返回空 `sections` 和一条重拍问题。
- 请求边界固定为：`target` 非空且最长 200 字符，`user_message` 最长 2000 字符；
  `current_structure` 最多 64 个键，键最长 200 字符，值继续只允许正整数；canonical hints 最多
  256 项，每项只能有 `field_id/label/unit/shape`，三个字符串各最长 200 字符，shape 只允许
  `scalar/array`，field_id 不得重复；`image_bytes` 必须是 bytes、非空且不超过 20 MiB。

### 输出必须精确长什么样

S01 将旧的 `candidates/structure_suggestion` 整体替换为下列单一响应，不并行保留旧响应：

```json
{
  "sections": [{
    "label": "温度监控",
    "fields": [{
      "screen_label": "料管温度",
      "canonical_id": null,
      "role": "setpoint",
      "unit": "°C",
      "items": [{
        "label": "喷嘴",
        "value": 350,
        "sources": ["ocr", "vlm"],
        "evidence": ["喷嘴 350 °C"],
        "needs_confirmation": true
      }],
      "sources": ["ocr", "vlm"],
      "evidence": ["料管温度", "喷嘴 350 °C"],
      "needs_confirmation": true
    }]
  }],
  "questions": []
}
```

结构规则固定如下，执行者不得自行发明第二种形状：

- 顶层只能有 `sections/questions`；section 只能有 `label/fields`。
- field 只能有 `screen_label/canonical_id/role/unit/items/sources/evidence/needs_confirmation`。
  `canonical_id` 为非空字符串或 `null`；`role` 只允许 `setpoint/actual/limit/unknown`；`unit`
  为字符串或 `null`；`needs_confirmation` 必须是 `true`。
- item 只能有 `label/value/sources/evidence/needs_confirmation`。无逐项标签的标量用
  `label: null`；`value` 只接收有限 JSON 数字；`sources` 是去重后的非空数组，只允许
  `ocr/vlm/user`；`evidence` 是非空字符串数组。
- 同一 section/field/item 可保持屏幕原文，不做翻译或 canonical 改名。field 的
  `sources/evidence` 是其 items 的去重汇总，可额外包含字段标题证据。
- 同一 `screen_label + role + unit + item.label` 出现不同数值时，保留为两个 item（各自带来源与
  证据），两者 `needs_confirmation` 均为 `true`；只有数值也一致时才能合成一个 item 并合并来源。
  不使用浮点容差、字符串相似度或模糊匹配。无法确定是否同一字段时保留两个 field。

### 明确的边界上限

校验 VLM 返回值时固定采用：最多 32 个 sections、全局 256 个 fields、全局 1024 个 items、
32 个 questions；section/field/item label、unit、canonical ID、question 和单条 evidence 最长
500 字符；每个 field 或 item 最多 32 条 evidence；每个 sources 最多 3 项。空白 label、空白
evidence、布尔值冒充数字、`NaN/Infinity`、未知 key、未知枚举、重复完全相同候选和任何超限
结果都抛 `VlmError`。OCR evidence 输入沿用服务现状上限：最多 2000 行、每行只能有
`text/confidence/bbox`，text 非空且最长 1000 字符，confidence 为可选的 0..1 有限数，bbox 为
可选的 4 个有限数数组；纯函数也必须独立校验，不能信任未来 HTTP 调用者。

### 测试逐条证明什么

在 `tests/test_vlm_text_mapping.py` 替换旧白名单 draft 测试，最少留下这些可辨认的断言：

1. hints 内字段得到 `canonical_id`，目录外字段仍返回且为 `null`；
2. `喷嘴/前部/...` 动态 item 标签原样保留，`setpoint` 与 `actual` 不互相覆盖；
3. 相同值的 OCR/VLM observation 合并 sources，不同值保留两个 item；
4. 图片存在而 OCR 为空时调用 `_chat_completion`，两者皆空时不调用模型；
5. 坏 JSON、额外 key、空 evidence、未知 role/source、非有限数、布尔数值、各级数量或字符串
   超限均抛 `VlmError`；
6. questions 可返回但不得产生自动确认状态。

只运行该文件的 draft 聚焦用例及 `git diff --check`。通过后运行 GitNexus `detect_changes` 核对
仅命中 draft 预期符号/流程，创建指向 S02 的 S01 HANDOVER，提交 draft hunk + 测试 + HANDOVER
并停止；不得开始 HTTP 接线。

## 2. S02：让 `/api/v1/draft` 只返回 S01 新合同

### 本 Slice 实际修改什么

只修改 `hmi_service.py::draft_image`、必要的函数注释，以及
`tests/test_generic_extraction.py` 中 draft endpoint 聚焦测试；S01 纯函数只有发现合同缺陷时才可
做最小修正。不得触碰 `recognize_image`、`extract_fields.py`、TACT 模板/路由和 Web 仓。
修改 `draft_image` 或任何被迫联动的符号前逐个运行 GitNexus upstream impact 并报告风险。

### HTTP 请求与内部调用

- 路由仍为 `POST /api/v1/draft`，仍接收 multipart `file/target/current_structure/allowed_fields/message`
  和当前工作树已有的可选 `ocr_evidence`；不新增 `/draft/v2`。
- 为避免 Reader 与 Web 同时切换，表单名 `allowed_fields` 在本 PLAN 内保留，但解析后只作为 S01
  的 canonical hints，不再拒绝目录外字段。S02 HANDOVER 必须明确这是待 Web 独立 PLAN 改名的
  过渡字段，而不是白名单。
- `ocr_evidence` 已提供且合法时不再次执行 OCR；未提供时仍通过现有 `recognize_image` 取得 evidence。
  两条路径都把同一份图片 bytes 交给 `draft_from_ocr`，且只返回其 `sections/questions`。
- 继续使用现有 Bearer middleware 和 `asyncio.to_thread`；图片 bytes 用与 recognize 相同的
  `np.frombuffer + cv2.imdecode` 判空/判格式，不新增 helper 层。调用 VLM 前检查并获取现有
  `concurrency_semaphore`，忙则 429，`finally` 释放；无 evidence 时先让 `recognize_image` 完成其
  自有信号量区段，再为 VLM 单独获取一次，禁止嵌套获取造成死锁。不另建队列、缓存、持久化或
  后台任务。

### HTTP 错误语义

- multipart 缺必填字段沿用 FastAPI `422`；空文件或无法解码的图片为 `400`；
- `current_structure/allowed_fields/ocr_evidence` 不是合法 JSON，或 S01 输入边界不合法，为 `422`；
- Bearer 不合法为 `401`，现有信号量忙为 `429`；
- VLM 网络错误、坏 JSON、输出 schema/上限不合法统一映射为 `502`，响应中不得夹带半份候选；
- OCR/VLM 都没有有效候选不是 HTTP 错误，返回 `200 {"sections":[],"questions":[...]}`。

### 测试逐条证明什么

在 `tests/test_generic_extraction.py` 更新旧 `candidates` 断言，至少覆盖：

1. 带 `ocr_evidence` 时不调用 `recognize_image`，且原图 bytes、hints 和上下文只传一次给
   `draft_from_ocr`；
2. 不带 evidence 时复用 `recognize_image` 的 `ocr_evidence`，新 `sections/questions` 原样返回；
3. 目录外 field 不被 endpoint 过滤，`allowed_fields=[]` 仍可返回开放字段；
4. 空文件、坏图片、坏 context JSON、坏 OCR evidence、401、429 和 VLM `VlmError -> 502`；
5. `/api/v1/recognize` 既有聚焦测试原样通过，响应 key 与本 Slice 前基线无变化；
6. endpoint 不写文件、不落库、不把任何 `needs_confirmation` 改成确认态。

运行 draft endpoint 聚焦测试、S01 纯函数测试及现有 recognize 相称回归；不得访问真实 VLM、部署或
重启服务。提交前运行 GitNexus `detect_changes(scope=compare, base_ref=master)`，区分工作树既有
TACT HIGH 基线与本 Slice 的 draft 影响，执行 `git diff --check` 和 workflow preflight。创建终态
S02 HANDOVER，附最终 curl/请求字段表、完整成功/失败响应样例、限制、错误状态、测试命令和提交
SHA；只提交 draft hunk、对应测试和 HANDOVER，然后停止。

完成标准：Reader 只有一份开放式 `sections -> fields -> items` draft 响应；目录只提供 canonical
hints；`/recognize` 零合同变化；所有候选仍需人工确认；未修改 Web、未部署、未重启。

## 3. Web 接力出口（不在本 PLAN 实施）

`/data1/code/mold-data-webpage-tool/docs/dev/` 新建独立 PLAN，至少拆成：

2. 上传后自动 draft、通用结构 review 与人工编辑；
3. 已确认结构到既有 canonical mapper 的显式映射，映射不了的仍可保存；
4. mock 全链路与获批测试环境的真实 Reader smoke。

page-purpose/import gate”的临时行为；采集 review 可放宽，最终写入业务表的安全门禁必须
保留。

## 明确不做

- 不自动接受候选，不因 OCR/VLM 一致就跳过人工 review。
- 不为一个调用方新增接口版本路由、通用插件系统、对话会话表或后台任务。
- 不顺手提交当前 TACT 温度路由/模板工作。
