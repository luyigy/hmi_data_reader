# HANDOVER · 真实常驻 Run 停止验收

## 当前结论

- 用户前两次执行 `/ap job stop workflow-watcher` 均超时；对应 Run 的临时 Node 承载进程
  已提前退出，因此是无人回写终态的僵尸 Run。
- 后续通过内部命令处理函数得到成功结果，只证明底层取消链路可工作，不能替代用户从飞书
  执行命令的端到端验收。
- 当前不得宣称停止功能已通过真实验收。

## 下一步

1. 查清 `/ap job run`、常驻 Feishu runtime 和 systemd scheduled-job runner 各自由哪个
   进程执行 handler，选择现有正式链路中最小的真实 Run 启动方式。
2. Run 必须由 systemd 常驻服务承载；禁止临时 Node、内部 handler 直调或直接插入数据库。
3. 若现有 job 会立即结束，补一个最小受控等待入口：复用正式 runner 和现有取消轮询，
   默认禁用或只开放给 `workflow-test`，不新增 runner、队列或通用抽象。
4. Agent 只负责启动并回报 Run ID、job ID 和常驻服务状态；随后停止操作，等待用户亲自在
   飞书执行 `status → stop → status`。
5. 仅当用户实际命令返回成功、最终 `running: false`，且数据库记录为
   `failed + job cancelled by operator` 时，记录验收通过。

## 边界

- 不把内部函数调用、测试桩结果或 Agent 代执行命令描述为端到端成功。
- 不清理失败 Run，先保留证据；需要清理时另行取得用户授权。
- 修改任何函数、类或方法前先做 GitNexus upstream impact；HIGH/CRITICAL 先报告。
