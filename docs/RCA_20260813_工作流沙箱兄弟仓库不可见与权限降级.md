# RCA · 工作流沙箱“看不到第二个仓库”与 full_access 权限降级

- 日期：2026-08-13
- 触发现象：`mold-data-webpage-tool`（科学试模助手 / machine-converter-release）工作流中，kimi-code 在沙箱内无法看到 Reader 仓（`/data1/code/hmi_data_reader`）；成员权限“本来是 full access，后面被降级”。

## 1. 结论（一句话）

平台**早已支持** `execution_policy.extraReadOnlyPaths`（即之前那次“修复”），但 `mold-data-webpage-tool`
在 `config/projects.yaml` 里从未把 Reader 仓登记进该列表；于是在 `preset: workspace` 下，任何 full_access
成员都会被工作流策略**强制收敛为单目录 Bubblewrap 沙箱**，导致只挂载项目仓自身、Reader 仓自然不可见。

> 这是**配置遗漏**，不是平台缺能力。修复 = 给该项目的 `execution_policy` 补上 `extraReadOnlyPaths`。

## 2. 证据链（数据流，自上而下）

1. `config/projects.yaml`（`mold-data-webpage-tool`）原为 `execution_policy: { preset: workspace }`，无 `extraReadOnlyPaths`。
2. `src/lib/workflow-execution-policy.ts`
   - `buildWorkflowPermissionSnapshot`（:118）：`extraReadOnlyPaths = policy.extraReadOnlyPaths ?? []`（→ 空）；
     `effective.permissionConfig.writableRoots = [projectPath, ...extraWritableRoots]`（只含项目仓）。
   - `detectWorkflowPermissionDowngrade`（:344）：`policy.preset === 'workspace'` 时，凡是 `profile === 'full_access'`
     的成员都被标记，并产生告警：
     `⚠️ 权限降级：成员拥有 full_access，已按 Workflow 策略收敛为 workspace 单目录沙箱`。
     —— 这正是“本来 full access，后面降级”的来源（**按设计行为**，非 bug）。
   - `applyWorkflowPermissionSnapshot`（:312）：把成员实际权限改写为 `snapshot.effective.permissionConfig`，
     并把 snapshot 原样记录进 `workflowPermissionSnapshot`。
3. `src/lib/acpx/runner-harness.ts`（:123-129）
   - `profile === 'full_access'` → `workspaceRoot = undefined`（**不套 Bubblewrap**，整盘可见，Reader 仓此时可见）。
   - 非 full_access → `workspaceRoot = writableRoots[0]`（项目仓），`extraReadOnlyPaths = workflowSnapshotExtraRoots(...)`（原为空）。
4. `src/lib/harness/adapters/kimi-code.ts`（:39/:60）→ `src/lib/real-agents/kimi-code-agent.ts`（:232-241）
   `wrapWithBubblewrap({ readOnlyPaths: extraReadOnlyPaths })`。
5. `src/lib/harness/bubblewrap.ts`（:56）：`readOnlyPaths` 经 `--ro-bind` 只读挂载；未登记的路径**完全不进沙箱**。

因此：full_access 时无沙箱、Reader 仓可见；一旦被工作流收敛为 workspace 沙箱，且 Reader 仓未登记 → Reader 仓消失。

## 3. 修复（本次提交）

`config/projects.yaml` → `mold-data-webpage-tool` 的 `workflow-watcher`：

```yaml
execution_policy:
  preset: workspace
  extraReadOnlyPaths:
    - /data1/code/hmi_data_reader   # Reader 仓：只读挂载进沙箱
```

只读挂载满足 kimi-code“读取 datasets / ground_truth / `hmi_service.py` / hash 防污染核验”的需要，
同时不破坏 Reader 仓（其自身仍由 `hmi-data-reader` 项目的工作流独立守护）。

### 验证（已跑）

```bash
TS_NODE_COMPILER_OPTIONS='{"module":"commonjs","moduleResolution":"node"}' node -e "…loadProjectsConfig + buildWorkflowPermissionSnapshot…"
```

输出：
```
policy: {"preset":"workspace","extraReadOnlyPaths":["/data1/code/hmi_data_reader"]}
writableRoots: ["/data1/code/mold-data-webpage-tool"]
extraReadOnlyPaths: ["/data1/code/hmi_data_reader"]
exceptions(readOnly): ["/home/hello/.codex","/home/hello/.agents","/data1/code/hmi_data_reader"]
```

即：项目仓保持可写，Reader 仓作为只读例外挂载，完整贯通到 Bubblewrap 的 `--ro-bind`。

## 4. 生效方式 / 注意事项

- 权限快照在**每次任务运行启动时**按最新 `config/projects.yaml` 重建；当前已在跑的沙箱不会热更新，**下一次任务运行**即生效（无需改代码或重建镜像）。
- 若 kimi-code 需要在沙箱内**运行** Reader 服务（`hmi_service.py`，会写 `output/`、`__pycache__/`、模型缓存等），只读会让这些写操作失败。
  此时应把该条目从 `extraReadOnlyPaths` 改为 `extraWritableRoots`（或在 Reader 仓内指定可写子目录），权衡隔离性后决定。
- 若确实要“整盘可见、不收敛”，可把该 job 的 `execution_policy.preset` 改为 `full_access`；代价是放弃 Bubblewrap 隔离（仅建议短期排障）。
- 其它兄弟项目同理：只要沙箱需要看到本仓之外的目录，都必须在各自 `execution_policy` 里显式登记，平台不会自动收录兄弟仓。
