# 飞书重启后原会话持续执行失败

## 根因与范围

2026-10-25 用户报告最新改动后每轮显示“执行失败”，随后明确要求修复。
17:14 的两条投递实际失败原因均为 `Session already has an active run`，尚未启动模型。
17:13 服务重启时，原运行 `cmvnlzido04s6mt8t8mmdqn1c` 的参与者已完成，
但外层 TaskRun 仍为 running；投递被标为 `Stale: runtime shutdown`。

普通 Codex 聊天和任务图执行共用 graphWriter 进程身份。启动清理错误地将存在 graphWriter
解释为任务图归属，跳过普通聊天；现有 liveness 检查也不会处理参与者全部完成的外层遗留运行。
普通聊天的并发保护因而持续拒绝后续消息。原卡片仅展示通用失败文案，具体错误保存在投递记录。

本次只修复普通聊天重启收尾，不合入隔离 S02 分支，不推进 S03，不恢复 M06 业务。

## 修改

实现提交：`4e107b7b6495bbe01a3b12595d04feed64a16a90`。

- `src/lib/feishu-startup-task-cleanup.ts`：依据实际 execution 绑定、review/conversation 身份判断任务图归属；
  普通聊天须先证明原 supervisor 和带身份标记的进程均退出，再在事务内复核同一运行身份。
  Task、Session、Run 依序加锁，遗留运行标为 interrupted，不冒充业务成功。
  保留已完成参与者结果，仅在 activeRunId 仍指向该运行时清除占用。
  存活 supervisor、仍在收尾的 supervisor、未知/异机进程及真正任务图归属均保留。
  支持按一个 TaskRun ID 定向修复，避免生产恢复时扫描修改无关运行。
- `tests/feishu-startup-task-cleanup.test.ts`：重启后的完成参与者夹具、同 Session 的真实 runner admission、
  存活且已释放 harness 的 supervisor、未知 host、已退出但仍归任务图的执行、图对话隔离和幂等检查。

无 API、数据库 schema、权限、审批、导出或外部集成协议变化。
通用失败卡文案未在本次改动中调整。
