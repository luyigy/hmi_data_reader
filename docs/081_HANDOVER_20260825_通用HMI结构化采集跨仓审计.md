# 通用 HMI 结构化采集跨仓审计交接

## 本轮结论

目标是面向任意控制器、任意 HMI 页面，由 OCR 与 VLM 联合生成可人工复核的开放式
结构化结果；模板和标准字段目录只提供提示，不得限制新字段发现。人工确认后必须保留
屏幕原始标签、分组、设定/实际角色、逐项标签、单位、证据、来源和置信状态；只有导入
具体试模记录时，才映射到既有标准字段并执行现有业务门禁。

本轮只做只读审计与工作流固化，未修改生产代码、未部署、未重启服务。

## 为什么必须跨两个仓

- `hmi_data_reader` 负责图片/OCR/VLM 输入、候选融合和通用结构化响应协议。
- `mold-data-webpage-tool` 负责自动触发 VLM、保存整份已确认结构、通用 review UI，
  以及将已确认结构显式映射到普通/科学试模字段。
- 只改 Reader，Web 仍只会保存 `confirmed_fields: 字段键 -> 数值`，结构语义会丢失；
  只改 Web，Reader 仍受 `allowed_fields` 白名单限制，无法发现任意页面结构。

因此 Web 仓是本目标的必要组成部分，但不应与 Reader 协议首个 Slice 同时修改。先稳定
生产者合同，再在 Web 仓按其自身 workflow contract 建立独立 PLAN，可避免两个脏工作树
同时漂移。

## 已确认的真实链路与缺口

1. `/api/v1/recognize` 是 OCR + 模板/通用空间规则主链，响应兼容性必须保留。
2. `/api/v1/draft` 已能直接读取原图并结合 OCR evidence，但
   `scripts/vlm_qwen.py::draft_from_ocr` 仍只允许返回调用方 `allowed_fields` 中的字段。
3. Web 已能调用 draft、编辑候选并 PATCH 采集记录，但候选模型只有
   `field_id/values/unit/evidence/status`。
4. Web `confirmed_fields` 只持久化字段键和值，不保存屏幕标签、分组、逐项标签、
   setpoint/actual 关系、来源或冲突。
5. Web 导入仍绑定已有 canonical 字段和普通/科学试模 mapper；这应保留为最终写入门禁，
   不应前移为采集门禁。

## 最小目标合同

```json
{
  "sections": [{
    "label": "温度监控",
    "fields": [{
      "screen_label": "料管温度",
      "canonical_id": "barrel_temperature",
      "role": "setpoint",
      "unit": "°C",
      "items": [
        {"label": "喷嘴", "value": 350},
        {"label": "前部", "value": 320}
      ],
      "sources": ["ocr", "vlm"],
      "evidence": ["屏幕标签或 OCR 原文"],
      "status": "needs_confirmation"
    }]
  }],
  "questions": []
}
```

- `screen_label`、section label 和 item label 保存现场真实文字。
- `canonical_id` 可为空；现有目录仅作为建议，不能阻断目录外字段。
- `role` 至少允许 `setpoint`、`actual`、`limit`、`unknown`。
- OCR 与 VLM 冲突时保留来源并进入人工确认，不静默覆盖。
- VLM 输出永远是候选，不自动写试模记录。
