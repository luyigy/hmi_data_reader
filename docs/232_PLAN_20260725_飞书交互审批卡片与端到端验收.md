# PLAN · 飞书交互审批卡片与端到端验收

## 目标

补齐 workflow watcher 的飞书交互审批卡片，并完成一次由真实审批人操作的受控端到端
验收。卡片只作为现有 PLAN 审批状态机的新输入面，不新增审批状态机。

当前基线：

- 平台 `workflow-watcher` 已为 active，最近调度成功但 `candidate=none`。
- Hermes `coding-handover-watcher` 与 `long-file-checker` 均为 paused；验收期间继续
  保持 paused。
- watcher 当前发送文字 `PLAN_REVIEW`，并轮询 `approve`、`reject`、
  `revise: <反馈>`。
- 平台已有 `sendFeishuInteractiveMessage`、`card.action.trigger`、
  `resolveFeishuCardActionIdentity` 和已解决卡片更新能力，应优先复用。
- `config/projects.yaml` 的 DM、审批人和 active 配置是既有未提交改动，本计划不得
  覆盖或混入无关提交。

## 已确认设计

### 单一状态转换

按钮回调与文字回复必须进入同一个 workflow 审批转换函数：

```text
pending.review
  ├─ approve → approved → watcher 执行现有 reset / Prompt 链路
  ├─ reject  → rejected → 保留终态，不执行
  └─ revise  → revision → 投递现有 PLAN_REVISE，等待新提交后重新审批
```

数据库中的 `ScheduledJobState.cursorJson.pending` 继续是 pending 真相源。卡片回调不得
直接启动 Session，也不得绕过 watcher 的 `execute`、幂等键和 cursor 推进。

文字回复仍由 watcher 读取，但解析后调用同一转换函数；不得保留一套“按钮状态”和
另一套“文字状态”。

### 卡片交互

卡片展示文档名、`plan_path`、`reviewed_commit` 和审批时限，提供：

- **批准**：提交 `approve`。
- **拒绝**：提交 `reject`。
- **修改**：只提示真实审批人回复原审批消息
  `revise: <具体反馈>`；收到文字反馈后再进入 `revision` 并投递现有
  `PLAN_REVISE`。第一版不增加表单或二次弹窗。

卡片 action value 只携带稳定的项目、Job 和 pending key，不携带可篡改的审批结果
上下文。服务端必须重新读取数据库 pending 并校验。

### 安全、幂等与过期

每次转换必须同时校验：

1. 操作者 `open_id` 精确等于项目唯一 `approver_open_ids[0]`。
2. 项目、Job、pending key、审批卡片 `message_id` 与当前数据库记录一致。
3. pending 仍处于可处理的 `review` 状态。
4. 审批未超过合同 `completion_gate.timeout_seconds`；过期后只返回已过期提示，
   不推进状态。

首次有效决定通过数据库条件更新原子落盘。重复点击、按钮与文字竞争、旧卡片点击均
返回当前结果，不重复发送 revise、reset 或 Prompt。卡片状态更新失败只记录并允许
重试，不回滚已落盘决定；业务状态写入失败则不得更新卡片为成功。

## 实施步骤

### S01：审批转换收口

1. 对所有拟修改函数运行 GitNexus upstream impact，报告直接调用方、受影响流程与
   风险；HIGH/CRITICAL 先停下警告。
2. 从 `workflowWatcherHandler` 中提取最小的 workflow 审批读取/条件转换入口，
   继续读写 `ScheduledJobState.cursorJson.pending`。
3. 让现有文字 `approve`、`reject`、`revise: <反馈>` 调用该入口，保持现有 reset、
   Prompt、revision 和 idempotency key 行为不变。
4. 增加一个小型测试覆盖合法转换、错误操作者、过期和重复决定。

验收：

- 没有新增 Prisma model、migration、队列或第二套状态枚举。
- 同一 pending 只能产生一次有效决定。
- 未经真实审批人操作不会进入 approved。

### S02：卡片发送与回调

1. 复用现有飞书交互消息 API 生成 workflow PLAN 审批卡片，并保存返回的
   `reviewMessageId`。
2. 在现有 `card.action.trigger` handler 中仅增加 workflow action 路由；复用现有
   v2/legacy 操作者与消息 ID 解析。
3. 回调调用 S01 的统一转换入口；批准、拒绝后把原卡片更新为已解决，修改按钮返回
   `revise: <反馈>` 的输入提示。
4. 保留文字审批入口；卡片发送失败时本次 watcher run 失败且 cursor 不越过该
   candidate，由既有稳定幂等键安全重试。
5. 扩展最小测试，覆盖“按钮 action → 现有审批状态转换”，不访问真实飞书。

验收：

- 卡片包含批准、拒绝、修改三个操作。
- 非审批人、旧 message ID、旧 pending key、过期或重复点击都不产生副作用。
- 按钮与文字回复得到相同状态结果，批准后仍只由 watcher 执行后续链路。

### S03：专项验证与安全切换

1. 运行 workflow watcher、card action、Scheduled Job Runner 专项测试及
   TypeScript 检查和 `git diff --check`。
2. 运行 GitNexus `detect_changes`，确认只影响预期审批发送、回调和 watcher 流程。
3. 复核 `config/projects.yaml` 原有 diff 未被覆盖，三个平台服务正常，Hermes 两个
   watcher 仍 paused。
4. 重启必要的平台服务并做 `candidate=none` 空闲周期观察；不得为了制造 candidate
   临时篡改 cursor 或目标 Git ref。

验收：

- 所有专项检查通过，GitNexus 未发现意外流程扩散。
- 空闲周期无审批、reset 或 Prompt 副作用。
- 任一异常立即停止后续动作，将平台 workflow watcher 恢复 shadow；Hermes 仍
  保持 paused，等待人工判断，禁止自动双写恢复。

### S04：受控真实端到端验收

实现验收通过后，另行在目标仓库提交一份符合其
`docs/workflow/workflow-contract.yaml` 的可执行测试 PLAN。该 PLAN 必须使用新的
唯一编号与真实提交，不复用或回拨 cursor。

按以下顺序验收：

1. watcher 发现唯一 candidate 并发送一张审批卡片。
2. 核对卡片文档、commit、审批人和三个按钮；在用户点击前所有 Agent 停止操作。
3. 用户亲自选择批准、拒绝或修改。
4. watcher 记录唯一状态转换；批准才执行 reset / Prompt，拒绝不执行，修改提示
   用户输入反馈并等待修订提交。
5. 核对 `ScheduledJobRun`、cursor、飞书卡片终态和目标 Git ref，记录验收结果。

真实验收的通过标准：

- 从 candidate 发现到结果记录只有一个 event key、一个审批决定和一条可解释链路。
- 重复点击原卡片不会再次执行；错误身份点击被拒绝；过期卡片不能推进。
- 文字 `approve` / `reject` / `revise: ...` 兼容测试至少验证一种，并与按钮共用
  状态转换。
- 批准场景只在真实审批人点击后启动下一 Session；拒绝或修改场景不误启动。

## 回滚与停止条件

- 卡片回调身份无法可靠取得、pending 无法原子条件更新、或服务端无法绑定原
  `reviewMessageId`：停止实施，不以客户端字段或内存锁降级。
- 真实验收出现重复执行、错误身份通过、过期审批通过、cursor 跳跃或 reset/Prompt
  顺序异常：立即停止副作用并恢复平台 shadow。
- 不自动 resume Hermes；避免平台状态不明时形成双 watcher。
- 不提交 `config/projects.yaml` 或其他无关工作区改动，除非用户另行明确批准。
