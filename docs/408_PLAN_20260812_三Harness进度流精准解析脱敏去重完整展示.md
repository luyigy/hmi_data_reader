# PLAN · 三 Harness 进度流 ＋ Workflow 自动推进可靠性 ＋ 文档契约闭环 ＋ Workflow 执行权限与会话连续性

> `doc_status` 改为 `ready`、不得把 `next_action` 改为 `start_first_slice`、不得实施任何 Slice。**
> 批准后再逐 Slice 落地，并在执行前补齐各 Slice 的最小回归测试。

## 背景与根因（代码取证结论）

直播室里 kimi-code / pi-agent / antigravity 三种 harness 长时间“静默”，不是 ACPX 收不到
stdout，而是事件没有被**精准解析 → 脱敏 → 去重 → 完整展示**地接到飞书进度卡和直播室时间线。
现有代码已经具备部分能力（codex 与 kimi-code 的思考流、`FeishuProgressTracker` 的节流卡片），
但三种 harness 的覆盖不一致，且 `/run` 角色串行流水线完全没接进度回调。具体证据：

1. **Kimi Code** `src/lib/real-agents/kimi-code-agent.ts`
   - 用 `--output-format stream-json`；`processKimiCodeJsonLine` 只转发 `role:'assistant'` 的
     **整段字符串** `content`、`tool_calls`、`tool_use`、`content_block_start.tool_use`。
   - **缺口**：流式文本增量（`content_block_delta` / `delta`）不转发，`thinking` /
     `redacted_thinking` 不转发，`tool_result` 不计数；工具预览直接用原始 `input`，**未脱敏**。
2. **Pi Agent** `src/lib/real-agents/pi-agent.ts`
   - 用 `--print` 文本模式，stdout 原样转发；**从不调用 `onToolEvent`**，也没有结构化事件。
   - **缺口**：`--print` 会把正文积压到结尾才输出。pi 原生支持 `--mode json`（已由
     `scripts/agent-platform-runner.js` 验证可解析 `event.message.content` 文本块）。
3. **Antigravity** `src/lib/real-agents/antigravity-agent.ts`
   - 用 `--output-format stream-json`；stdout 处理**只转发 `step_update.text_delta`**，
     `extractAntigravityResponse` 从最后一条 `event:'result'` 取正文。
   - **缺口**：**从不调用 `onToolEvent`**，工具/函数调用与其他 `step_update` 子类型丢失。
4. **直播室回放路径** `src/lib/live-room-delivery-execution.ts`
   - 已构造 `FeishuProgressTracker` 与 `liveRoomStreamCallbacks`，已有节流
     （思考 8s、工具 3s、心跳 45s；卡片 1.5s）与基础去重（工具签名、连续思考预览）。
   - **缺口**：`shouldRelayLiveRoomStdoutProgress(harnessType)` 只对 `codex`、`kimi-code`
     返回 true → **pi-agent、antigravity 的思考流被完全排除**；且 pi/antigravity 自身不发射
     工具事件，所以卡片里也看不到它们的工具进度。
5. **`/run` 角色串行流水线** `src/lib/live-room-workflows.ts` + `src/lib/feishu-workflow.ts`
   - 经 grep 确认：这两个文件**完全不引用** `streamCallbacks` / `FeishuProgressTracker`。
   - 阶段执行只发“阶段开始/完成”两条系统消息，阶段内部的思考、工具、心跳一律不可见。
6. **脱敏**：当前只有截断（工具预览 50 字、思考 80 字）。绝对路径、文件内容、命令、token /
   密钥 / HMAC 等可能原样进入飞书卡片与直播室时间线。

## 目标（四个硬指标，三者全改）

- **精准解析**：三种 harness 的 stream-json / `--mode json` 事件都被解析成统一事件模型
  （思考 / 助手正文 / 工具调用 / 工具结果 / 系统），不再依赖单一字段。
- **脱敏**：所有进入飞书卡片与直播室时间线的预览都过统一 `sanitize`：绝对路径转相对/基名、
  遮蔽 token/密钥/签名、截断大块参数与文件内容；`stderr` 原始块只入库不再外发。
- **去重**：统一的签名去重 + 最小间隔节流，跨“适配器 → 回放层 → 卡片”一致；突发流量聚合计数。
- **完整展示**：直播室回放路径与 `/run` 角色串行路径**共用**同一套进度桥；卡片显示当前阶段
  （思考 / 工具 / 等待）、步数、最近工具、已用时与心跳，结束用成功/失败摘要 + 工具 tally 收尾。

## 非目标

- 不改 harness 的任务结果判定（success/fail、会话续聊、completion gate 逻辑不变）。
- 不把原始 stdout/stderr 无筛选地全量转发到飞书（按设计仅发脱敏后的进度）。
- 不引入新的 harness、新命令、新房间 mode 或新调度层。
- 不做 Git Worktree、并行子任务、自动重试策略调整。
- 不改远端 runner（`scripts/agent-platform-runner.js` 已用 `--mode json`），仅对齐本地 pi 适配器。

## 切片总览

本计划含两个**相互独立、可并行推进**的切片组：

- **切片组 A · 进度流（S01–S06）**：解决 kimi-code / pi-agent / antigravity 三种 harness

## 第二部分 · 切片组 B：Workflow 自动推进可靠性

> 来源：科学试模群 Codex 只读诊断 + pi-agent 源码复核 + @antigravity 架构确认。

### B 组背景与根因（已逐条复核源码确认）

科学试模项目出现“039 HANDOVER 已提交但 S03 没启动、Kimi 反而重跑了 S02”。经核验源码，
确认为**两个连续竞态**，并非“正常停止”：

1. **旧 pending 在房间空闲后被重投**（`src/lib/scheduled-jobs/workflow-watcher.ts`）
   - `if (previous.pending)` 分支（`:371`）会先处理旧 pending；房间忙时返回
     `gate=waiting_previous_completion`（`:577`）且 `cursor: previous` 不变。
   - **关键缺陷**：候选扫描（`:590` 的 `git diff scanFrom head`）只在“无 pending”分支执行 →
     只要 038 的 pending 还卡着，后提交的 039 对 watcher **完全不可见**。
   - 房间一空，watcher 投递的是 038(S02)，而不是 039(S03) → Kimi 重跑 S02，S03 从未启动。

2. **提交门禁拦不住同编号并发提交**（`.git/hooks/reference-transaction` +
   `src/lib/scheduled-jobs/workflow-validator.ts`）
   - 钩子用 `git diff --name-only $old $new` 只看**本次提交**改动的文件；两个执行者各自
     提交一份 039 时，第二个提交的钩子看不到兄弟提交里的那份 039。
   - `workflow-validator.ts:537` 只校验编号**位数**（width），**不做唯一性检查**；
     唯一性只在 watcher 运行时（`workflow-watcher.ts:608`）查，那时两份都已落地，为时已晚。

3. **隔离后权威文档不会自动复评**（`workflow-watcher.ts:642-655`）
   - 同一 blob 第二次校验失败即 `quarantined=true` 并把游标前移跳过；注释写明“重新提交产生
     新 blob 才会复验”。
   - 把冲突副本改名成 040（终态）后，权威 039 没有新 blob → 游标已越过它 → `candidate=none`。
   - 当前只能靠人工对 039 追加说明造一个新提交来触发复评。

**架构确认（@antigravity 复核）**：

- B01 超越检查放在 **watcher 入口（`if (previous.pending)` 顶层）判定并清空 pending** 最稳，
  不引入 `supersededBy` 幽灵字段。
- B02 全树编号唯一校验用 `git ls-tree -r --name-only $new -- <watchRoot>`（只读 tree 对象），
  开销 < 5ms，不拖慢大仓提交。
- B03 隔离文档在待选队列为空时，用当前 head 对应路径重验一次。

**B 组非目标**：不回拨 watcher 游标；不改 completion gate 的成功/失败判定；不改角色编排顺序；
不改 append-only 历史保护（恢复一律以“新增提交”方式进行，不 amend/rebase/reset/强推）。

### B01：Watcher 入口的 pending 超越检查

**范围**（`src/lib/scheduled-jobs/workflow-watcher.ts`）

- 进入 `if (previous.pending)` 分支顶层（`:371`）后，先执行一次候选超越检查：用
  `git diff --name-only previous.commit head -- <watchRoot>` 扫描，判定是否存在**编号更大**
  的有效 HANDOVER/PLAN。
- 若存在更高编号文档：输出
  `summary: head=${head} pending_superseded=${previous.pending.path} by=${newerCandidate.filePath}`，
  **清空** `cursor.pending`（置 undefined），**fall-through** 进入下方正常候选扫描流程
  （立即处理 039/S03），不再投递旧 S02。
- 不引入 `pending.supersededBy` 等冗余字段，避免幽灵状态/分支死锁。
- `tests/workflow-watcher.test.ts` 增补：pending=038 且 039 已提交时，watcher 不再投递 038，
  改选 039 并推进；并覆盖 `mode='shadow'` 不改变 cursor 的幂等性。

**完成标准**

- 旧 pending 被更高编号文档超越时立即让位，不再重投旧 Slice；
- `tsc --noEmit`、`test:workflow-watcher`、长文件守卫（`workflow-watcher.ts` 已较大，注意
  抽函数不越 800 行预警线）、`git diff --check` 通过。

### B02：提交门禁做分支级编号唯一性校验

**范围**（`src/lib/scheduled-jobs/workflow-validator.ts` + `.git/hooks/reference-transaction`）

- 在 validator 中新增编号唯一校验：对受保护 ref 的新 commit 执行
  `git ls-tree -r --name-only $new -- <watchRoot>`，从文件名提取编号做 `Set` 碰撞检查。
- 同编号出现两份（含跨目录）即判 `error`：指出现存文档与新增文档路径，拒绝提交。
- 钩子侧无需改动调用方式（已走 `--hook-batch` 调 validator）；validator 抛
  `WorkflowDocumentValidationError` → 钩子按 `WORKFLOW_DOCUMENT_VALIDATION_FAILED` 拒绝。
- 性能：仅当本次提交改动了 `*_PLAN_*.md` / `*_HANDOVER_*.md` 才触发；tree 遍历只读对象、
  毫秒级，对大仓无影响。
- `tests/workflow-validator.test.ts` 增补：ref 已有 039 时再交第二份 039（含跨分支目录）
  被拒并报出现存路径；不同编号放行。

**完成标准**

- 同编号并发提交在落地时即被拦截，不再依赖 watcher 运行时才发现；
- validator 运行时崩溃仍按现状降级为告警（不冻结提交）；`tsc --noEmit`、相关测试、
  `git diff --check` 通过。

### B03：隔离区文档自动复评

## 第三部分 · 切片组 C：文档契约闭环（事前预防）

> 来源：pi-agent 根因分析 + @antigravity 架构决策。

### C 组背景与根因（为什么 HANDOVER 总和规则对不上）

经核验源码，一篇 HANDOVER 要过 **~20 条相互依赖的规则**（`workflow-validator.ts` + 合同）：
YAML 必须是 mapping；`doc_type` 与文件名一致、`doc_status`/`next_action` 在枚举内；**Prompt
标记是最大地雷**——可执行动作必须**恰好一对**标记、终态动作必须**零对**（`promptFrom()`
靠 `split(start).length` 数次数）；Prompt 内容必须引用 plan + handover 文件名；`slice` 必须是
PLAN 里真实存在的编号；PLAN 的 kind/roadmap/父级 slice 校验……

**结构缺陷（链条脆的根因）**：这 20 条规则**只在两个边界生效**——`reference-transaction` 钩子
（commit 时，且只看 `$old..$new` 单提交）和 watcher 扫描（异步、事后）。而 Agent 拿到的只是
`AGENTS.md` 几条散文 + 一个占位符模板——**规则在代码里是严格的机器契约，给 Agent 时却退化
成“请读模板自己悟”**。失败回报还是一行拼接字符串（如 `executable action requires exactly
one prompt marker pair`），Agent 得反推才知道“哦要删掉标记”。本计划作者写 408 时就连续踩了两次
`PROMPT_FORBIDDEN`。

**架构决策（@antigravity 拍板）**：

1. **优先做 C02 骨架生成器**（而非 A 规格下发）——治本，根绝“从零手写格式敏感样板”，极低成本、
   零运行时风险（不碰 watcher/cursor/session）；A 作为 C02 落地后的自然延伸，届时 AGENTS.md
   可极简化为一条强指令“必须用 CLI 生成骨架，严禁手写”。
2. **C01 preflight 必须复用 `workflow-validator.ts` 校验核**（严禁分叉独立脚本，避免规则漂移）；
   通过抽象文件读取层实现 SSOT。
3. **C03 收窄 Prompt 标记高频地雷**。

**C 组非目标**：不改 watcher/cursor/调度；不改 harness；不把原始规则重新发明；不改 append-only
历史保护。C 组所有输出只新增文件 / 新增 CLI 参数 / 改 AGENTS.md 文字，不破坏现有钩子行为。

### C01：Validator 工作区 Preflight + 结构化输出

**范围**（`src/lib/scheduled-jobs/workflow-validator.ts` + `scripts/validate-workflow-documents.ts`）

- 在 validator 内抽象文件读取层为一个 `Reader` 接口（`read(path): Promise<string>` +
  `exists(path): Promise<boolean>`），统一现有 4 处 `git show '${ref}:${path}'` 读取点
  （contract `:104`、exists `:202`、readPlan `:314`、candidate content `:550`）。
- 提供两个实现：`GitRefReader(cwd, ref)`（现状行为，钩子/在线校验用）与
  `WorkingTreeReader(cwd)`（从 `fs.readFile` 读工作区；引用的父级 PLAN 工作区不存在时回退到
  `HEAD`，保证跨文件引用校验不丢）。
- `validate-workflow-documents.ts` 新增 `--preflight <工作区文件> [--json]`：
  - `--preflight` 用 WorkingTreeReader 校验单个文件，**提交前自检**；
  - `--json` 输出结构化 `WorkflowValidationIssue[]`（含 `code/severity/location/message/expected/
    actual/template`），供未来自动修复与 Agent 直接消费；默认仍为人机友好文本（高亮报错 + 修复模板）。
- **SSOT 保证**：钩子的 `--hook-batch` 与在线 `<ref> <doc>` 两种现有入口行为不变，共用同一校验核，
  防止“两套规则又漂移”。
- `tests/workflow-validator.test.ts` 增补：WorkingTreeReader 与 GitRefReader 对同一文档结论一致；
  `--preflight --json` 输出可解析、字段齐全；父 PLAN 仅在工作区缺失时回退 HEAD。

**完成标准**

- `npm run workflow:validate -- --preflight docs/<工作区文件>` 可在提交前精确报出全部 issue；
- 钩子与在线校验行为不回归；`tsc --noEmit`、相关测试、长文件守卫、`git diff --check` 通过。

**完成标准**

## 第四部分 · 切片组 D：Workflow 执行权限与会话连续性

> 来源：试模项目现场反馈（kimi-code 跨仓库 + 浏览器被沙箱阻断、执行后追问变全新会话）+
> pi-agent 根因核验 + @antigravity 架构决策。

### D 组背景与根因（已逐条复核源码确认）

Workflow 执行路径**无条件强制单仓库沙箱**，把成员房间里的 `full_access` 直接覆盖，且事后交互
取不到 workflow 内的 session：

1. **静默降级到单仓库沙箱**（`src/lib/workflow-execution-policy.ts` +
   `src/lib/harness/bubblewrap.ts`）
   - `buildWorkflowPermissionSnapshot` 把权限钉死成 `preset:'workspace'` →
     `sandboxMode:'workspace-write'`、`writableRoots:[projectPath]`（**只有一个仓库**）；
     `validateWorkflowExecutionPolicy` 显式拒绝 `preset` 为任何其他值。
   - `applyWorkflowPermissionSnapshot` 在 snapshot 存在时**整体替换**成员真实 permissionConfig
     （`snapshot ? {...snapshot.effective.permissionConfig} : permission`）。
   - `bubblewrap.ts` 用 `--unshare-all` + `--tmpfs /`，只 `--bind workspaceRoot`：workspaceRoot
     **之外的一切对 agent 不可见**——第二仓库（在 projectPath 之外）消失，宿主机浏览器
     （装在 workspaceRoot 之外、且依赖 D-Bus/X11/Wayland/udev/`/tmp` IPC）即便 bind 二进制也无法
     运行。这正是 kimi-code“看不到另一个仓库、用不了浏览器”的物理原因。

2. **会话不连续**（`src/lib/acpx/session-tracking.ts`）
   - `getParticipantContinuationKey` 用 `(backend, gatewayId, harnessType, role, agentId)` 拼 key。
   - `findLatestParticipantSession`（`:129-145`）的 `where` 含 `role: participant.role`，**精确匹配
     role** 才返回候选。workflow 角色串行里 kimi-code 是某 role（如 implementer），事后交互回复时
     role 为 custom/默认 → **key 不同、查不到 → 全新会话，不知道之前干了啥**。

3. **降级静默**（`src/lib/feishu-workflow.ts`）
   - `runWorkflowInBoundLiveRoom`（`:97`）无条件触发降级；执行卡虽渲染了“Workflow permissions”，
     但只是“现在用什么”，**没有高亮告知“你配置的 full_access 被收敛成 workspace-write”**。

**架构决策（@antigravity 拍板）**：

1. **双轨**：新增 `preset:'full_access'`（跳过 Bubblewrap，走 harness 原生 full access），同时
   `preset:'workspace'` 支持 `extraWritableRoots` / `extraReadOnlyPaths` 满足辅助目录白名单。
   浏览器/多仓库重度场景走 `full_access` 直通（因 Bubblewrap `--unshare-all` 破坏系统 IPC 环境）。
2. **消除静默降级**：Job 级 `execution_policy` 为第一优先级；Job 配 `workspace` 而成员拥有
   `full_access` 时，任务卡必须高亮告警“⚠️ 权限降级：成员拥有 full_access，已按 Workflow 策略
   收敛为 workspace 单目录沙箱”。
3. **会话 Fallback 继承**：Workflow 内部保持按 role 隔离（避免一人分饰 planner+reviewer 串台）；
   交互期取不到同 role session 时，回溯该 Task/Room 中该 Agent 最近一次完成的 workflow
   participant session 续聊。

**D 组非目标**：不改 append-only 历史保护；不改 watcher/cursor；不改 harness 结果判定；不改
房间成员权限模型本身（只在 workflow 执行路径上决定“尊重还是收敛”）。`full_access` preset 落地前
需确认沙箱豁免范围与审计。

---

### D01：权限策略双轨（full_access 直通 + workspace 多根白名单）

**范围**（`src/lib/workflow-execution-policy.ts` + `config/projects.yaml` 校验）

- `validateWorkflowExecutionPolicy` 放开 `preset`，支持：
  - `preset:'full_access'`：snapshot 标记不套 Bubblewrap，走 harness 原生 full access
    （Antigravity `--dangerously-skip-permissions` / Kimi 直调），`applyWorkflowPermissionSnapshot`
    保留成员原有 `full_access` permissionConfig。
  - `preset:'workspace'` 增加可选 `extraWritableRoots: string[]` 与 `extraReadOnlyPaths: string[]`，
    并入 snapshot 的 `writableRoots` / `exceptions`；`bubblewrap.ts` 对这些 root 做 `--bind` /
    `--ro-bind`（满足跨仓库读写与共享 cache 目录）。
- `buildWorkflowPermissionSnapshot` / `readWorkflowPermissionSnapshot` 同步扩展：`full_access` 的
  effective 标记“直通无沙箱”，`workspace` 的 effective 携带 extra roots。
- `readWorkflowPermissionSnapshot` 校验逻辑同步放宽（允许 extra roots、允许 full_access preset），
  保持 snapshot 自洽防算改。
- `tests/workflow-execution-policy.test.ts`（新增或复用）覆盖：full_access 保留成员权限且不触发
  Bubblewrap；workspace + extra roots 正确并入且 snapshot 校验通过；非法路径（越界、绝对穿越）被拒。

**完成标准**

- 跨仓库 + 浏览器项目可配置 `preset:'full_access'` 让 kimi-code 直通工作；辅助目录场景可用
  workspace + extra roots；`tsc --noEmit`、相关测试、长文件守卫、`git diff --check` 通过。

### D02：消除静默降级（显式告警 + 尊重 full_access）

**范围**（`src/lib/feishu-workflow.ts` + `src/lib/workflow-execution-policy.ts`）

- `runWorkflowInBoundLiveRoom` 在生成 snapshot 后，与成员房间实际 permissionConfig 比对：若成员为
  `full_access` 而 Job 策略为 `workspace`，在执行卡（`buildWorkflowExecutionCard`）渲染高亮告警
  “⚠️ 权限降级：成员拥有 full_access，已按 Workflow 策略收敛为 workspace 单目录沙箱”。
- Job 配置为 `full_access` 时尊重成员权限，不降级、不告警。
- 告警同时写入 dispatch metadata，便于事后审计。
- `tests/feishu-workflow.test.ts`（新增或复用）覆盖：workspace job + full_access 成员 → 卡片含
  降级告警；full_access job + full_access 成员 → 无告警、不套沙箱。

**完成标准**

- 任何权限收敛都可见、可审计；用户不再“完全不知道发生降级”；
  `tsc --noEmit`、相关测试、长文件守卫、`git diff --check` 通过。

### D03：会话 Fallback 继承（交互期回溯 workflow 末态 session）

**范围**（`src/lib/acpx/session-tracking.ts`）

- `findLatestParticipantSession`（`:129`）保持“同 role 优先”查询不变；**当同 role 无命中时**，
  增加一道 fallback：放宽 `role` 约束，回溯该 Task/Room 中同一 Agent（backend+gateway+harness+
  agentId）**最近一次 completed** 的 workflow participant session 续聊。
- fallback 仅作用于交互期（role 为 custom/默认，或显式标记为“追问”的投递）；workflow 内部角色
  串行仍按 role 隔离，避免一人分饰 planner+reviewer 串台。
- fallback 命中的 session 同样过现有过滤（`continuationStaleAt`、taskRun 失败、permissionConfig
  一致性），避免继承失效/失败会话；权限不一致时优先采用 D01/D02 决定的实际执行权限。
- `tests/acpx-session-tracking.test.ts`（新增或复用）覆盖：同 role 命中不走 fallback；同 role 无
  命中但存在该 Agent 最近的 implementer session → fallback 继承；fallback 遵循 stale/failed/权限
  过滤。

**完成标准**

- workflow 执行后追问同一 Agent 能续上 workflow 末态上下文，不再“完全不知道之前干了啥”；
- workflow 内部角色隔离不被破坏；`tsc --noEmit`、相关测试、长文件守卫、`git diff --check` 通过。

D01（策略双轨）是 D02（告警）与 D03（会话权限一致性）的前提，**优先做**；D02 紧随；D03 最后。

## 风险与守卫

- **长文件守卫**：`live-room-delivery-execution.ts`、`runner-harness.ts` 等已较大，
  新增职责必须先抽函数/模块再使用，绝不越 1000 行阻断线；开工前跑 `npm run check:long-files`。
- **行为兼容**：pi 切 `--mode json` 必须带 `--print` 回退；不改结果判定与 completion gate。
- **脱敏误伤**：sanitizer 只作用于“展示用预览”，不写库、不改原始事件入库内容。
- **Git 历史**：本仓库工作流历史只追加；本 PLAN 落地期间不 amend/rebase/reset/强推。
- **B 组 watcher 安全**：B01 超越检查只在“存在编号更大的有效文档”时清空 pending，避免误清
  正常等待审批的 pending；B02 的全树校验只拦同编号碰撞，不影响合法重命名/移动；B03 复评
  有节流，隔离未解除不刷屏。任何 watcher 恢复都不回拨游标。
- **B 组与 A 组隔离**：两组改动文件集不重叠（A=适配器/回放层，B=watcher/validator/钩子），
  并行落地时各自独立验收，互不阻塞。
- **C 组 SSOT 红线**：C01 preflight 必须共用 `workflow-validator.ts` 校验核（抽象 Reader 实现），
  严禁分叉独立校验脚本；C02 骨架生成器只产文件、不改 watcher/钩子判定语义，生成后必跑 preflight
  自检；C03 不改 Prompt 标记的判定结果（仍按合同 0/1 对），只升级诊断信息。
