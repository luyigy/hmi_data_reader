# FIX · Workflow 完成回执重复发送修复

## 问题与根因

- 可执行 HANDOVER 通过校验并发送完成回执后，如果旧 Session 尚未结束，watcher 会把整个游标回退到执行前状态。
- 下一轮扫描因此把同一 HANDOVER 当成未处理文档，再次发送校验通过消息和完成回执，直到旧 Session 可以结束。
- 飞书发送层已有幂等 UUID，但正常轮询不应反复进入发送层；服务在游标落盘前失败时则仍需复用同一 UUID 兜底去重。

## 修复

- 首次发送完成回执后，将可执行 HANDOVER 保存为现有 `workflow_ready` pending，并保留原 event key。
- 旧 Session 未结束时只轮询现有 pending；不重新校验文档，也不重发完成回执。
- manual 自治模式继续阻止定时自动推进；手工执行复用同一 pending 和 event key。
- Session 成功启动后清理 pending，同时保留原 HANDOVER commit 游标，避免跳过等待期间新增的后续文档。
- 未新增 Schema、迁移或第二套状态机。

## 验证

- `npm run test:workflow-watcher`：覆盖连续等待只发送一次完成回执、manual 轮询不重发，以及手工推进复用 event key。
- 模拟“消息已发送但游标未保存”后重试，确认飞书请求复用同一个 32 位幂等 UUID。
- `npm run test:workflow-roadmap-inbox`：通过。
- `npm run test:scheduled-jobs`：通过。
- `npx tsc --noEmit`：通过。
- `npm run check:long-files`：通过，无达到 1000 行阻断阈值的文件。
- `git diff --check`：通过。
- GitNexus 修改前影响分析为 LOW：3 个直接调用者，均为 watcher/roadmap 测试入口；最终变更检测未发现 watcher 既有执行流程之外的意外扩散。

## 防止复发与后续边界

- 回归测试固定验证：游标成功保存后，等待和 manual 轮询均不会再次进入完成回执发送层。
- 游标落盘前进程失败的窄窗口继续由既有飞书 UUID 幂等能力处理。
- 本修复不改变卡片入口、审批、Workflow Dashboard 或 Session 结束判定。
