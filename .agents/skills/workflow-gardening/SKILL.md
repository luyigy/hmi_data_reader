# 任务图 Gardening

在当前交付闭环之外运行本流程。报告失败留待后续处理，不能改变路线审批、ExecutionOutcome、依赖放行或 Issue 完成状态。正常交付可以没有新教训。

## 步骤

1. 读取本仓 `docs/agents/issue-tracker.md`、`domain.md` 和本次相关 Spec。以实际 Run、node、execution、TaskRun 和提交标识收集原始事件。区分当前状态与历史事件，记录读取时间。
2. 查找 `docs/gardening/` 的既有报告。按根因归并重复事件，不按错误文案或出现次数猜测共同原因。没有重复证据时明确写“尚未证明重复”，允许结束为无新增防线。
3. 沿实际代码确认根因，分类为平台、业务代码或 Agent 方法。记录现有防线及其边界。优先复用已有架构、类型、Lint 或行为测试，必要的实施另按原仓授权与审批执行。
4. 在一次性副本中注入准确的历史错误，运行相同检查。失败必须命中预期行为差异。依赖缺失、启动异常或超时不算红色证明。恢复正确源码后，同一检查必须通过。
5. 请未参与实现的 Verifier 检查红绿日志、代码与影响面。只有具体错误被拦截、正确行为通过且独立复核通过，才把防线记为 Active。条件不足时保持 Proposed，保留下一步，不能合成成功。
6. 在 `docs/gardening/<根因>.md` 记录根因、重复证据、修复提交、检查命令、红绿回执、Verifier、状态与局限。追加已验证的拦截记录；未实际观察到的后续拦截次数写“未测量”。给用户一段短摘要与报告链接，详细日志只放折叠详情或报告。

## 历史案例入口

跨服务 TaskRun 归属案例见 `docs/gardening/taskrun-owner.md`。运行 `node scripts/verify-taskrun-ownership-wire.mjs` 可在独立 schema 与一次性源码副本中重演。脚本只移除图任务归属守卫，保留当前实现，输出独立的红绿日志及源码和测试摘要。
