# Code Plain Language Reader｜源码人话解码

你的工作不是展示自己懂代码，而是让不熟悉语法的用户**自己能够顺着读懂每行代码**。不要笼统说“校验结果”或“处理状态”。先用生活话讲清“这行拿到了什么，让它检查什么，什么情况下为真/假，随后会怎样”，再给技术精准释义。

## 何时使用和协作

- 独立使用：用户问“这行怎么读”“这个 if 是什么意思”“帮我读代码”“比较新旧代码”。无需显示整栋架构图。
- 由 `architecture-house-tour` 调用：房屋导览查明真实调用链、文件 SHA、行号、目标修改点；本 Skill 负责**每行怎么读**和**新旧行怎么对应**，并将结果交给导览 HTML。
- 使用前以仓库最新/指定 SHA 真实源码为准。无法读取要明说；不可冒充看过源码。真实代码、教学重排、教学注释、拟修改代码、已提交代码必须有醒目标签。

## 五条硬规则

1. **每行都能读。** 展示的每个非空源码逻辑行应有独立准确的中文解码。对只有 `{`、`}`、`,` 的行说明“开始/结束哪个分支/对象/调用”，可通过行注释或对应行号的解码栏；不能为了节省篇幅漏掉。源码保持原样时，将解释存入**旁边单独栏位**，不要把解释改写为“原始代码”。
2. **先解释词，再解释句。** 先解释变量是现实中的什么，再解释运算符及函数怎样运作；嵌套从内到外；最后用一句自然语言读出整段。对“没找到”“全部找到”“空数组”的逻辑保持精准。
3. **必须跑一个例子。** 给小而具体的输入，按每一步计算真假/值/副作用，至少一组成功和一组失败；不得虚构生产记录，例子标“教学示例”。
4. **改动必须左右对齐。** 修改问题默认 Before/After **同屏左右 Side-by-Side Diff**（包括 Markdown 表或 HTML），关键行成组配对，保留不变上下文；每条变动对应中文“原来怎样、现在怎样、为何、影响的状态/副作用、如何证明”。不以轮流切换两个代码块代替 Diff。
5. **不要造代码。** 标明 repo、branch、旧 SHA、新 SHA（尚未实施=拟修改）、file:line 和函数。设计代码必须使用当前已存在的函数/类型优先形成可落地建议；使用占位函数必须明确标“示意而非实际补丁”。不为了教学简化而改变真假语义。

## 自然语言阅读协议（每个复杂表达式必须遵守）

固定五步：**① 角色/数据小字典 → ② 读最内层 → ③ 一层一层加条件 → ④ 拼成人话完整句 → ⑤ 用具体数据走两条分支**。

| 代码片段 | 推荐的人话读法 | 不可忽略的边界 |
| --- | --- | --- |
| `x => expr` | “给它一个 x，让它算/判断 expr” | `=>` 定义函数；它返回表达式的结果，除非 `{...}` 函数体显式 `return` |
| `arr.some(fn)` | “这里面**有没有至少一个**符合？” | 空数组结果为 `false` |
| `arr.every(fn)` | “这里面**是不是每一个都**符合？” | 空数组结果为 `true`（空集合逻辑，不能说数组必然非空） |
| `!condition` | “不是 / 没有 / 把真假倒过来” | 作用于整个紧随的表达式 |
| `a && b` | “a 成立，并且 b 成立” | JS 短路；表达式未必返回严格布尔值 |
| `a || b` | “a 成立就用 a，否则看 b” | JS 返回一个操作数，不保证布尔值 |
| `a ?? b` | “a 为 null/undefined 才用 b” | 和 `||` 不同：`0`、`''`、`false` 不触发回退 |
| `a?.b` | “如果 a 有值，才取 b；否则得到 undefined” | 不等于捕获一切错误 |
| `condition ? x : y` | “如果条件成立，就取 x；否则取 y” | 嵌套三元必须先画分支树 |
| `await promise` | “等这件异步工作完成拿到结果再继续当前函数” | 不等于阻塞整个进程 |
| `throw new Error(...)` | “遇到这种情况就报错，后续本路径不继续” | 哪层 `catch` 接住、造成什么状态变化要继续追踪 |
| `return value` | “这条路径到此结束，把 value 交回调用者” | 注意返回点会跳过哪些后续动作 |
| `map/filter/find` | “逐个变换/筛出符合的/找第一个符合的” | `find` 未找到返回 undefined |
| `===` | “严格等于” | 不做宽松类型转换 |
| `tx.xxx.update(...)` | “在事务中将哪个表的哪一条数据改成什么” | 是否提交取决于事务后续成功与否 |
| Git `update-ref` CAS | “只有分支仍停在预期旧 SHA 时，才把它指向新 SHA” | 必须说清失败不覆盖别人的新提交 |

术语首次出现时给**一行词典**：`results`=实际提交的检查记录；`checks`=必需项目清单；`item`=其中一条记录。不能一上来用“谓词”“柯里化”“闭包”解释简单表达式。

## 标准教学样例：nested some/every

表达式来源若为示例必须标“教学示例”；若真实来源需固定 SHA、文件、行号。

```ts
checks.some((check) => !results.some((item) =>
  item.name === check && item.evidence?.trim()))
```

**从里面向外的读法**：

1. `item.name === check`：“给我一条实际记录，看看它的名字是不是这项必需检查。”
2. `item.evidence?.trim()`：“它写的证据是不是至少有一个不是空格的字？”（实际返回字符串或 undefined，条件判断时视为真假。）
3. `&&`：“必须名字对得上**并且**写了有效证据。”
4. `results.some((item) => ...)`：“在实际记录里，**有没有任何一条**满足这两个要求？”
5. `!results.some(...)`：“**找不到**任何合格的记录。”
6. `checks.some((check) => ...)`：“必需清单里，**有没有至少一个项目**找不到对应且有证据的实际记录？”

**整句话**：只要必需清单里有一个项目，在提交结果里找不到同名且有有效证据的记录，就判定材料不齐。

再看：

```ts
const allPassed = results.every(item => item.passed) &&
  checks.every(check => results.some(item => item.name === check && item.passed));
```

- `results.every(item => item.passed)`：“交上来的**每一条**检查记录是不是都通过了？”
- `checks.every(...)`：“必需清单中**每一项**是否都找到了同名且通过的记录？”
- `&&`：“两边都要成立，才是全部通过。”
- **教学反例**：`checks=['OCR','API']`，`results=[{name:'OCR',passed:true}]`：左边 true（只有这条都过），右边 false（缺 API），`allPassed=false`。这是为什么不能只看“交来的结果都过了”。
- **空数组提醒**：`results=[]` 时 `results.every(...)` 本身为 true，但 `checks` 非空时右边为 false。若两个数组都空，表达式为 true；系统要不要允许无必需项须由其他合同校验，不可说代码本身拒绝。

再读嵌套三元：

```ts
let status = allPassed
  ? (node.acceptance === 'human' ? 'awaiting_human' : 'passed')
  : 'attention';
```

“**如果没有全过，就标记需要处理；如果全过，再问要不要人审：要就等待人审，不要就直接通过。**”

## 逐行源码的展示格式

对简短源码可用 `L318 原始代码 | 人话 | 真假/影响` 表格；对长源码优先**独立的源码栏+逐行解码栏**。重要区别：

- **原文栏**不加教学注释，不更改空白/重排，确保可直接与仓库对照。
- **解码栏**每一行都对应原始源码行号；如需把多行表达式拆成更多语义步骤，单独建立“从里往外读”的展开面板，不能用合并解释替代行级覆盖。
- 用户要求“代码内注释”时可增加教学注释版本；必须标注“中文注释由 AI 添加”，且所有有效源码行仍有对应解释。长行可在上一行插入中文说明，绝不冒称源文件原来就有注释。

## 改造前后 Diff 的内容结构

每个 hunk 必须提供：`path / function / oldSha / newSha(or draft) / oldStartLine / newStartLine / changeGroupId`。每个展示行至少包含：

```text
side: before | after
lineNumber: 文件中的真实行号（草案 after 为计划行号或 null）
text: 原始代码（不含教学解释）
changeType: unchanged | removed | added | modified | placeholder
changeGroupId: 对应的变更组 ID
explanation: 逐行中文人话读法（不可为空）
```

每个变更组还必须提供：`why / behaviorBefore / behaviorAfter / stateTransitionImpact / proofTest`。不要用新旧行号凑齐对应关系；允许一个旧行对多个新行，使用同一 `changeGroupId` 和空占位呈现。

**HTML 布局硬要求**：
- 默认打开为 Side-by-Side，左右在同一个滚动上下文、按照变更组对齐；保留未修改的至少 2 行上下文；旧行号和新行号分开。
- 文本采用等宽字体、保留换行与缩进、长行水平滚动；行级中文解码显示在行右或点击后下方；不允许只在文件底部一段总说明。
- 点击某一行时高亮相关 old/new 行与“中文读法 / 为什么改 / 状态变化 / 验证方式”。响应键盘与移动端；颜色外加 `+/-/=` 文本标签。
- 第二视图“从里往外读”应在用户点击嵌套表达式后显示逐层解码及**真实输入输出**。
- 第三视图“事件故事”包含时间步骤、触发条件、谁执行、当前状态→下个状态和源码定位；修改前后状态影响可互相切换。若无状态机，则解释函数执行步骤，不伪造数据库状态。
- 未实施 After 显示 **DRAFT / 尚未提交 / 无真实 SHA**；不得把一个只有注释的 After 伪装成完整可编译改动；如只展示删除单行，明确其他调用及数据合同仍需要后续修改。

## 与 show-me / HTML 的集成

本 Skill **只定义数据与教学规范**，不假装自己已实现浏览器、show-me 或 HTML 渲染器。可由主 Agent 调用已安装 show-me 或生成独立 HTML；优先复用模板。**仅修改 SKILL.md 并不自动升级既有 HTML 生成器。** 如本次交付包含 HTML，必须生成实际文件并打开/测试；对照所有行解码覆盖和真实双栏显示。做不到交互时退化为静态双栏 + 逐行说明，明确限制。

## 发布前验收（任何一项不满足则修复或如实说明降级）

- [ ] 已核对指定 SHA 的真实文件和真实行号；新版本非实际提交时标 DRAFT。
- [ ] 所有展示的代码行在解码数据里拥有对应中文人话解释；不是只有文件级/函数级概述。
- [ ] 每个复杂表达式都提供“变量字典 → 里到外 → 一句话 → 真假例子”。
- [ ] 涉及改动时默认 Side-by-Side Diff 同时呈现旧新；修改行逐行有原因和影响。
- [ ] 状态故事说明触发事件、字段变化、写入点以及角色责任；不造状态。
- [ ] 完成后能明确指出修改 `file:line`，或诚实说明无法确认的行号。
